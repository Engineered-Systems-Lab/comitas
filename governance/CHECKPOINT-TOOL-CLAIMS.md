# Checkpoint tool: claims and execution status

Part of the [checkpoint tool notes](CHECKPOINT-TOOL.md), which list the files by purpose. The claims database, execution status and the commands that read them.

### Claims and execution status

The tools declare their ref windows in a small local database, and `worktree.py execution-status` reads them next to evidence derived from Git. The [local coordination procedure](LOCAL-COORDINATION.md#execution-status) owns who reads the status and what the levels mean; this section is the implementation.

- **Store.** `governance/tools/worktrees/claims.py`, standard library `sqlite3` only. One file, `.local/claims/claims.sqlite` with its WAL files, in the primary checkout, which is the parent of the Git common directory. `/.local/` ignores it; it is local disk only, never committed or backed up, and rebuildable because it only mirrors what the derived evidence shows. The code refuses a symlinked, junctioned or non-directory `.local` or `claims` folder and a folder that Git does not ignore, creates the folder on the first write only, and opens read-only for reads, so a read creates nothing. Writes run in `BEGIN IMMEDIATE` with a 5 second busy timeout.
- **Schema version.** MAJOR.MINOR, kept in `PRAGMA user_version` as MAJOR times 1000 plus MINOR, so 1.0 is 1000. A minor adds fields: a tool with a lower minor upgrades the file additively inside one transaction, and a tool with a higher minor reads it and leaves it untouched. A different major is incompatible: the tool reports `schema_incompatible` with both versions, leaves the file alone and runs on derived evidence.
- **Tables.** `claims` holds one row per window: kind, scope (`prepare` or `lifecycle`), owner (the mission ID of the `tx/<id>` branch), Job handle, state, since time, worktree, process id and its start token, and the close time, with at most one open row per owner and scope. `events` is append-only: opened, state and closed with its reason. Levels are never stored. Schema 1.1 adds `claim_paths` (claim, path, class and the comma-joined subclasses) and a second kind of claim, `paths`, one open row per owner, which holds what the mission's preview named; a 1.0 tool never reads it and a 1.1 tool reads a 1.0 file without it. A closed claim keeps no path rows, and the append-only events add `landed`, `attention`, `cleared` and `reconciled`, which belong to no claim except the landing.
- **Hooks.** In `checkpoint.py`, `main` wraps each command in `claims.command_window`. Prepare, seal and resume open a window with the process id and start time, and on the way out keep it as `validated` or close it, by the packet state. Abandon, finish, commit and the approval decision close the owner's window. In `worktree.py`, `lifecycle_lock` declares a lifecycle window for create, reconcile, integrate and remove while it holds the lock, and the integration guard hashes `claims.py` with its other files (`claims_sha256`). Schema 1.1 adds hooks. `checkpoint.py preview`, which takes the optional `--job-handle`, writes the owner's path claims from the manifest's classification views (path, class and subclasses, a deleted path included) and replaces the owner's earlier ones; it is still read-only for the repository, and the claims database is the one thing it writes. Abandon releases the owner's path claims and writes an `attention` event; finish and commit keep them, because the work has not landed. `worktree.py`'s command line writes the `landed` event, which names the owners it overlapped, and releases the owner's path claims in one transaction after a guarded integration succeeds (`integrate` takes `--job-handle`), releases them after a removal and writes a `reconciled` event after a reconciliation. A failed prepare or seal, an abandon and an integration that stopped each write an `attention` event with the reason, the owner and the Job handle.
- **Never a gate.** Every hook is best effort. A failure prints one `NOTICE: claims database <state>: <reason>; continuing on derived evidence` line on standard error and the command continues; the states are `missing`, `locked`, `unreadable`, `corrupt`, `refused` and `schema_incompatible`. No hook raises into prepare, seal, approve, commit, finish, integrate or the other lifecycle operations, and none of them reads the database to decide.
- **Process liveness.** The standard library only: on Windows `ctypes` calls `OpenProcess`, `GetProcessTimes` and `GetExitCodeProcess`, and elsewhere `os.kill(pid, 0)` and the `/proc` start time. A pid whose start token differs is a reused pid, not the command. A negative observation can also reflect restricted process visibility: the status flag and diagnostic messages therefore say "unknown or dead". The `running` values and inspection logic are unchanged; this wording does not establish death or authorize cleanup.
- **Status payload.** `schema` is the string `"1.1"`; a reader accepts any minor of its own major and ignores fields it does not know. The fields are `level`, `line`, `read_at`, `windows`, `declared_without_evidence`, `database` (`state` and `message`) and `derived`. Each window has `owner`, `scope`, `state`, `job_handle`, `since`, `worktree`, `evidence`, `declared`, `command` (`pid` and `running`), `flags` (`undeclared`, `unknown_or_dead_command`, `age`) and `age_flag`. Schema 1.1 adds `claims` (one row per active owner: `owner`, `job_handle`, `level`, `subclasses`, `files`, `since`, `flags`), `overlaps` (`owners`, `kind` as `same_file` or `same_subclass`, the shared `files` and `subclasses`, and the `text`), `base_moved`, `stale_claims` (the stale claims the tool cannot prove dead, which the lead developer clears), `stale_claims_clearing` (the provably stale ones that the next claims-writing command clears itself; a reader that does not know it ignores it), `owner` and `notes`. The level is FROZEN when any derived window exists, otherwise OVERLAP when two live owners share a file or a subclass, CLEAR when neither and UNKNOWN when the derived evidence cannot be read; a declared window without live evidence is listed and never freezes. The age flag shows after 60 minutes for a prepare and 10 for a lifecycle operation.

- **Path claims and overlap.** A claim lives while its transaction exists, meaning its worktree is registered and its branch exists; a claim whose worktree is gone is stale and is ignored for every decision. It is counted in `stale_claims_clearing` when the tool can prove it dead (the worktree is in no entry of `git worktree list` and no `tx/<mission>` branch exists) and in `stale_claims` otherwise. Two live owners overlap when they share a file (compared without regard to case, and leaving out a file that both only add to as a [proved append](CHECKPOINT-TOOL-CARRY.md#append-only-lists)), worded `same file(s): a.py, b.py` because a textual conflict is probable, or, with no shared file, a subclass, worded `same subclass, different files: checkpoint` because the change usually carries forward. The overlap is computed at read time and never stored, and it only predicts: whether an approval carries forward after the other owner lands is decided by the diff-bound proof and never by a claim. When the other owner lands, its claims are released and the waiting owner's read says `base moved: main advanced to <sha> by <owner>; <what is known>`, until its next preview, reconcile or carry. What is known comes from read-only facts: with the carry switch true and the owner's branch committed with an approval record, it says that `worktree.py carry` can try the approval, which no gate has judged yet; otherwise it says that the carry is off, that nothing is committed and approved to carry, or that the record gate would refuse. It evaluates no gate that needs work, so it never promises a carry.
- **Commands.** Run them from the primary checkout through the launcher, with `--main` naming it: `create`, `integrate` and `remove` need the main checkout, because the reviewed committed tooling owns the promotion and a candidate never re-executes itself.

| Command | Who runs it | What it does |
| --- | --- | --- |
| `execution-status [--json-only] [--owner <mission>]` | anyone | Reads the level, windows, claims, overlaps and notes; always exits 0; `--owner` narrows the overlap and base-moved parts to one mission. |
| `execution-status --wait-clear [--timeout <s>]` | the worker, before a prepare | Polls the status about every 5 seconds inside the tool and exits 0 as soon as the level is CLEAR or OVERLAP, printing the one human line. After the timeout (300 seconds by default) it prints the line that names who holds the window on standard output, `FAIL: ...` on standard error, and exits 3. UNKNOWN is not clear. It only reads and writes no window; it cannot be combined with `--watch` or `--json-only`. |
| `execution-status --watch [--all] [--interval <s>] [--polls <n>]` | the Coordinator, attached through a monitor | Prints one flushed line per landing or per thing that needs attention and nothing else, until interrupted (`--polls` stops it after that many polls). `--all` also prints the routine events, for diagnosing. |
| `clear` | the lead developer, in a terminal | Lists every open claim as STALE or LIVE with its evidence and prints what it would clear; changes nothing. |
| `clear --apply [<id> ...]` | the lead developer | Clears every STALE claim, or exactly the named ones. A LIVE claim needs `--even-if-live`, which prints its evidence and asks for the id to be typed again. |
| `doctor [--repair]` | the lead developer | Checks the schema version, integrity and orphan rows and prints `would repair:` lines; `--repair` applies exactly those. |
| `checkpoint.py preview --job-handle <handle>` | the worker | Writes the mission's path claims; see the hooks above. |
| `worktree.py integrate --job-handle <handle>` | the guarded integration | Names the Job in the `landed` event and the lifecycle window. |
| `worktree.py carry --path <checkout> --owner <mission> --expected-main <sha> --expected-tip <sha> [--job-handle <handle>]` | the worker, or the delegated lifecycle | [Carries the approval](CHECKPOINT-TOOL-CARRY.md#the-carry) of a finished, committed branch onto a moved main; moves nothing unless every gate holds; names the Job in its lifecycle window and writes a `reconciled` event that ends the base-moved note. |
| `worktree.py carry-go --path <checkout> --owner <mission> --expected-main <sha> --go <file> --message <file> [--worker-context <file>] --output <file> [--job-handle <handle>]` | the worker | [Carries the go](CHECKPOINT-TOOL-CARRY.md#the-go-carry) given at a preview, or at a staged transaction, onto a moved main and moves the worktree there; moves nothing unless every gate holds; writes a `reconciled` event that ends the base-moved note. |

- **The watch.** One line each, starting with `LANDED` or `ATTENTION`, then the reason, the owner, the Job handle and the time. A landing is the `landed` event of a guarded integration. Attention is a prepare or seal that ended `prepare-failed` or stopped, an integration that stopped, an abandoned transaction, a window whose declared command is unknown or dead while the window is still open or with no transaction behind it, and a Job record that the worker set to BLOCKED or whose reported activity is STOPPED while its window is open. Routine events (a window opened or closed, a claim declared or cleared) stay quiet, and so does everything that existed before the watch started. Each attention condition prints once until it clears. There is no heartbeat: a worker whose session simply ended without writing anything shows only indirectly, and the lead developer watches for that. Without a readable database it prints one notice and polls the packets, the operation locks, the worktree list and the tip of main: a landing then reads `LANDED (inferred, claims database unavailable) main advanced <a>..<b>` with no owner or Job, and a failed integration is invisible. The command reads only, never blocks the approval machinery and names no vendor.
- **Self-clearing.** A provably stale claim is cleared by the next command that writes claims: `checkpoint.py preview` and `prepare`, and a successful `worktree.py integrate` or `remove` (`execution-status` only reads). The proof is the one above and Git must answer; a claim whose recorded worktree path is still listed, whose owner is not a mission id or that belongs to the mission whose command runs is kept, and windows are never swept. Each clearing prints one `NOTICE: cleared stale claim ...` line on standard error that names the mission and why, closes the claim with a `cleared` event holding the evidence and `automatic: true`, and appends one line to `.local/claims/clearing.log`. A missing, locked or unreadable database changes nothing.
- **Clearing.** The lead developer runs `clear` in a terminal; the tool cannot authenticate who runs it, so the rule is a convention in the briefs: workers and the Coordinator never run it and report a stale claim the tool did not clear instead. Each claim shows a short id (`c7`), its status and its evidence: whether the worktree is registered, the branch exists and the packet state, whether the derived evidence still shows a window, the process id and whether it runs, and the Job record's state. The transaction wins over the Job record, which never clears a claim: a Job marked COMPLETE or CANCELLED while its transaction exists is shown as a conflict and stays LIVE. A window whose command is unknown or dead while its transaction still exists is LIVE, and clearing its claim does not unfreeze the refs, which the derived evidence still holds. Every clearing closes the claim with a `cleared` event holding the evidence, prints what it cleared and appends one line to `.local/claims/clearing.log`.
- **The lead developer's entry point.** `governance/scripts/claims.sh` finds the primary checkout from its own location and the Git common directory, starts `worktree.py` with `py -3` (or `python3`, then `python`, only when `py` is absent) and runs `worktree.py --main <primary> <command> [args]` from there: `execution-status` (alias `status`, short `-e`), `watch` (`execution-status --watch`, short `-w`), `clear` (short `-c`) and `doctor` (short `-d`). It adds no logic, prints the tool's output unchanged, returns its exit code, never adds `--apply` or `--repair` and refuses every other word with a usage line. Workers use the command form in the table.
- **The guard and the status.** The [runtime guard](CHECKPOINT-TOOL-COMMANDS.md#runtime-guard) refuses every GATED command at once while a lifecycle operation holds its lock, and lets the READ commands through, among them the exact read-only forms `governance/tools/worktree.py --main <path> execution-status ...` and `paths`, which must answer while an integration or removal runs. That is also why `--wait-clear` works while a window is open. Workers write no loop for the refusal: they run the command again after the operation finishes, and `--wait-clear` waits for the status.
