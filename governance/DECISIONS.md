## G018 - Delegated checkpoint authority and continuity (2026-10-01, Accepted)

Adopt the [checkpoint workflow](CHECKPOINT-WORKFLOW.md): the lead developer retains explicit scope and full exact-message commit authority; review challenges scope/evidence; bounded workers prepare, execute and report; deterministic tools prove mechanics without interpreting governance or granting authorization. This is governance for future tooling, not an instruction to stage, commit or implement it now.

The existing checker requires the latest runtime SHA in Progress and exactly one matching indexed devlog entry, but that SHA exists only after commit. Recognize a bounded `checkpoint committed; continuity follow-up pending` phase for a verified authorized runtime commit, followed by separately delegated fresh-worker record preparation and full final continuity validation. Pending never means PASS, never excuses unrelated failures, and never weakens the final invariant. Keep historical-record follow-up unstaged/uncommitted unless separately authorized, and do not advance the runtime checkpoint for documentation/tooling-only commits. Record-only commits do not recursively require logs. This durable authority boundary belongs in a standing decision; execution details remain in the workflow.

### G018 approval UX refinement (2026-10-03)

Lead developer approval is unambiguous consent to the exact presented transaction; receipt mechanics are tooling responsibilities. The lead developer gives a direct command in the active conversation after reviewing the complete final sealed transaction/message. The agent records the original user reply against that exact identity without requiring token copying or a local approval command. Explicit source/context verification remains an agent execution obligation; local keyed receipts authenticate integrity, not conversation authorship. Worker text, embedded approvals and ambiguous praise supply no authority. Every reseal, changed bound fact or stale-base reconciliation requires fresh consent. Preserve exact parent/tree/message/manifest/evidence verification, continuity, evidence binding and guarded integration/cleanup. See [the workflow](CHECKPOINT-WORKFLOW.md#exact-approval-and-execution) and [tooling contract](CHECKPOINT-TOOL.md#conversation-consent-interface-agent-execution-contract).

This is a durable chain-of-command obligation, meeting the registry threshold. A human command decides authorization; tooling carries out the receipt mechanics. G018's exact final authorization remains intact. This transaction must land through the previously authoritative exact-token path; it cannot authorize itself with its new semantics.

### G018 deterministic approval decision (2026-10-05)

G018 commit authorization is a deterministic `approve` or `reject` decision bound to the exact sealed transaction: its transaction identity and complete prepared digest. Interactive hosts SHOULD present explicit Approve / Reject controls; selecting a control MUST yield exactly that decision, so a presented Approve control never produces a value tooling rejects. Hosts without such controls use the canonical text tokens `APPROVE` and `REJECT`, matched exactly apart from surrounding whitespace. General natural-language interpretation is not part of the commit authorization boundary: wording such as "Approved.", "Go ahead." or emphatic prose neither approves nor rejects, and the agent requests the control or token instead. Reject never authorizes and withdraws any approval recorded for that seal. Ordinary conversation remains natural language. The repository defines a vendor-neutral request/decision contract; host adapters render it and never fabricate a selection. See [the workflow](CHECKPOINT-WORKFLOW.md#exact-approval-and-execution) and [tooling contract](CHECKPOINT-TOOL.md#conversation-consent-interface-agent-execution-contract).

This partially supersedes the 2026-10-03 approval UX refinement above, whose text is retained as history: its natural-language recognition (example phrases and equivalent affirmative variations) no longer authorizes commits. Its other obligations stand: a direct lead developer decision in the active task after review of the complete sealed transaction/message, agent source verification, no copying of internal identifiers, no self-authorization by worker, quoted, repository or tool text, a fresh decision after every reseal, changed bound fact or stale-base reconciliation, and exact parent/tree/message/manifest/evidence verification. New commits do not accept superseded `approver-consent-v1` receipts; the exact legacy typed-token recovery receipt is unchanged. A recognizer that understood clear approval yet refused it over punctuation was validating syntax, not authorization; failing closed on the wrong predicate is still a bug. This transaction lands through the previously authoritative consent path; it cannot authorize itself with its new semantics.

### G018 decision-channel equivalence (2026-10-05)

The authorization boundary validates the decision, not the presentation mechanism. A lead developer decision from the active-task user, verified by the agent under the existing trust boundary, that yields the canonical `approve` or `reject` decision bound to the exact transaction identity and complete prepared digest carries the same authority whether the host produced it from a selected control, a menu choice or typed canonical input. One exact response table applies on every declared channel: the control labels `Approve` / `Reject`, the canonical tokens `APPROVE` / `REJECT` and the machine values `approve` / `reject`, ignoring only surrounding whitespace. The declared channel remains required, recorded provenance; it MUST NOT alter the authorization result, and an undeclared channel fails closed. A host that returns the same answer for a selected option and for typed text therefore need not prove the physical gesture. This adds no authentication: the source remains the agent's verified assertion about the active task, not cryptographic user identity.

Everything else stands: general natural-language interpretation remains outside the boundary (prose, other casing, punctuation, emphatic or embedded wording are invalid on every channel); exact seal binding, Reject's non-authorizing withdrawal, fresh decisions after every reseal or stale-base reconciliation, replay refusal, receipt integrity and the legacy typed-token recovery receipt are unchanged. The receipt kind remains `approver-decision-v1`; every previously valid receipt stays valid. See [the workflow](CHECKPOINT-WORKFLOW.md#exact-approval-and-execution) and [tooling contract](CHECKPOINT-TOOL.md#conversation-consent-interface-agent-execution-contract).

This partially supersedes the 2026-10-05 deterministic decision above, whose text is retained as history: only its channel-specific response mapping (controls by label or value, text by uppercase token only) no longer applies. Requiring proof of a button click that the host could not express made a safe adapter impossible without protecting anything. Fail-closed is good; failing closed on an irrelevant distinction is still a bug. This transaction lands through the previously authoritative deterministic path; it cannot authorize itself with its new semantics.

### G018 abandon extension (2026-10-07)

A transaction that has not begun to commit can be withdrawn with `abandon`. It authenticates the sealed packet, requires HEAD and the branch to equal the sealed parent, refuses when anything outside the manifest is staged, unstages exactly the transaction's own paths and clears the scratch slot. It changes no working byte, ref or other index entry, runs no suites, archives nothing and may be repeated. A transaction in committing, commit-attempted, verified or follow-up-pending is refused; use `verify` or `finish`. See [the tool](CHECKPOINT-TOOL.md#state-and-evidence) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

### G018 timing record extension (2026-10-07)

The checkpoint tool keeps an advisory, machine-local record of how long each check takes. `estimate` states the expected seal time with its basis, and no history means no estimate, never a guessed figure. A check that departs from its own history is flagged in the sealed packet, and a flag never blocks, approves or changes any check, scope or approval. The record lives in the Git common directory, is configured by the `timing_record` policy key and is committed only by an explicit export. See [the timing record](CHECKPOINT-TOOL.md#timing-record) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

### G018 tool-rendered review extension (2026-10-07)

`present` returns a review that the tool renders deterministically from the sealed packet, and `present --text` prints it. The layout is pinned by tests and begins with the worktree, branch and parent. The review is a view, is not sealed and never alters the digest. The agent shows it verbatim and adds only its own `Review focus`, which stays out of the commit message. See [the sealed review](CHECKPOINT-TOOL.md#sealed-review) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

### G018 review before the seal (2026-10-08)

The checkpoint workflow separates the preview, which stages nothing, from the sealed review. A preview is required by default when a manifest has any governance, tooling or runtime path and skipped for record-only manifests; the lead developer may waive it for any class, request one for a record, or waive it for one mission in an order, in the plain words "no preview" or "skip preview" (case-insensitive), never in a reply to a question; a bare go does not waive it. The standalone uppercase token that did this until 2026-10-18 (first `SP`, renamed `NP` on 2026-10-13 because `SP` could also mean show preview) is retired by [G041](#g041---agent-entry-and-role-files-2026-10-18-accepted). The Coordinator may relay a waiver in the brief, quoting the lead developer's words, and the worker accepts one from the lead developer in its own session at any time before it presents the preview; after the preview is shown only an approval word is a go. Waiving the preview waives neither the estimate, the tool-rendered sealed review nor the lead developer's Approve or Reject, which stay bound to the exact sealed transaction and its evidence under this decision. A conditional approval given before the seal is not part of this decision. See [the workflow](CHECKPOINT-WORKFLOW.md#review-before-the-seal) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

### G018 approval words extension (2026-10-10)

The lead developer's plain words count as approvals, matched by the tool and never interpreted by the agent. The checkpoint tool takes the whole raw reply, uppercases it, removes all whitespace and punctuation and compares the result with exactly `GO`, `APPROVE`, `APPROVED`, `PROCEED` and `DOIT`. Anything else is not a match, a reply that contains a question mark never matches, and `REJECT` stays the reject token. What a match means depends on what is presented, not on the word: at a preview it means stage and seal, and at a sealed review it means Approve. The word list lives in one module with one matching function, and tests pin accepted and refused examples.

This extends decision-channel equivalence by widening the one exact response table that applies on every declared channel with these approving words. It therefore partially supersedes that decision's statements that other casing, punctuation and wording are invalid on every channel, for these words only, and the earlier statement that "Approved." neither approves nor rejects; their text is retained as history. Everything else stands: the decision is bound to the exact sealed transaction and complete prepared digest, the declared channel stays required provenance, Reject never authorizes, receipts keep their kind, and every previously valid receipt stays valid. Provenance is unchanged: the reply must be typed or selected by the lead developer in the worker's own session and refer to the currently presented exact seal; a quotation, a cross-session message, a tool result, worker prose or the Coordinator's relay never counts, and the Coordinator never approves. The Approve control stays canonical. The set of words was later changed by [G040](#g040---approval-words-2026-10-16-accepted). This decides only which reply words count. A preview go does not approve a commit, and what an approval binds to is not decided here. See [the workflow](CHECKPOINT-WORKFLOW.md#approval-words), [the tool](CHECKPOINT-TOOL.md#approval-words) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

This transaction lands through the previously authoritative path: only the Approve control or the exact token `APPROVE` approves it. It cannot authorize itself with its new semantics.

### G018 early conditional approval extension (2026-10-10)

An approval binds one of two things. At a sealed review it binds the exact sealed transaction, as before: repository, parent, staged tree, manifest, exact message, validation evidence and complete prepared digest. At an eligible preview, the lead developer's go binds the exact candidate that preview names: parent, tree, manifest, message bytes and the derived check list. The go approves that candidate when four things hold: the manifest is eligible, the sealed result reproduces every previewed fact, every check passes and the feature switch reads on. The lead developer does not see the evidence before approving; they approve the rule that every derived check must pass, which the worker cannot reduce.

A manifest is eligible when no path is approval-critical in the artifact classification table (the G026 approval-critical column extension), none is on the runtime boundary and every path has a row; an unreadable table, an unknown value or a path with no row is not eligible, and a mixed manifest takes the strictest rule. Any difference in parent, tree, manifest, message or check list, any failed check, a switch that reads off, a reply that is not an approval word and an exhausted go return to the sealed review and its Approve, which stay the default. The go is single-use and binds the facts of its preview; it has no clock. A re-prepare that reproduces the same candidate keeps it, up to three prepare attempts, and a moved parent or any changed fact does not. The lead developer gets a landing notice after every integration, whichever approval carried it; the notice is not behind the switch.

The switch is `governance/config/checkpoint-features.toml`, a committed TOML file with one boolean key per feature named like its Job, and a comment above each key saying what it does and how to turn it off. It ships on. Only the boolean `true` is on; a missing key or file, any other value, an invalid file or a duplicate key means off. The tool reads it from main's current tip at the preview, at the go, when sealing, before the commit and before integration. Turning it off is the lead developer's manual commit and the safe direction; turning it back on takes the sealed Approve, because the file is approval-critical. If it reads off after the commit exists, nothing lands under the early approval and the seal is redone, and the worker asks the lead developer whether they want a preview or the seal directly. The key `diff_bound_approval` of a later decision slots into the same file.

The preview keeps its content and adds the short parent and tree ids beside the workspace folder, says the lead developer can read the change in IntelliJ or another IDE, and carries one line about what a go approves. The sealed review's decision line names the accepted words in lowercase bold. Provenance is unchanged: the go must be typed or selected by the lead developer in the worker's own session and refer to the preview presented; the receipt authenticates integrity and exact binding, never who typed it. This extends the approval words extension and settles what it left open about what an approval binds. It supersedes, for eligible manifests only, the statement of G018 review before the seal that a conditional approval before the seal is not part of that decision; their text is retained as history. It applies to every new transaction and is not retroactive. See [the workflow](CHECKPOINT-WORKFLOW.md#early-conditional-approval), [the tool](CHECKPOINT-TOOL.md#early-conditional-approval) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

This transaction touches approval-critical paths, so it lands through the previously authoritative path: the normal preview and the sealed Approve. It cannot authorize itself with its new semantics.

Later context (2026-10-14): the boolean key `early_conditional_approval` became the string key `early_approval_reach` with the values `off`, `low` and `medium`, and the G026 column `Approval-critical` (`yes` or a hyphen) became `Approval-sensitivity` (a hyphen for low, `medium` for the former `yes` and `high` for the approval machinery, which never carries a go), with no change of behavior at the committed reach `low`; the text above is kept as it was written. See [the tool](CHECKPOINT-TOOL.md#feature-switches) and the [rationale](RATIONALE.md#change-classification-and-validation-scope-g026).

### G018 diff-bound approval extension (2026-10-14)

The lead developer's go or Approve binds to the diff they saw, so any mechanical re-derivation that yields the same diff, with every check passing, keeps it. Three things follow, and the first two are in force with this transaction.

First, the early conditional approval extends from low paths to ordinary approval-critical ones. The committed reach `early_approval_reach` becomes `medium`, so a go at an eligible preview also approves a manifest of `medium` paths under the same gates: the sealed result reproduces the preview, every check passes, the reach does not read off, and the lead developer's kill switch stays. The approval machinery keeps the sealed Approve whatever the reach says: the paths marked `high` in the [artifact classification table](ARTIFACT-CLASSIFICATION.md#approval-sensitive-paths), an explicit short list that the tool reads from the table and never guesses. The lead developer decided that the early go also reaches manifests on the runtime continuity boundary, under the same gates and the kill switch, with the continuity records commit keeping its own sealed Approve; the code lifted its refusal of such a manifest the same day (2026-10-14), and the Boundary column takes the same higher-of rule as the sensitivity.

Second, a path counts as the higher of its row in the table at HEAD and its row in the candidate's own table, so no path is judged by a table its own transaction wrote. A modified path takes the higher of the two rows, a deleted path its HEAD row, a new path the higher of its enclosing row at HEAD and the candidate's row, and a path with no usable row at HEAD, a `blocked` profile or an unreadable HEAD table counts as `high`. This also corrects the earlier reading in which every deleted path counted as `high`. The sealed packet records both levels and the effective one.

Third, the design of the carry is recorded, not implemented: an approval already given survives a moved base when `git merge-tree` is clean, the carried diff equals the approved diff by `git patch-id --stable` and by bytes with message and trailers unchanged, the selection re-derived on the new main equals the sealed one and every selected check runs again, with a notice and an authenticated audit. It applies to every class, runtime included, under a boolean `diff_bound_approval` that ships `true` with its code. A runtime commit and its continuity records stay two transactions in one worktree, carried in order with an id map. Repeated carries are verified against the originally approved diff. Slice 1 carries committed, approved candidates and slice 2 carries previews and the staging go, each a later transaction. See [diff-bound approval](CHECKPOINT-TOOL.md#diff-bound-approval) and the [rationale](RATIONALE.md#checkpoint-authority-g018).

Slice 1 of the carry is implemented (2026-10-14): `worktree.py carry` carries a finished, committed, approved branch onto a moved main, commit by commit in order with the id map, under the gates above and the key `diff_bound_approval` committed `true`, writing the notice and the authenticated audit into the landing record, while previews and the staging go (slice 2) remain design; see [the carry](CHECKPOINT-TOOL.md#the-carry).

Slice 2 is implemented (2026-10-14): `worktree.py carry-go` re-binds a go given at a preview, or at a staged transaction, to a moved main and moves the worktree there, under the same key and gates (a clean merge, the originally previewed diff and message, equal facts derived on the new main, still eligible), with a notice and an authenticated audit inside the go, and `reconcile` no longer refuses a transaction that adds a folder; see [the go carry](CHECKPOINT-TOOL.md#the-go-carry).

This transaction edits approval machinery of `high` sensitivity, so it lands through the previously authoritative path: the normal preview and the sealed Approve. It cannot authorize itself with its new reach. The slice 1 and slice 2 transactions edit `high` files as well and land the same way.

## G019 - Authoritative artifact first (2026-10-02, Accepted)

Adopt [Authoritative artifact first](CONSTRAINTS.md#authoritative-artifact-first): inspect the current authoritative repository source before concrete proposals to change an existing governed artifact or contract. Memory and secondary records cannot establish its current surface. Delegated workers inspect and identify the source themselves; unavailable sources limit discussion to conceptual work or explicitly unverified claims/proposals. This prevents stale summaries from driving source-level redesign while preserving existing ownership, frozen-artifact precedence and G018 approval boundaries. AGENTS directs workers to the active rule; no new governance mechanism or contract change is introduced.

## G023 - Validation scope (2026-10-03, Accepted)

Validation scope must match change scope. Derive checkpoint checks from reviewed path classifications of the sealed manifest, combine affected checks for mixed scope, and fail closed for unclassified or unsupported paths. Record-only changes require lightweight documentation/continuity and integrity checks; governance and component changes require their relevant tests. Do not run full suites merely because a transaction exists. Preserve G018 exact approval and continuity. See [the validation rule](CONSTRAINTS.md#validation-scope).

## G024 - Python interpreter minimum (2026-10-03, Accepted)

Repository-owned Python tooling requires Python 3.13 or later, permitting compatible newer interpreters without an exact-version or installation-provenance pin. Query the environment's existing `python` first and use it when it meets the minimum and required capabilities; only a missing or too-old interpreter permits broader platform discovery. Internal/bundled runtime lookup and portable interpreter downloads remain fallbacks. Verify version and required capabilities explicitly. See the [interpreter policy](CONSTRAINTS.md#python-interpreter-policy) for invocation and scope, and the [non-normative rationale](RATIONALE.md#python-interpreter-minimum-g024).

### G024 bounded runtime admission (2026-10-05)

The canonical governance admission shim and one explicit repository-local runtime registration, shared by worktrees, supersede the earlier per-worker discovery order. The shim alone may start under older Python 3; governed commands require the admitted 3.13+ runtime. Initial provisioning/registration is an explicit operator action. Ordinary admission fails without searching or downloading when the registered runtime is unavailable or changed; preserve the minimum and the capability checks. See the [admission procedure](CHECKPOINT-TOOL.md#runtime-guard). **Superseded by [G043](#g043---the-runtime-guard-replaces-the-admission-shim-2026-10-18-accepted) (2026-10-18):** the shim, the registration and the operator step are gone; the Python 3.13 minimum and the rule that nothing searches for or downloads an interpreter stand, now in the runtime guard.

### G024 inherited Git environment (2026-10-07)

The canonical launcher scrubs the inherited Git environment instead of rejecting it. It removes every `GIT_*` variable except exactly `GIT_PAGER=cat` before its own Git calls, the runtime probe and the dispatched governed command, and reports the removed names, never their values, on standard error and as `scrubbed` in `--check`. A host-injected variable such as `GIT_EDITOR=true` therefore no longer stops a governed command, and no variable that could redirect the repository, index or configuration reaches Git. Tools started directly without the launcher keep their strict rejection of unreviewed `GIT_*` overrides as defense in depth, and the reviewed trust grants for the exact `safe.directory` pair apply there unchanged. This preserves G018 sealed configuration binding, G024 admission and G025 guards. See the [admission procedure](CHECKPOINT-TOOL.md#runtime-guard) and the [rationale](RATIONALE.md#python-interpreter-minimum-g024). **Continues in [G043](#g043---the-runtime-guard-replaces-the-admission-shim-2026-10-18-accepted):** the runtime guard removes the same variables and names them; only the launcher that did it is replaced.

## G025 - Transaction-owned Git worktrees (2026-10-03, Accepted)

Use a temporary Git worktree and unique branch per active transaction/mission; main is integration territory while concurrent work is active. Preserve isolated dirty state/indexes, explicit ownership, G018 approval and continuity; integrate reviewed exact commits by guarded fast-forward, reconcile divergence as new governed work, and remove only the owned completed worktree. Preserve shared stash/refs and inspect semantic compatibility independently of Git. See the [workflow](WORKTREE-WORKFLOW.md) and [non-normative rationale](RATIONALE.md#transaction-owned-worktrees-g025).

### G025 same-tree transient ref-name extension (2026-10-08)

### G026 artifact-classification extension (2026-10-07)

The lead developer's October 7, 2026 design review settles how classification and validation scope are authored and enforced. This is accepted scope: it records the design, and implementation proceeds in separate transactions that each need their own G018 approval.

Classification MUST have exactly one authored source: a strictly formatted, ASCII-only Markdown table in `governance/ARTIFACT-CLASSIFICATION.md`, parsed directly by the checkpoint and continuity tools, with no generated copy. It replaces the hand-maintained path lists now spread across `scope_rules`, `frozen_paths`, `runtime_paths` and `governance_paths` in `checkpoint-policy.json`, the path rules of `impact` and `commit_metadata` in `checkpoint-profiles.json` and the `RUNTIME` list in `validate_continuity.py`. Check commands, profile definitions, invariant definitions and the symbol map remain JSON configuration. The columns are Path, Class, Profile, Boundary, Bound, Invariants, Subclass and Reachable. Boundary is `runtime` (the runtime-continuity boundary) or `frozen`; Bound names files whose bytes are sealed into approvals and replaces `governance_paths`; Reachable means the document must exist and be reachable from `AGENTS.md`, enforced by continuity, and is not required reading. Rows are sorted by ASCII ordinal comparison of Path, enforced by the parser.

The most specific row wins: an exact path, then the longest directory prefix, with a `dir/*.ext` filter ranking as a directory-level row. Directory and filter rows fill every column. A more specific row may leave cells empty: an empty or whitespace-only cell inherits cell by cell from the nearest enclosing complete row, and a filled cell overrides it. A single hyphen means a deliberate no-value and clears an inherited value; Class and Profile are never no-value; a list cell is replaced and never merged; and a child row MUST NOT clear `frozen`. Matching fails closed: a path with no row is blocked, and so are unknown classes or profiles, malformed rows, duplicate paths and an unreadable table. A plain directory row is blocked unless it names the file types it accepts, as `devlog/` blocked with `devlog/*.md` as a record. Specificity lets a non-normative file inside a runtime directory, such as a component README, validate as a record without that component's gates or the runtime-continuity lifecycle.

The effective classification MUST be visible. A read-only command `show-classification <path>...` prints each path's resolved row and where each cell came from, with `--checks` listing the checks a change would select and `-v` printing the matching row and its parent row as written with their table line numbers. Every presented sealed review lists each path's resolved Boundary, Bound, Subclass and Reachable values beside the class, profile and impact it already shows. A small, independent golden file, `governance/config/artifact-classification-golden.json` (ASCII, sorted keys, an optional short `why` ignored by its test), pins the fully resolved classification of critical paths, and a strict test fails on any difference. Reclassifying a critical path therefore needs a governance edit to the table and a tooling edit to the golden file in one transaction.

Editing a table row validates narrowly through a dedicated `classification` impact invariant: continuity plus the classifier tests, without the checkpoint integrity, evidence or reconcile suites or any component gate. Only a change to the parser or loader code is tooling and takes the selector and integrity suites. This restates the standing principle of this decision: run the checks that verify the modified system and no more, and test the affected systems when a change crosses systems.

A permanent but narrow reviewed mechanism lets documents named in the policy have links retargeted with continuity only. Its `link_retarget` configuration lives in the JSON policy, not in the table, and lists `documents` and `moves` in repository-root-relative terms. The tool resolves each Markdown link against its document's folder and computes the expected file-relative target, keeping fragments; any other change, a partial retarget, an unmapped target or an unparsed link form fails closed to the document's normal envelope. When no cleanup is pending the lists are empty and the mechanism is dormant. A qualifying document is sealed as record with the record-only profile even when the artifact classification table blocks it or gives it a runtime-class profile; frozen and runtime-boundary documents cannot be listed. Each runtime profile declares the `runtime_checks` it owns, there is no shared default, and a runtime path whose profile declares none is refused; this is already in force.

The tools switched to the table at policy version 4, and the path lists above no longer exist. A Subclass is a label and never a lever: it selects no check, and a transaction's `Subclass:` trailer MUST equal the labels the table gives its manifest paths. The table has a second, Historical paths section (Path, Class, Subclass) for deleted files, which only reconstructs the class and subclass of old commits and is never consulted when preparing. Continuity requires each live file row to name an existing file and each historical path to be absent, so a deletion moves its row in the same transaction. Versions 1 to 3 of the policy were removed on 2026-10-07 with the other legacy fallbacks; only version 4 is read.

## G043 - The runtime guard replaces the admission shim (2026-10-18, Accepted)

Every governed command starts with one small standard-library module, the [runtime guard](CHECKPOINT-TOOL.md#runtime-guard) (`governance/tools/runtime_guard.py`), which each thin launcher and the checkpoint facade call first. This supersedes the admission part of G024: the admission shim (`governance_python.py` and its implementation), the machine-local runtime registration in the shared Git directory, the operator step that created it, the shim's capability probe and its 180-second wait for a lifecycle operation. G024 stands for the minimum (Python 3.13 or later, no exact version or vendor pin) and for the rule that nothing searches for or downloads an interpreter; the removal of inherited `GIT_*` variables (G024 inherited Git environment) is kept and moved into the guard.

The guard is written in syntax that any Python 3 can parse, so that an interpreter older than 3.13 stops with one clear message instead of a syntax error. It never discovers or downloads an interpreter; `python` in the documents means any Python 3.13 or later, and a specific interpreter is run by its path. It sets no-bytecode, removes every inherited `GIT_*` variable except exactly `GIT_PAGER=cat` and names the removed ones (names only, never values) on standard error, and enforces the lifecycle gate. Every command and, for `local_jobs`, `worktree` and `timing_record`, every subcommand is registered in one registry with a mode. `READ` writes nothing and passes. `LOCAL` writes only machine-local scratch, or a file the caller names explicitly, and decides nothing from Git state, and passes. `GATED` writes shared state, or decides on Git state and then writes, and is refused at once, without waiting, while a worktree lifecycle operation holds the lifecycle lock. A command or subcommand that is not registered is `GATED`. The old exemption of `execution-status` is one `READ` entry. The core registry names no extension (G042): an extension script states its own mode when it enters the guard.

Drift is caught per transaction. The guard fingerprints the running interpreter (resolved executable path, size, SHA-256 of the file, version). The first step of a transaction records the fingerprint, in the preview record or, when there is no preview, in the checkpoint packet under its authentication; the landing record keeps it after `finish`. Every later step compares it at its start and refuses with `the interpreter changed since the preview: re-run the preview, nothing was lost yet`: the go, the prepare, the seal, the decision, the commit, the verification, the finish, the reconciliation, the integration, the carry of an approval and the carry of a go. The hash is the strict signal, so a patch-version upgrade is a change. A tool run outside a transaction needs only the version check. A record made before the pin existed carries none and is not compared.

The documents show one command form, `python -B governance/tools/<tool>.py`, and a conformance test fails when any Markdown command line uses the retired form or another spelling. See [the runtime guard](CHECKPOINT-TOOL.md#runtime-guard), [the interpreter policy](CONSTRAINTS.md#python-interpreter-policy) and the [rationale](RATIONALE.md#the-runtime-guard-g043).

## G044 - Shared machine-local state lives in .local of the primary checkout (2026-10-18, Accepted)

**The rule: the Git directory holds only what dies with its worktree; everything else that is machine-local lives in `.local/`.** State that every worktree of a repository shares, and that outlives any one worktree, lives in the git-ignored `.local/` folder of the **primary checkout**, which is the parent of Git's common directory and is found the same way from the main checkout, from any linked worktree and from a clone (a clone has a primary checkout of its own, so its own `.local/`). A repository without a primary checkout (a bare repository, or a common directory that is not named `.git`, as with a submodule or a separate Git directory) has no such place: the tools refuse with a clear message and never guess.

The shared locations are `.local/timings/checkpoint-timings.jsonl`, the advisory timing record, and `.local/locks/worktree-workflow.lock`, the lifecycle lock that spans every worktree. They sit beside `.local/claims/` and `.local/coordination/`, which already followed the rule. The runtime registration of the old admission shim no longer exists (G043), so there is no `.local/runtime/` folder and nothing to move for it. **One module, `governance/tools/support/local_state.py`, spells these locations**; the runtime guard, which must run under an older Python 3 before any repository module is trusted, keeps a small copy of the lifecycle lock's location and a test asserts that the copy agrees with the module. The per-checkout checkpoint scratch (`tmp/checkpoint/`, with the receipt key, the packets and `operation.lock`) is not part of this decision: it moves in a later step with its own decision, and nothing about its location, its key or its packets changes here. Later context: G046 moved it to the `governance/` folder of the checkout's Git directory, so the operation lock named below now lives there.

The tools create `.local/timings/` and `.local/locks/` on demand, and **refuse to write there while `.local/` is not git-ignored**, so shared state can never be committed or make a checkout dirty. The lifecycle lock stays **exclusive**: it is created with an atomic exclusive create, and a missing folder or file means no lock. There is no migration code, because the template has no adopters: a timing record kept in the Git directory by an earlier version can be copied by hand to the new place, and `export` and `import` keep working.

**Removing a stuck lock.** A lock file carries no owner, so its presence proves nothing. The lifecycle lock and the checkpoint `tmp/checkpoint/operation.lock` are removed **only with the lead developer's word, after establishing that no process owns them** (the running processes and their command lines; a container runtime is not a checkpoint process). The coordination writer lock, the helper's short exclusive lock on Job records, may be removed by the Coordinator after confirming that its writer stopped, and the Coordinator tells the lead developer afterwards. This is the rule in force until the tools can prove a lock stale on their own, which a later decision will take up; it makes the previously disagreeing texts of the hazards, the checkpoint tool notes, the Coordinator role and local coordination say the same, and changes no other rule. `git clean -x` deletes `.local/` and is recorded as a hazard. See [the worktree workflow](WORKTREE-WORKFLOW.md#ownership-and-shared-state), [the timing record](CHECKPOINT-TOOL.md#timing-record), [the runtime guard](CHECKPOINT-TOOL.md#runtime-guard), [worker hazards](WORKER-HAZARDS.md#h3-stale-lock-files) and the [rationale](RATIONALE.md#shared-machine-local-state-g044).

## G046 - The checkpoint store lives in the worktree's Git directory (2026-10-18, Accepted)

**The per-checkout checkpoint store moves from `<checkout>/tmp/checkpoint/` to the `governance/` folder of the checkout's own Git directory.** For the primary checkout that is `<primary>/.git/governance/`; for a linked worktree it is `<primary>/.git/worktrees/<name>/governance/` (the folder `git rev-parse --absolute-git-dir` names, plus `governance`). This completes the rule of G044: the Git directory holds only what dies with its worktree, and everything else lives in `.local/`. The store dies with its worktree, so it goes in the worktree's Git directory.

The store is the whole of what a checkout keeps for its transaction: `receipt.key` (32 random bytes, mode 0600), `transaction.json` (the sealed packet, authenticated with the key), `pending.json`, `handoff.json`, `cleanup.json`, `landing.json` (the carry's authenticated landing audit), `early-approval.json` (the signed record of go attempts, unchanged in meaning), `operation.lock` and the `stale-<hash>.json` files. Nothing about what a file contains, how a packet is authenticated or what an approval binds changes; only the place does. **One module names the place:** `governance/tools/support/local_state.py` (`store_folder`, `checkout_store`); the repository anchors keep only the file names, and the old `SCRATCH` constant is gone. The name `governance` collides with nothing Git keeps in a Git directory or the tools read there (`HEAD`, `index`, `config`, `hooks`, `info`, `logs`, `objects`, `refs`, `worktrees`, `locked`, `gitdir`, `commondir`, and the markers `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply` and `index.lock` that `quiet_operation` reads).

**What follows from the place.** Git deletes the worktree's Git directory when the worktree is removed or pruned, so the store, the landing record and the go-attempt record go with the worktree without any code of ours; `git clean -x` cannot reach it, because it is outside the working tree; editors and searches do not index it; the check that the store is ignored and untracked has no meaning any more and is gone, and a store that is a link or a junction is still refused. The guarded removal accepts the store at its new place (the key, the lock, the landing record and the spent go-attempt record beside an otherwise idle store), the idle checks of main and of a mission read the new place, and the execution status and the carry's note read the stores of the other worktrees from the `.git` entry of each, without running Git. **The key is never made again silently:** it is made at the first use of an empty store; a store that holds records but no key stops the tool with one message that names the store and says the key was deleted or the store was damaged, and asking for a missing key stops with its own message. The key is created with mode 0600 and is never printed, logged or copied into a packet. Backups of `.local/` need no exclusion for the store, because it is not there. The `tmp/` ignore rule stays for other uses, and the continuity check still refuses evidence paths under `tmp/`.

There is no migration code, because the template has no adopters: a transaction in flight under the old place when the tools are upgraded is finished or abandoned first, and a leftover `tmp/checkpoint/` folder can be deleted by hand. See [the tool notes](CHECKPOINT-TOOL.md#state-and-evidence), [the worktree workflow](WORKTREE-WORKFLOW.md#ownership-and-shared-state), [worker hazards](WORKER-HAZARDS.md#h22-git-clean--x-deletes-local) and the [rationale](RATIONALE.md#the-checkpoint-store-in-the-worktrees-git-directory-g046).

## G056 - A project may declare which checks its paths select (2026-10-23, Accepted)
