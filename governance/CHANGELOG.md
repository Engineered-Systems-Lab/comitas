# Changelog

This changelog is curated, not generated. An entry says what someone who has adopted Comitas must do or know; if it could be produced from `git log`, it does not belong here, and an entry points to a decision or a document instead of copying text. The version is in [VERSION](VERSION). A release that needs action from adopters gets a Migration note under it, written when that first change is made. A release heading carries the date the release was made, written `## <version> (YYYY-MM-DD)`.

## 0.3.1 (2026-10-23)

**Documentation and one message; nothing to do but take the upgrade.** GitHub's "Use this template" is enabled on the Comitas repository, and a repository it generates needs no adoption helper: its shell scripts already carry the executable bit and `project-governance/config/citations.json` already declares the label `template`. The README and the [project lifecycle](PROJECT-LIFECYCLE.md#1-adopt) now describe both routes, the template and the manual export, and the adoption helper's refusal after the first commit says that a repository made with "Use this template" needs no adoption step. The helper's behaviour is unchanged.

## 0.3.0 (2026-10-23)

**The framework is named Comitas; nothing to do but take the upgrade.** Comitas is Latin for courtesy and friendliness, the spirit in which people and AI agents work together here. Only names changed: the README title, subtitle and tagline, the identity line of Mission Control, the `NOTICE`, and the documents and messages that called the framework "the template" or "the governance template" now say Comitas. No folder, file name, configuration key or tool name changed, and an upgrade stays "replace everything under `governance/`". The citation label `template` stays, with every `template commit` citation: it now names the private archive that holds the framework's history before Comitas, a project made from Comitas declares it with the adoption helper as before, and the helper still writes that label.

## 0.2.4 (2026-10-22)

**Two defects fixed that blocked a project from adopting the recovery chain; nothing to do but take the upgrade.** The checkpoint tool's preparation gate required the `implementation_checkpoint` row to be committed already whenever the project's classification table has runtime rows, so it refused the very change that adds that row ([Adopting the recovery chain](COMMAND-CONTINUITY.md#adopting-the-recovery-chain)); in a project whose runtime rows were already committed it refused every prepare. The gate now accepts that one change: HEAD's progress record holds no such row, the change touches no runtime path, and it adds the progress row naming the latest runtime commit, the fact in the project's reconstruction contract and, when the project keeps a devlog, the entry that carries the pointer. A project that already has the row keeps the unchanged rule, and anything short of the full adopting change is refused with a message that names what is missing. And the scratch copy of `test_extension_removal.py` was a new repository with one commit, where a commit cited by a devlog entry or by the checkpoint does not exist, so with one such entry both removal tests failed with `Git evidence unavailable`; the copy's commit now sits on the checkout's HEAD, whose objects it reaches through an alternate object store, so cited commits resolve and the checkpoint stays an ancestor of HEAD. A project that got past the first defect by hand keeps its commit.

## 0.2.3 (2026-10-22)

**One defect fixed; nothing to do but take the upgrade.** The 0.2.2 regression test in `test_artifact_classification.py` (`SealedClassificationTest.test_disagreement_is_refused_in_a_root_with_a_project_profile_and_a_row_naming_it`) replaced the project's real checkpoint profiles file with a synthetic one in its temporary root, so in a project whose table names a profile of its own it failed with `unknown profile`, and so did the two extension-removal tests that rerun that file. The temporary root now keeps every profile the copied table names: the fixture profile is merged into the project's own profiles file, under a name that file does not use. The test also no longer depends on one template row when it adds its project row, and a third test runs the same path in a root whose project table already names a profile of its own.

## 0.2.2 (2026-10-22)

**One defect fixed; nothing to do but take the upgrade.** The 0.2.1 fix for project profiles left one conformance test failing in a project that has its own profiles: `SealedClassificationTest.test_disagreement_with_the_policy_refuses_preparation` copied the project's checkpoint profiles into its temporary root but not the framework's, and failed with `Checkpoint profiles are missing`. It now copies both, and a second test runs the same path with a project profile and a project row that names it, so the template's own suite covers what only an adopting project exercised.

## 0.2.1 (2026-10-22)

**Two defects fixed; nothing to do but take the upgrade.** The conformance classification tests (`test_artifact_classification.py`) read only the framework's checkpoint profiles, so a project table row that names a profile the project added in `project-governance/config/checkpoint-profiles.json` failed them; they now read the framework's profiles plus the project's, as the tools do ([G045](DECISIONS.md#g045---the-project-overlay-is-read-by-every-tool-and-the-settings-override-code-defaults-2026-10-18-accepted)). And `checkpoint.py prepare` and `preview` staged a new `*.sh` file with a plain `git add`, which on Windows (`core.filemode` false) seals it at mode 100644 and fails `test_script_modes`; they now stage the manifest's `*.sh` files as executable, so the sealed and previewed trees carry 100755 ([H19](WORKER-HAZARDS.md#h19-a-scripts-mode-lives-in-the-index-not-in-the-working-tree)). The rule that a committed `*.sh` is 100755 is written once, in `artifact_classification.is_script`, and the tool, the adoption helper and the test share it.

## 0.2.0 (2026-10-21)

**Frozen files are checked against a checksum manifest, not against the last runtime commit.** The continuity check used to take the runtime implementation checkpoint as the baseline of every frozen file, so a runtime commit that added and froze a path failed `Implementation checkpoint changed frozen artifacts`, and a path changed after the checkpoint and then frozen failed `Frozen index differs from checkpoint`. Now `project-governance/config/frozen-manifest.json` records the SHA-256 of each frozen file (CRLF read as LF), the check compares the working tree and the index with it, and it reads no history. Freezing is always allowed and takes the content as it is; only changing or removing an entry is restricted, by `--refreeze <path>` and the sealed Approve of the manifest change. The checkpoint must still be the latest runtime commit. See [G054](DECISIONS.md#g054---freezing-is-always-allowed-and-only-changing-a-freeze-is-restricted-2026-10-21-accepted) and [the frozen manifest](PROJECT-GOVERNANCE.md#the-frozen-manifest).

Migration. A project with `frozen` rows in its classification table writes its manifest once after taking this version: run `python -B governance/tools/validate_continuity.py --freeze`, then stage and commit `project-governance/config/frozen-manifest.json` together with the frozen files, as one reviewed change (the manifest is graded high, so it takes the sealed Approve). Until then the continuity check fails with `Frozen file inventory changed: no manifest entry for ...`. A project with no frozen row changes nothing.

## 0.1.0 (2026-10-20)

First release. The template's first commit was made on 2026-10-16 (UTC); it builds on governance work done since 2026-09-30 in an earlier private project of the licensor.

The first release: the governance framework, ready to adopt. Nobody had adopted the template before it, so it has no Migration notes; they start with the first release after someone adopts it.

**The two sides.** `governance/` is the framework and an upgrade replaces it wholesale; `project-governance/` is the project's and an upgrade never touches it. The tools read both and take the union of the classification tables, the profiles, the policy and the reconstruction contract, refusing a clash instead of choosing; the feature switches, the devlog settings and the Mission Control port are one project file each, and the defaults are in the code. The project also keeps its own rules, decisions (prefix D) and rationale there, each optional. [Project governance files](PROJECT-GOVERNANCE.md) lists every file with its keys, its defaults and what the tools refuse, and a conformance test pins its defaults to the code. See [G045](DECISIONS.md#g045---the-project-overlay-is-read-by-every-tool-and-the-settings-override-code-defaults-2026-10-18-accepted), [G049](DECISIONS.md#g049---the-framework-numbers-its-decisions-with-g-and-a-project-numbers-its-own-with-d-2026-10-19-accepted) and [G050](DECISIONS.md#g050---the-project-keeps-its-own-rules-decisions-and-half-of-the-reconstruction-contract-2026-10-19-accepted). The template ships a starter of each project file, with the devlog opt-out (`"enabled": false`) for a project that keeps none.

**What the framework contains.**

- The rules, workflow and decision registry (prefix G) and the rationale, with a conformance test that fails when a framework document cites a commit id that does not resolve in the repository, and one that fails when a D-prefixed framework decision reference appears under `governance/`.
- A commit of another repository is cited as `<label> commit` and the id in backticks. A project declares the labels in `project-governance/config/citations.json`; the template declares none. The framework cites its own commits as `template commit`, which the conformance test requires, so a project that copies the framework declares `template` and its copy stays valid ([G051](DECISIONS.md#g051---the-commit-of-another-repository-is-cited-by-a-declared-label-2026-10-20-accepted), [the setting](PROJECT-GOVERNANCE.md#citationsjson)).
- The agent entry: `AGENT-ORIENTATION.md` is the file every agent reads first, with `ROLE-COORDINATOR.md` and `ROLE-WORKER.md` for the two roles (an agent that is not told its role is a worker). `AGENTS.md` is the project's own thin file that points to it, pinned by a conformance test. The preview is waived with the plain words "no preview" or "skip preview" in an order. See [G041](DECISIONS.md#g041---agent-entry-and-role-files-2026-10-18-accepted).
- The tools in `tools/` (checkpoint, worktree guard, claims, local jobs, continuity check, test runner, runtime guard) with their tests in `tests/`, the scripts that start them in `scripts/`, and a conformance test that pins the mode of every committed shell script.
- The framework's configuration in `config/`: policy, profiles, the classification golden pin and the framework part of the reconstruction contract, with the conformance tests that pin them.
- The checkpoint workflow: a worker asks for a go, and later for an Approve, alone, never with another question ([G047](DECISIONS.md#g047---the-go-and-the-approve-are-asked-alone-2026-10-18-accepted), [the workflow](CHECKPOINT-WORKFLOW.md#the-go-and-the-approve-are-asked-alone)); the final trailer block of a checkpoint holds only `Class:`, `Subclass:` and `Worker:`, and `checkpoint.py preview` and `prepare` refuse any other key, `Co-Authored-By:` included, because `Worker:` already names the agent for every vendor ([the commit-message convention](CHECKPOINT-WORKFLOW.md#commit-message-convention)).
- Any change to a path under `governance/` or `project-governance/` also runs the whole conformance folder, `config/conformance/`, with the continuity tests (`tests/continuity/`): the `continuity-regressions` check discovers every `test_*.py` of both, so a conformance test that pins rule text can no longer be broken by a change that never selected it. It adds about two minutes to a governance mission. A path outside both folders selects it only when its table row names the `conformance` invariant ([the impact selection](CHECKPOINT-WORKFLOW.md#impact-selection-beneath-profiles)).
- Transaction worktrees with guarded integration. A worker removes its own superseded mission with `worktree.py remove --superseded-by <landed full commit>`, which refuses unless the replacement is on main, its landing is recorded under the same Job, the old store holds no live packet and the owner matches ([G048](DECISIONS.md#g048---the-owner-removes-its-superseded-mission-2026-10-19-accepted), [the worktree workflow](WORKTREE-WORKFLOW.md#a-superseded-mission)). `worktree.py remove` also deletes the mission's own review folder (`_review/<mission-id>/`) after the worktree and the branch, and refuses before removing anything when that folder holds a subfolder, a link or a junction ([the G025 review folder lifecycle extension](DECISIONS.md#g025-review-folder-lifecycle-extension-2026-10-18)).
- The runtime guard. Every governed command starts with `tools/runtime_guard.py` and is written `python -B governance/tools/<tool>.py`, with no registration and no operator step. The guard stops under a Python older than 3.13, removes inherited `GIT_*` variables, refuses at once a command that writes shared state while a worktree lifecycle operation runs, and pins a transaction to the interpreter it began on ([G043](DECISIONS.md#g043---the-runtime-guard-replaces-the-admission-shim-2026-10-18-accepted), [the runtime guard](CHECKPOINT-TOOL.md#runtime-guard)).
- Machine-local state that every worktree shares lives in the git-ignored `.local/` folder of the primary checkout (the timing record and the lifecycle lock), named by `tools/support/local_state.py`; the tools create the folders on demand and refuse to write there when `.local/` is not ignored, so a project's `.gitignore` ignores `/.local/` (hazard H22: `git clean -x` deletes it). The per-checkout checkpoint store lives in the `governance/` folder of the checkout's own Git directory and dies with its worktree ([G044](DECISIONS.md#g044---shared-machine-local-state-lives-in-local-of-the-primary-checkout-2026-10-18-accepted), [G046](DECISIONS.md#g046---the-checkpoint-store-lives-in-the-worktrees-git-directory-2026-10-18-accepted), [the worktree workflow](WORKTREE-WORKFLOW.md#ownership-and-shared-state)).
- The test runner keeps its per-run scratch folders in a `tmp` folder next to the main checkout's folder, created when missing and found through Git's common directory ([the test runner](CHECKPOINT-TOOL.md#test-runner)).
- Mission Control, the first extension: `extensions/` holds the optional pieces and `tests/extensions/` their tests, and the core never depends on an extension. `python -B governance/extensions/remove_extension.py <name>` removes one, and a conformance test proves the core passes its tests without them ([G042](DECISIONS.md#g042---the-core-never-depends-on-an-extension-2026-10-18-accepted), [the extensions README](extensions/README.md)). Its port is the project setting `config/mission-control.json`, 8765 without the file, bound exclusively with no fallback ([the Mission Control README](extensions/mission_control/README.md)).
- The `devlog/` folder at the project root, empty, with the project's conventions and the index.
- A new project runs the adoption helper once, after `git init -b main` and `git add -A` and before its first commit: `python -B governance/tools/adopt.py` sets the executable bit of the staged shell scripts in the index and declares the label `template` in `project-governance/config/citations.json`, so the project passes the script-mode and cited-commit conformance tests; it refuses where a commit exists. The first Coordinator thread creates the queue record with `python -B governance/tools/local_jobs.py --repo . claim-coordinator --identity '<who you are>'`, and a later thread takes the role over only with `--take-over --reason` ([G053](DECISIONS.md#g053---a-new-project-runs-one-adoption-helper-and-its-first-coordinator-claims-the-role-by-command-2026-10-20-accepted), [the helper](CHECKPOINT-TOOL.md#the-adoption-helper), [the claim](ROLE-COORDINATOR.md#claiming-the-role)). The conformance test of cited commits now reads the labels the repository declares.
- [Project lifecycle](PROJECT-LIFECYCLE.md) is the framework's page for the lead developer: six phases (adopt, set up, run, repair, change, upgrade), the commands a person runs in each and links to the sections that own the details. The steps for adopting a project and for taking an update moved there from the root `README.md`, which keeps a short summary and a link; the root `README.md` is the project's and an upgrade never replaces it, so an adopter's copy of the old steps is not updated, and the page is the one to follow. A conformance test checks that every path the page names exists.
- Licensed under PolyForm Noncommercial 1.0.0. `NOTICE` in this folder carries the Required Notice line and the license's URL, so a copy of `governance/` alone, an upgrade or an extension copied on its own keeps the notice; keep it, and keep the root `LICENSE` with a copy of the whole template. A conformance test keeps the two notice lines equal and the license text canonical. [Contributing](CONTRIBUTING.md) says how a contribution to the framework is disclosed, with a frozen [contribution record](CONTRIBUTION-RECORD.md) of the history and an append-only [contribution register](CONTRIBUTION-REGISTER.md); third-party material enters only with its own license and notice ([G052](DECISIONS.md#g052---notices-travel-with-the-framework-and-contributions-are-recorded-in-files-2026-10-20-accepted), [the rules](CONSTRAINTS.md#licensing-and-provenance)).
