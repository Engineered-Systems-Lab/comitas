# Changelog

This changelog is curated, not generated. An entry says what someone who has adopted Comitas must do or know; if it could be produced from `git log`, it does not belong here, and an entry points to a decision or a document instead of copying text. The version is in [VERSION](VERSION). A release that needs action from adopters gets a Migration note under it, written when that first change is made. A release heading carries the date the release was made, written `## <version> (YYYY-MM-DD)`. Entries collect under `## Unreleased` until the lead developer cuts a release, which dates the heading and sets VERSION.

## Unreleased

**Epics can close automatically or explicitly.** The optional `closure_policy` is `automatic` (also the default for existing records) or `explicit`. Normal completion/pruning still removes the last member and closes automatic Epics. Explicit Epics stay open, including when empty, until the lead developer confirms closure and the Coordinator removes them through the existing guarded update. Either policy permits adding Jobs while the Epic exists, and the Coordinator can change an existing Epic’s policy through the guarded update; an empty Epic changed to automatic closes on the next prune. The queue report and Mission Control show the policy and retained empty Epics; no migration or VERSION change is required. Older helpers reject the new field, so update them before reading records that use it.

**Core docstrings describe optional readers without naming an installed extension; documentation only, no adopter action.** Four docstrings now use neutral wording for readers and extension tests, following [G042](DECISIONS.md#g042---the-core-never-depends-on-an-extension-2026-10-18-accepted) without adding a prose exception. The [dated rationale](RATIONALE.md#the-core-never-depends-on-an-extension-g042) records the alternatives and the removal test's existing marker-only coverage. No executable behavior, removal test or rule changes.

**The citation label `template` names the framework repository by role; documentation only, no adopter action.** [The citation documentation](PROJECT-GOVERNANCE.md#the-template-label) clarifies its meaning for Comitas, its earlier archive and adopting projects. Supporting descriptions refer there, and [dated context for G051](RATIONALE.md#labeled-commit-citations-g051) corrects the archive-only explanation from the 0.3.0 rename while preserving historical records and the rejected refusal of labeled local commits. No rule, test, label or adoption behavior changes.

**The worker brief keeps an extension-neutral reminder to follow presentation rules; nothing to do but take the upgrade.** `local_jobs.py brief` replaces its diff viewer sentence with a reminder to follow any rule in a README under `governance/extensions/` for presenting a preview or a sealed review. Workers still read the [worker role](ROLE-WORKER.md#the-optional-diff-viewer) and follow the existing viewer rule. The extension-removal check now also runs the local Job helper tests, including the brief, after all extensions are removed. This repairs the [G042 discrepancy](RATIONALE.md#the-core-never-depends-on-an-extension-g042) without changing G042 or approval rules.

**The release procedure and the boundary between review aids and approval now have standing decision records; documentation only, no adopter action.** [G057](DECISIONS.md#g057---how-a-release-is-made-2026-10-25-accepted) records Unreleased collection, readiness before immutable public tags and version choices; [G058](DECISIONS.md#g058---review-aids-never-affect-approval-2026-10-25-accepted) records that review aids display the recorded candidate and never affect approval. Their rationale preserves the supplied reasons and alternatives, with later context on G018's unchanged higher-of rule and the verified G042 brief-wording discrepancy. No tool, test, VERSION or approval rule changes.

## 0.4.0 (2026-10-23)

**A `Repository checkpoint:` line that is not exactly one backticked full id of this repository is now refused, as the documentation always said; a devlog entry with a labeled id written without backticks (`Repository checkpoint: lab commit <id>`) was silently ignored and can now fail the continuity check and the Mission Control generator after taking the upgrade.** Both read the line through one function, `checkpoint_line_refusal` in `governance/tools/continuity/artifact_classification.py`, and stop with the one message "A repository checkpoint is a commit of this repository, not a labeled one". Write the line as ``Repository checkpoint: `<full 40-character hash>` ``, or move a labeled or short id to a line of its own, where it counts as a citation. The [Mission Control README](extensions/mission_control/README.md#cli) now says that its example commands take the framework inventory alone, so a reader gets no devlog or project datasets from them; the Refresh path assembles the full inventory.

**`local_jobs.py complete` no longer mistakes another Job's fresh mission for the Job it closes; nothing to do but take the upgrade.** The landing check found the mission to look for from the Job's own claims, windows and landing event or from `--owner`, but also took every `tx/` branch that points at one of the Job's commits, which is where another Job's new mission starts right after a landing; the close then refused with "branch tx/<other> still exists", `--owner` did not help, and the message invited deleting another Job's branch. The mission is now found from `--owner`, the claims database, windows and the landing event; a branch at a given commit counts only when none of them names a mission, and never when its claims, windows or landing event name another Job, name two Jobs or name none; a claims database that exists but cannot be read refuses the close. Claims only widen what the check looks at and never replace one of its steps. The refusals for a branch, worktree or folder of the Job's own mission are unchanged ([Local coordination](LOCAL-COORDINATION.md#updates-handoff-and-disposal)). A project test that expects a branch of another Job at the same commit to block `complete` must change.

**The worker brief says where the scope lives and who the Coordinator is; nothing to do but take the upgrade.** `local_jobs.py brief` no longer prints the placeholder "The Coordinator pastes the Job-specific scope here"; its section is now `SCOPE` and points to the Job record, which holds the scope, riders and any routed handoff, and the record wins over any text outside it ([Local coordination](LOCAL-COORDINATION.md#execution-status) says so after the COORDINATION block). `--extra-file` stays for a short note, printed under the pointer and marked as subordinate to the record. The COORDINATION block's messaging line no longer tells a worker to wait when no session is named "Coordinator": the Coordinator is that session or, where a session started the worker, that session, which receives its end-of-turn report. A project test that asserts the old placeholder or the heading `JOB-SPECIFIC SCOPE` must change; `test_local_jobs.py` carries the new assertions.

**Frozen files are always compared with the manifest; a project with `frozen` rows and no declared fact was unprotected, so it can now fail the continuity check after taking the upgrade.** `validate_continuity.py` used to compare the files under `frozen` rows with `project-governance/config/frozen-manifest.json` only when the reconstruction contract declared the optional fact `frozen_contracts_and_fixtures_unchanged` (which needs `implementation_checkpoint`), so a project that had rows and a manifest without the fact passed with a frozen file changed, in the working tree or in a commit made by hand, although [the frozen manifest](PROJECT-GOVERNANCE.md#the-frozen-manifest) says the check requires them to be equal. The comparison now runs whenever the classification table has a `frozen` row, with or without a runtime boundary and with or without the fact; the fact keeps its place in the contract and still reports the check in the reconstruction. The check never creates or changes the manifest; only `--freeze` and `--refreeze` do, when you run them. A project with frozen rows and no manifest, or with frozen files that differ from it, first reviews that the frozen files are the intended baseline, because `--freeze` records their current content as it is, including any change made while they were unprotected (compare them with the commit or release they were frozen at). Only then does it run `python -B governance/tools/validate_continuity.py --freeze` (or `--refreeze <path>` for a file changed on purpose) and commit the manifest as one reviewed change, which takes the sealed Approve; a project with no `frozen` row changes nothing. The `PASS` line no longer claims checks that did not run: it names `checkpoint/evidence` only for a project with the `implementation_checkpoint` fact and `frozen invariants` only for a project with a frozen row (`PASS: recovery documents, links and logs.` for a project with neither). See [Command continuity](COMMAND-CONTINUITY.md#layer-1-deterministic-verification).

Migration. A project with `frozen` rows whose frozen files differ from `project-governance/config/frozen-manifest.json` (possible until now when the contract declared no frozen fact) fails the continuity check after the upgrade. It either restores the files or, when the change was intended, re-freezes the named paths with `python -B governance/tools/validate_continuity.py --freeze --refreeze <path>` through a governed change.

**A project can narrow checks inside its own profile; nothing to do but take the upgrade, and nothing changes until a project uses the new keys.** `project-governance/config/checkpoint-profiles.json` may now hold `impact.invariants`: new invariant names with the same `groups` and `requires` as a framework invariant, over the framework's commands or the project's own in `checkpoint-policy.json`. A project row of the classification table may name them in its Invariants column. A project profile opts in to narrowing with `narrowable`, a list of its own check ids that the groups of a row's invariants replace for a path; a profile without it runs every check for every path, as before. The tools refuse a project invariant named like a framework one, an unknown group or required invariant, a `narrowable` check the profile does not hold or that is a required check or a runtime gate (runtime gates are never narrowed by an impact invariant), and any other key inside `impact`; a row naming an unknown invariant is refused as before. The explainer `show_classification.py` shows the narrowed list. See [G055](DECISIONS.md#g055---a-project-may-add-impact-invariants-and-name-the-checks-an-impact-mapping-may-replace-2026-10-23-accepted) and [Checkpoint tool](CHECKPOINT-TOOL.md#the-project-overlay).

**A commit that changes a project's own checkpoint files can now carry the Subclass `checkpoint`; nothing to do but take the upgrade, and a commit that touches only these files must now name the Subclass.** The framework's table gave `governance/config/checkpoint-policy.json` and `checkpoint-profiles.json` the Subclass `checkpoint`, but their project counterparts fell to the row for the folder `project-governance/`, which has no Subclass, and a project cannot add rows under that folder, so its commit of an overlay file could carry none. [Artifact classification](ARTIFACT-CLASSIFICATION.md#the-table) now has exact rows for `project-governance/config/checkpoint-policy.json` and `checkpoint-profiles.json` with the Subclass `checkpoint` (same label as the framework's), and gives the same label to `checkpoint-features.toml` and the project's `artifact-classification-golden.json`. Class, profile, invariants and the `high` approval sensitivity are unchanged, and the other files of the folder keep no Subclass. The Subclass trailer must equal the labels of the manifest, so a project commit that touches one of these files now needs `Subclass: checkpoint` and is refused without it. A row under `project-governance/` may name a file the project does not have: the continuity check no longer reports it as a missing file, because these files are optional.

## 0.2.2 (2026-10-22)

**One defect fixed; nothing to do but take the upgrade.** The 0.2.1 fix for project profiles left one conformance test failing in a project that has its own profiles: `SealedClassificationTest.test_disagreement_with_the_policy_refuses_preparation` copied the project's checkpoint profiles into its temporary root but not the framework's, and failed with `Checkpoint profiles are missing`. It now copies both, and a second test runs the same path with a project profile and a project row that names it, so the template's own suite covers what only an adopting project exercised.

## 0.2.1 (2026-10-22)

**Two defects fixed; nothing to do but take the upgrade.** The conformance classification tests (`test_artifact_classification.py`) read only the framework's checkpoint profiles, so a project table row that names a profile the project added in `project-governance/config/checkpoint-profiles.json` failed them; they now read the framework's profiles plus the project's, as the tools do ([G045](DECISIONS.md#g045---the-project-overlay-is-read-by-every-tool-and-the-settings-override-code-defaults-2026-10-18-accepted)). And `checkpoint.py prepare` and `preview` staged a new `*.sh` file with a plain `git add`, which on Windows (`core.filemode` false) seals it at mode 100644 and fails `test_script_modes`; they now stage the manifest's `*.sh` files as executable, so the sealed and previewed trees carry 100755 ([H19](WORKER-HAZARDS.md#h19-a-scripts-mode-lives-in-the-index-not-in-the-working-tree)). The rule that a committed `*.sh` is 100755 is written once, in `artifact_classification.is_script`, and the tool, the adoption helper and the test share it.

## 0.2.0 (2026-10-21)

**Frozen files are checked against a checksum manifest, not against the last runtime commit.** The continuity check used to take the runtime implementation checkpoint as the baseline of every frozen file, so a runtime commit that added and froze a path failed `Implementation checkpoint changed frozen artifacts`, and a path changed after the checkpoint and then frozen failed `Frozen index differs from checkpoint`. Now `project-governance/config/frozen-manifest.json` records the SHA-256 of each frozen file (CRLF read as LF), the check compares the working tree and the index with it, and it reads no history. Freezing is always allowed and takes the content as it is; only changing or removing an entry is restricted, by `--refreeze <path>` and the sealed Approve of the manifest change. The checkpoint must still be the latest runtime commit. See [G054](DECISIONS.md#g054---freezing-is-always-allowed-and-only-changing-a-freeze-is-restricted-2026-10-21-accepted) and [the frozen manifest](PROJECT-GOVERNANCE.md#the-frozen-manifest).

Migration. A project with `frozen` rows in its classification table writes its manifest once after taking this version: run `python -B governance/tools/validate_continuity.py --freeze`, then stage and commit `project-governance/config/frozen-manifest.json` together with the frozen files, as one reviewed change (the manifest is graded high, so it takes the sealed Approve). Until then the continuity check fails with `Frozen file inventory changed: no manifest entry for ...`. A project with no frozen row changes nothing.

## 0.1.0 (2026-10-20)

First release. The template's first commit was made on 2026-10-16 (UTC); it builds on governance work done since 2026-09-30 in an earlier private project of the licensor.

The first release: the governance framework, ready to adopt. Nobody had adopted the template before it, so it has no Migration notes; they start with the first release after someone adopts it.

**The two sides.** `governance/` is the framework and an upgrade replaces it wholesale; `project-governance/` is the project's and an upgrade never touches it. The tools read both and take the union of the classification tables, the profiles, the policy and the reconstruction contract, refusing a clash instead of choosing; the feature switches, the devlog settings and the Mission Control port are one project file each, and the defaults are in the code. The project also keeps its own rules, decisions (prefix D) and rationale there, each optional. [Project governance files](PROJECT-GOVERNANCE.md) lists every file with its keys, its defaults and what the tools refuse, and a conformance test pins its defaults to the code. See [G045](DECISIONS.md#g045---the-project-overlay-is-read-by-every-tool-and-the-settings-override-code-defaults-2026-10-18-accepted), [G049](DECISIONS.md#g049---the-framework-numbers-its-decisions-with-g-and-a-project-numbers-its-own-with-d-2026-10-19-accepted) and [G050](DECISIONS.md#g050---the-project-keeps-its-own-rules-decisions-and-half-of-the-reconstruction-contract-2026-10-19-accepted). The template ships a starter of each project file, with the devlog opt-out (`"enabled": false`) for a project that keeps none.

**What the framework contains.**

- The rules, workflow and decision registry (prefix G) and the rationale, with a conformance test that fails when a framework document cites a commit id that does not resolve in the repository, and one that fails when a D-prefixed framework decision reference appears under `governance/`.
- A commit of another repository is cited as `<label> commit` and the id in backticks. A project declares the labels in `project-governance/config/citations.json`; the template declares none. The framework cites its own commits as `template commit`, which the conformance test requires, so a project that copies the framework declares `template` and its copy stays valid ([G051](DECISIONS.md#g051---the-commit-of-another-repository-is-cited-by-a-declared-label-2026-10-20-accepted), [the setting](PROJECT-GOVERNANCE.md#citationsjson)).
- The agent entry: `AGENT-ORIENTATION.md` is the file every agent reads first, with `ROLE-COORDINATOR.md` and `ROLE-WORKER.md` for the two roles (an agent that is not told its role is a worker). `AGENTS.md` is the project's own thin file that points to it, pinned by a conformance test. The preview is waived with the plain words "no preview" or "skip preview" in an order. See [G041](DECISIONS.md#g041---agent-entry-and-role-files-2026-10-18-accepted).
- The tools in `tools/` (checkpoint, worktree guard, claims, local jobs, continuity check, test runner, runtime guard) with their tests in `tests/`, the scripts that start them in `scripts/`, and a conformance test that pins the mode of every committed shell script.
- The framework's configuration in `config/`: policy, profiles, the classification golden pin and the framework part of the reconstruction contract, with the conformance tests that pin them.
- The checkpoint workflow: a worker asks for a go, and later for an Approve, alone, never with another question ([G047](DECISIONS.md#g047---the-go-and-the-approve-are-asked-alone-2026-10-18-accepted), [the workflow](CHECKPOINT-WORKFLOW.md#the-go-and-the-approve-are-asked-alone)); the final trailer block of a checkpoint holds only `Class:`, `Subclass:` and `Worker:`, and `checkpoint.py preview` and `prepare` refuse any other key, `Co-Authored-By:` included, because `Worker:` already names the agent for every vendor ([the commit-message convention](CHECKPOINT-WORKFLOW.md#commit-message-convention)).
- Any change to a path under `governance/` or `project-governance/` also runs the whole conformance folder, `config/conformance/`, with the continuity tests (`tests/continuity/`): the `continuity-regressions` check discovers every `test_*.py` of both, so a conformance test that pins rule text can no longer be broken by a change that never selected it. It adds about two minutes to a governance mission. A path outside both folders selects it only when its table row names the `conformance` invariant ([the impact selection](CHECKPOINT-WORKFLOW.md#impact-selection-beneath-profiles)).
- Transaction worktrees with guarded integration. A worker removes its own superseded mission with `worktree.py remove --superseded-by <landed full commit>`, which refuses unless the replacement is on main, its landing is recorded under the same Job, the old store holds no live packet and the owner matches ([G048](DECISIONS.md#g048---the-owner-removes-its-superseded-mission-2026-10-19-accepted), [the worktree workflow](WORKTREE-WORKFLOW.md#a-superseded-mission)). `worktree.py remove` also deletes the mission's own review folder (`_review/<mission-id>/`) after the worktree and the branch, and refuses before removing anything when that folder holds a subfolder, a link or a junction ([the G025 review folder lifecycle extension](DECISIONS.md#g025-review-folder-lifecycle-extension-2026-10-18)).
- The runtime guard. Every governed command starts with `tools/runtime_guard.py` and is written `python -B governance/tools/<tool>.py`, with no registration and no operator step. The guard stops under a Python older than 3.13, removes inherited `GIT_*` variables, refuses at once a command that writes shared state while a worktree lifecycle operation runs, and pins a transaction to the interpreter it began on ([G043](DECISIONS.md#g043---the-runtime-guard-replaces-the-admission-shim-2026-10-18-accepted), [the runtime guard](CHECKPOINT-TOOL.md#runtime-guard)).
- Machine-local state that every worktree shares lives in the git-ignored `.local/` folder of the primary checkout (the timing record and the lifecycle lock), named by `tools/support/local_state.py`; the tools create the folders on demand and refuse to write there when `.local/` is not ignored, so a project's `.gitignore` ignores `/.local/` (hazard H22: `git clean -x` deletes it). The per-checkout checkpoint store lives in the `governance/` folder of the checkout's own Git directory and dies with its worktree ([G044](DECISIONS.md#g044---shared-machine-local-state-lives-in-local-of-the-primary-checkout-2026-10-18-accepted), [G046](DECISIONS.md#g046---the-checkpoint-store-lives-in-the-worktrees-git-directory-2026-10-18-accepted), [the worktree workflow](WORKTREE-WORKFLOW.md#ownership-and-shared-state)).
- The test runner keeps its per-run scratch folders in a `tmp` folder next to the main checkout's folder, created when missing and found through Git's common directory ([the test runner](CHECKPOINT-TOOL.md#test-runner)).
- Mission Control, the first extension: `extensions/` holds the optional pieces and `tests/extensions/` their tests, and the core never depends on an extension. `python -B governance/extensions/remove_extension.py <name>` removes one, and a conformance test proves the core passes its tests without them ([G042](DECISIONS.md#g042---the-core-never-depends-on-an-extension-2026-10-18-accepted), [the extensions README](extensions/README.md)). Its port is the project setting `config/mission-control.json`, 8765 without the file, bound exclusively with no fallback ([the Mission Control README](extensions/mission_control/README.md)).
- The `devlog/` folder at the project root, empty, with the project's conventions and the index.
- A new project runs the adoption helper once, after `git init -b main` and `git add -A` and before its first commit: `python -B governance/tools/adopt.py` sets the executable bit of the staged shell scripts in the index and declares the label `template` in `project-governance/config/citations.json`, so the project passes the script-mode and cited-commit conformance tests; it refuses where a commit exists. The first Coordinator thread creates the queue record with `python -B governance/tools/local_jobs.py --repo . claim-coordinator --identity '<who you are>'`, and a later thread takes the role over only with `--take-over --reason` ([G053](DECISIONS.md#g053---a-new-project-runs-one-adoption-helper-and-its-first-coordinator-claims-the-role-by-command-2026-10-20-accepted), [the helper](CHECKPOINT-TOOL.md#the-adoption-helper), [the claim](ROLE-COORDINATOR.md#claiming-the-role)). The conformance test of cited commits now reads the labels the repository declares.
- [Project lifecycle](PROJECT-LIFECYCLE.md) is the framework's page for the lead developer: six phases (adopt, set up, run, repair, change, upgrade), the commands a person runs in each and links to the sections that own the details. The steps for adopting a project and for taking an update moved there from the root `README.md`, which keeps a short summary and a link; the root `README.md` is the project's and an upgrade never replaces it, so an adopter's copy of the old steps is not updated, and the page is the one to follow. A conformance test checks that every path the page names exists.

A conformance test keeps the two notice lines equal and the license text canonical.
