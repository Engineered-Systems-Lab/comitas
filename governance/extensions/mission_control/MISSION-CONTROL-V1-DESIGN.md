# Mission Control v1 design

Status: Settled design; generator committed; UI settlement authorized for final validation and G018 review.
Scope: Read-only repository observation under [G030](../../DECISIONS.md#g030---mission-control-boundaries-2026-10-03-accepted).
Authority: [Governance](../../README.md), [Constraints](../../CONSTRAINTS.md), component contracts and their owning sources retain authority.

## Purpose and authority

Mission Control makes repository decisions, commits, devlog entries, rationale and documents browsable with content and traceability. It is read-only and non-authoritative. A displayed status, relationship or validation result does not grant approval, change project state, replace Progress, or override a source artifact. It supplies no write, commit, staging, acceptance or workflow-control action; the one dated exception, which touches only ignored local files, is the [local queue view and refresh](#local-queue-view-and-refresh-2026-10-10). Generated output is a disposable view, never a source of truth; the repository's prohibition on committing generated/transient build artifacts applies, except for the lead-developer-authorized five Mission Control v1 JSON snapshots under `data/` (generator implementation transaction), an exception that ended on 2026-10-11 when the [datasets left the repository](#datasets-leave-the-repository-2026-10-11). The datasets remain derived, disposable and non-authoritative; dependency state and scratch remain excluded.

This transaction records design only. No generator, data files or UI are created. Later implementation requires its own authorized scope and affected validation.

## Architecture and datasets

Use static HTML, CSS and JavaScript consuming JSON produced by a deterministic Python generator under the repository's [interpreter policy](../../CONSTRAINTS.md#python-interpreter-policy). No application server or network service is needed for rendering content. Initial partitioning is by artifact type:

| Dataset | Content |
| --- | --- |
| `decisions.json` | Decision identity, status and renderable decision content |
| `commits.json` | Full commit identity, declared repository commit metadata and message content |
| `devlog.json` | Renderable devlog entries |
| `rationale.json` | Non-normative explanations with source traceability |
| `documents.json` | Renderable repository documents and their source locations |

Each dataset is self-contained for rendering its own records: include content, display metadata and traceability rather than requiring live source reads or another dataset to assemble a record. Explicit cross-type navigation may resolve a target in another dataset; that target dependency must be declared for validation. Keep source authority, historical context, reported evidence and newly executed evidence distinguishable. Do not turn extracted prose into a new acceptance claim.

### Decision and rationale granularity (lead developer refinement, 2026-10-03)

Rationale explanations must be individually browsable, at decision granularity rather than one opaque record for an entire guide. Preserve an explicitly shared explanation as one joint record, including combined identities such as G016/G017; do not split or duplicate its shared prose. Use exact decision labels for associations, preserving extension identities; a label is a registry row or a dated extension heading of the Decisions document, as the [generator README](README.md#decision-identity) defines. A joint explanation can link to several decisions and a decision can have several explanations. Preserve audit-only findings, including explicitly missing rationale, and unnumbered explanations without assigning invented decision IDs.

Embed each explanation's complete section and the source's document-wide authority/evidence context. Retain the owning source fragment (or exact audit row), explanatory status and per-decision audit classifications. Emit both decision-to-rationale and rationale-to-decision links when the source explicitly identifies that association; each direction must cite that association evidence. This is a declared association extraction rule, not general permission to fabricate inverse Markdown relationships. Targets may carry an exact record ID alongside complete source identity so table-only decisions and shared-section records resolve without ambiguity. Validate those record targets and evidence against the declared selection. Both families depend on the association inventory; normal generation must invalidate either side when that mapping changes.

## Declared inputs and deterministic identity

The later generator must declare the repository source inventory, source revision/content selection, relevant Git objects and explicit configuration that determine output. Inputs include only those declared repository sources and objects. Exclude ignored scratch, caches, generated output and private or machine-specific configuration. Do not infer the source revision from an ambient branch selection. A declared configuration is itself a repository input.

Use repository-relative POSIX source paths with exact case and resolvable fragments where applicable. Use complete Git SHAs for commit/revision identity; abbreviations are not identities. Source traceability must identify the owning path and section or commit object, and the full revision when applicable. For proposed working content, identify it as a proposal using declared content identity; do not label it committed.

Output must not depend on wall-clock time, host details, network access, environment variables, filesystem timestamps, locale, traversal order, absolute checkout location or other ambient data. Dates already recorded in declared documents or Git objects may be represented as source facts; do not add a generation-time clock value.

Fix stable total sorting, including deterministic tie-breaks using stable record identity. Specify canonical serialization before implementation: UTF-8 without BOM, LF endings, a final LF, two-space JSON indentation, lexicographically sorted object keys, literal Unicode and no non-JSON numeric values. Array ordering must follow each declared total sort rather than filesystem or discovery order. Equal declared inputs must yield byte-identical output across checkouts and executions.

## Normal generation and full regeneration

Normal mode updates only affected type datasets before sealing an implementation transaction. Determine affected types from changed declared inputs and explicit extraction/link dependencies, including additions, deletions and changed link targets. A shared input may affect several types; explain that dependency rather than rewriting everything. Validate the complete resulting view, including unchanged datasets.

An unaffected dataset must remain byte-identical and must not be rewritten merely to refresh a timestamp, source-tip marker, envelope or global generation identifier. Traceability belongs to the content's declared source identity; a new unrelated commit must not stamp every dataset. If a dependency requires changed bytes, that dataset is affected.

Provide an explicit full regeneration mode, separate from normal updates. It reconstructs every dataset from the same declared input selection for verification or reconstruction. Compare its complete output with the normal-mode result to establish equivalence; it is not an implicit normal-mode fallback. Normal mode must fail when dependency knowledge or existing state cannot establish correctness, with an explicit full reconstruction available to the operator.

These are future generator acceptance requirements. Current checkpoint sealing concerns this design and its scoped evidence only; it executes no Mission Control generator.

## Evidence-backed directed links

Represent directed links only when source evidence supports the relationship. Preserve direction and cite the supporting source/path/fragment or full commit object. A citation, supersession, checkpoint association or document reference may support a link; similar names, shared topics, timestamps, neighboring IDs or matching suffixes do not.

Validate record identities, uniqueness, link targets, paths, fragments and evidence against declared inputs. Broken links fail validation; do not silently drop them, fabricate a target or downgrade the failure. Distinguish unresolved design questions from validated relationships. Existing historical path conventions must resolve against their explicitly identified revision rather than inventing a current path.

## Navigation, search and filtering

Provide free-text search and button filters by type, category, topic and status. No selection in a filter dimension means all values. Selected values within a dimension match any selected value; active dimensions and free text combine to narrow results. Preserve source-derived metadata; absence of category/topic/status must not invent a source fact.

Devlog entries are the entries of the devlog folder: historical engineering records, not current authority. Their `Date` line is shown as written and the display never renames or rewrites log metadata.

Full breadcrumbs represent actual navigation history, including repeated visits and cross-type transitions. They must not fabricate an authority hierarchy or a shortest path from the current item. A direct entry has only the actual entry history; back/forward and breadcrumb navigation must preserve the corresponding visited trail. Dataset links express evidence; breadcrumbs express the user's navigation.

## Visual direction and prototype boundary

Later UI work uses a plain terminal aesthetic: readable terminal typography, restrained color, clear panels and useful interaction states. Visual style cannot obscure authority labels or source links.

UI prototyping remains uncommitted in its own isolated, transaction-owned worktree until the lead developer explicitly says freeze. A freeze instruction settles the prototype boundary; G018 still requires approval of the exact prepared commit transaction. This design authorizes no prototype or UI implementation now.

## Later implementation verification

Require byte-identical independent full generations from equal declared inputs; normal/full equivalence; unchanged-type byte preservation; affected dependency/addition/deletion cases; full-SHA and POSIX-path traceability; and failing broken-link cases. Verify self-contained rendering without live source/network reads, filters with no selections, actual-history breadcrumbs and both log classes. Select focused generator/UI tests only when those components are authorized and implemented.

For this design transaction, use manifest-derived governance/checkpoint checks, document links/references, continuity and whitespace. Reuse authenticated unchanged regression evidence at sealing under the [checkpoint workflow](../../CHECKPOINT-WORKFLOW.md#reusing-checkpoint-validation-evidence). Design validation is not generator reproducibility or UI acceptance evidence.

Plain-text commits render once; original Markdown remains separately inspectable.

The UI reads only the five generated JSON datasets, resolves explicit exact record/source targets without guessing ambiguous sections, and adds no writes, graph, live transaction inference or general reverse relationships. The static local server is an optional loopback preview helper, not a product application backend.

## Local queue view and refresh (2026-10-10)

The lead developer asked for a live job queue in the browser and for a button that refreshes the datasets when they need it. Both are local conveniences beside the derived datasets, not repository observation: the queue comes from ignored machine-local records and the refresh rewrites ignored local copies of the datasets. Neither changes a tracked file, a ref or a worktree, and neither carries authority, approval or workflow control, so the read-only boundary above still holds for the repository. This records the server's allow-list and guards under the [G030 local queue and refresh extension](../../DECISIONS.md#g030-local-queue-and-refresh-extension-2026-10-10).

- **Allow-list.** GET serves the five UI assets, the five `/data/<kind>.json` datasets and `/queue.json`. POST serves `/refresh` and nothing else. Every other path is 404, every other method is 501, and HEAD of the two dynamic paths is 405.
- **Queue.** The Queue tab reads `GET /queue.json`, which the server computes for each request by running the validated `local_jobs.py queue` helper through its thin launcher: one parser, and the helper finds the primary checkout, also when the server starts from a linked worktree. The queue arrives in the helper's order of execution (in flight first, then priority, ready before blocked, then handle, as [local coordination](../../LOCAL-COORDINATION.md#epics-dependencies-and-priority) defines it) and the page keeps that order, so the page and the report cannot disagree. The page labels it local, non-authoritative and with its read time, and the repository and the committed records win on any conflict. When the local records are absent it shows a message and no queue. The server passes a fixed list of fields to the page: Epic rows include the effective `closure_policy` (`automatic` when omitted), shown in their bands, and empty explicit Epics remain visible as awaiting explicit closure; pending notes appear only as a count, and record paths, workers and steps never leave the server. Missing records are flagged, BLOCKED and waiting on dependencies are shown separately, and nothing is cached, polled or scheduled.
- **Status light (2026-10-13).** `GET /queue.json` also carries an `execution` field, computed for each request by one fixed read-only command, `worktree.py execution-status --json-only`, through its thin launcher (the [G025 execution status extension](../../DECISIONS.md#g025-execution-status-extension-2026-10-13)). The server passes a fixed list of fields: level, the status line, each open window's owner, scope, state, since time, Job handle, flags and whether its command is running, the database state, the number of windows declared without evidence and `poll_seconds`; paths, process ids and evidence text never leave it, and an unreadable status is UNKNOWN, never CLEAR. The masthead shows a status light to the left of the Refresh button on every tab: a legend, then a round dot, in a rounded rectangle tinted toward green (CLEAR), red (FROZEN, `REFS FROZEN: <owner>, <since>`), yellow (OVERLAP, reserved) or grey (UNKNOWN). The legend carries the meaning, and the page builds it with `textContent` and `setAttribute`. The page reads the status on load and when the tab regains focus, and on a timer only when the server was started with `--light-poll-seconds <n>` (0 by default, minimum 10). The payload version is MAJOR.MINOR and the page reads any minor of major 1. This adds no route and the page still only reads.
- **Claims strip (2026-10-13).** The same `execution` field carries the active claims of schema 1.1: one row per running mission with its owner, Job handle, level, subclasses, file count, since time and flags, the overlaps that name them (owners, kind and wording) and the number of stale claims. The server passes only those fields; worktree paths, process ids and claim ids never leave it. The Queue tab shows them in a strip under its notice, or one quiet line, built with `textContent`, and joins each row to the queue payload on the Job handle in the page (a handle inside an Epic reads `epic--job`), flagging a Job the record calls finished while its transaction exists; the transaction wins and the flag only asks the lead developer to look. The OVERLAP tint of the status light is now produced. The preview server's `PreviewServer` ignores exactly `ConnectionAbortedError`, `ConnectionResetError` and `BrokenPipeError` when a browser closes a connection early and prints every other exception (the [G025 claims overlap extension](../../DECISIONS.md#g025-claims-overlap-extension-2026-10-13)). No route is added and the page still only reads.
- **Waiting for the lead developer.** A Job record may carry `awaiting_lead` under [local coordination](../../LOCAL-COORDINATION.md). The Queue tab shows a `waiting for you` chip and, for an allow-listed vendor with a UUID session id, an `open session` link. The link opens a session and approves nothing.
- **Refresh.** The Refresh button sends `POST /refresh`, which runs one fixed command, `data_launcher.py refresh-local`: it brings the datasets to the checkout's HEAD and publishes them to `.local/mission-control/data/` in the primary checkout, which the job helper finds like the coordination records: ignored by Git and shared by every worktree. There is one current copy and no history. The update is incremental by default (lead developer, 2026-10-10: "can we just update, by default, rather than rebuild it all?"): the copy keeps the generator's dependency state (`state.json`) beside the datasets, the changed input paths come from Git between the revision in `meta.json` and HEAD, and the generator's own `normal` mode rebuilds only the affected datasets, which measured 19 to 22 s on the development machine against 39 s for the former full rebuild plus verify (a full rebuild without verify takes 20 s; a copy already at HEAD takes 0.1 s). Most of what remains is the generator's own Git calls for the commit dataset and the source checks, which normal mode keeps. It falls back to a full rebuild, and says why, when the state is missing or damaged or no longer matches its datasets, when the generator code or the inventory differs from the one that built it, when the recorded revision is not an ancestor of HEAD, when more than 200 input paths changed, or when `normal` refuses; a copy already at HEAD is left alone. The verify pass is skipped on this path, both for the incremental update and for its fallback: the copy is a local convenience, the generator already checks every record's source and link traceability on every run, determinism is covered by the test suite, and the `refresh-local-full` command keeps the verified full path. The full update with verification stays on the command line as `data_launcher.py refresh-local-full`; the page has no second button. The button and the status text name the kind that ran (incremental update, full rebuild or already current) and its time. The command builds the new copy in a temporary sibling folder, swaps it in and deletes the old one, so a failed run leaves the previous copy in use and nothing else needs pruning. `meta.json` beside it records when the copy was generated, from which revision and by which generator version. The command never writes the tracked datasets or the pinned selection, so a press cannot dirty a checkout. The server serves the local copy while it is whole (and, until 2026-10-11, the committed copy otherwise), and names the copy it served in the `X-MC-Data-Source` header: generated at, source revision, generator version and whether that revision is the checkout's HEAD. The page shows this in its footer, so an older or missing copy is visible.
- **Refresh guards.** The server binds 127.0.0.1 only. A refresh needs `Host` equal to `127.0.0.1:<port>`, `Origin` equal to `http://127.0.0.1:<port>` and, when the browser sends it, `Sec-Fetch-Site: same-origin`; a missing or foreign value is 403, so a page on another site cannot start one. It takes no request body, query string or parameter, runs the one fixed command (never `governance/scripts/mission-control-data-sync.sh`), allows one run at a time (a second request gets 409) and answers with a plain JSON status that the page shows as text. The page builds every queue value with `textContent` and `setAttribute`, and the Content-Security-Policy still drops inline scripts and styles, so the queue styles live in `ui/style.css` under `jq-` class names.
- **Removing the committed copy.** Until the committed datasets leave the repository the local copy shadows them. Once they have gone, only the fallback to the committed copy goes with them. That happened on 2026-10-11, as the next section records.

## Datasets leave the repository (2026-10-11)

The lead developer decided that the generated datasets leave the repository and that they refresh them locally when they need them, with no refresh Jobs. This amends the [G030 agent-consumption extension](../../DECISIONS.md#g030-agent-consumption-extension-2026-10-03) and retires the exception for committed snapshots; the [rationale](../../RATIONALE.md#mission-control-boundaries-g030) records why.

- **Not tracked.** Git stops tracking `governance/mission-control/data/*.json` and `governance/mission-control/snapshot-selection.json`, History keeps the old copies and nothing is rewritten. The ignore rule for the `data/` folder follows in a separate small change, because the checkpoint tool refuses a manifest path that an ignore rule already matches, deletions included; until then only the generator's own `state.json` is ignored there, and nothing in the repository writes the folder.
- **Retired.** The `mission-control-snapshots` check, the `refresh` and `check` modes of `data_launcher.py` with their backlog report, the pinned selection and the lead-developer-only sync script go. The generator, its tests, the terminal and the terminal check stay, and the generator still accepts an explicit selection file.
- **One source for the terminal.** The server serves the local copy under `.local/mission-control/data/` when it is whole and answers 404 otherwise; there is no committed fallback, and the `X-MC-Data-Source` header always names a local copy. With no copy the page says to press Refresh. `governance/extensions/mission_control/mission-control-data.sh refresh` runs the same `refresh-local` command as the button.
- **Terminal check.** The Node tests need datasets, so `governance/tests/extensions/mission_control/check.py` generates them at HEAD into a temporary folder for each run, or reads the folder named by `MC_DATA_DIR`. A fresh worktree has none of its own.
- **Measured.** On the development machine a full generation took about 29 seconds and `refresh-local`, which also verifies, about 58 seconds.
- **Agents.** Agents may use the local JSON as a cache that may be absent or older than HEAD; the source wins.

This changes presentation only: sources, selection, filtering and authority are unchanged. The earlier statements above keep their historical scope.
