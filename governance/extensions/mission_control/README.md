# Mission Control generator v1

Mission Control is a local, read-only view of this repository and its work. It has two parts: this generator, which derives five JSON datasets (decisions, commits, devlog entries, rationale and documents) from the repository’s Git history and declared sources, and the [terminal](ui/README.md), a static page served on 127.0.0.1 only that browses them. The terminal also shows two local views that no dataset holds: the job queue, read from the machine-local coordination records when the Queue tab opens, and a status light that reads the execution status of ref windows. Its one action is Refresh, which regenerates the datasets at the checkout’s HEAD into the ignored `.local/mission-control/data/` folder of the primary checkout and changes no tracked file. Everything shown is derived and non-authoritative: the owning repository sources retain authority, and the datasets are never committed. Use the JSON to find the answer; use the source to prove it.

The datasets are read-only and observational. Python 3.13+ and Git are the only dependencies. Complete `contentMarkdown` or `contentText` is embedded in each record; the browser renderer needs no Markdown source reads. Markdown is content, never executable HTML or authority. External links are preserved without network validation.

## Declared inputs

The inventory has three sources, merged by `declared_inputs.py` into the one file the generator takes. `inputs.json` beside it is the framework part: it ships with the extension and lists framework paths only. `project-governance/config/mission-control-inputs.json` is the project part: optional, `{"version": 1, "datasets": {...}}` with the same selectors, listing the project's own documents; the two lists are unioned, and without the file the terminal shows the framework alone. The project part may also declare the project's own `project-governance/DECISIONS.md` (prefix D) and `project-governance/RATIONALE.md`; the decisions dataset then lists them beside the framework's registry (prefix G), a registry holding a decision of the other prefix is refused, and a revision without the files simply has none (G050). The devlog dataset comes from the devlog setting (`project-governance/config/devlog.json`): its folder is the dataset's directory and the folder's conventions and index are excluded from the log (the part that owns them declares them as documents); with `"enabled": false` the dataset is empty, says `enabled: false` and the terminal says the project keeps no devlog. Exact document paths are intentionally listed. The declared rationale and devlog entry Markdown directories admit additions and deletions. Add other documents by editing the project part, then explicitly regenerate all datasets. Git tree metadata is used only to select declared directories and resolve explicit links; the generator does not crawl working files. Commits are the complete graph reachable from the explicitly supplied full commit SHA. It never reads ambient HEAD or branch names to select content.

Local Markdown references and explicit Repository checkpoint metadata supply directed links, with source evidence. References into documents, binary artifacts outside rendered families are traceable source targets, not invented dataset records. Fragment validation uses the repository's ATX heading convention with duplicate-heading suffixes. External URLs retain source facts, without fetching mutable external state. Code examples and historical prose paths do not invent links. Complete historical Markdown is preserved, including uncertainty and obsolete statements.

Source identity is the last owning Git commit and full blob SHA, or an explicitly supplied proposal content SHA-256. An unrelated source-tip advance never stamps every dataset. Decisions retain every registry row plus its matching detailed section; table-only decisions have an exact source line. Array ordering is by stable full record ID; link ordering is by canonical complete link bytes. Serialization is UTF-8 without BOM, LF and final LF, two-space indentation, sorted object keys, literal Unicode and finite JSON numbers.

Rationale extraction follows the [granularity refinement](MISSION-CONTROL-V1-DESIGN.md#decision-and-rationale-granularity-lead-developer-refinement-2026-10-03). Each level-two explanation is a record; a single-decision section uses `rationale:<exact-decision-label>`, while shared or unnumbered sections use `rationale:<path>#<source-fragment>`. Joint explanations remain intact. Coverage comes only from the owning heading's decision annotation after the colon (exact decision labels, comma/slash lists and inclusive ranges), never incidental prose mentions. An explicit compound registry label also identifies its constituent decisions. Audit rows not covered by a section become individual findings; missing reasons remain missing. A heading-free rationale document remains one document record. Duplicate single-decision record identities fail for reviewed disambiguation rather than merging unrelated explanations.

Each rationale embeds its section, document introduction and audit definitions, plus applicable audit rows. `decisionIds` lists explicit association endpoints; `decisionId` is supplied only for a singleton. `rationaleStatuses` retains source audit classifications separately from the explanatory/non-normative status. Both `explains` and `rationale` directed edges carry the source association evidence. Their targets include `recordId` and exact source identity, including a source line for table-only decisions; no UI source reads or guessed reverse links are needed. The shared decision/rationale source inventory is retained in dependency state even when it currently contains no association, so additions/removals invalidate both families.

## Decision identity

A decision record has the identity `decision:<label>`. A label is the text of a registry row's first cell, or the text of a dated extension heading of the Decisions document (`### D0xx <name> (date)`, or `(date, Status)`) that no registry row stands for. The Decisions document is the only source; the generator keeps no list of names.

A registry row stands for a heading when its label equals the heading text, or when its statement links the heading's anchor. The row keeps its identity, its record and its bytes, and the heading's text becomes another spelling of that label: a rationale audit row or a heading annotation may use either spelling and resolves to the same identity, and the same decision named twice fails as a duplicate. A heading no registry row stands for is its own record. Its date comes from the heading, its status from the heading's `(date, Status)` form and otherwise the fixed default `Accepted`, its summary is the first sentence of the section and its content is the section, which stops at the next heading of the same or a higher level. The enclosing registry decision keeps embedding the extension text as before.

An audit row or annotation whose label is neither a registry row nor an extension heading fails generation and names the label. So do two registry rows that link one heading, a repeated extension heading and an extension heading with no text.

For a standalone rationale about a dated extension, use that extension's exact decision label in the level-two heading annotation after the colon. The actual G025 example is `## Same-tree transient ref names: G025 same-tree transient ref-name extension`, matching the [dated extension](../../DECISIONS.md#g025-same-tree-transient-ref-name-extension-2026-10-08). `G025 extension` resolves to G025 instead of identifying that dated extension and can collide with an existing single-G025 explanation. A standalone section's position does not supply identity. The audit label and heading annotation resolve through the same source-derived decision labels. This explains the existing extraction rules; it introduces no generator change.

## CLI

Replace `python` with a verified 3.13+ interpreter and `<full-sha>` with the reviewed 40-character source commit. The launcher writes the merged inventory into its scratch; these commands take the framework part alone, which is a valid inventory but holds no devlog and no project datasets, so a project that wants those uses the inventory Refresh assembles with `declared_inputs.load(root)` instead. Any file of the same shape can stand in for it. Run from the repository root:

```sh
python -B governance/extensions/mission_control/generate.py full --repo . --revision '<full-sha>' --inventory governance/extensions/mission_control/inputs.json --output governance/extensions/mission_control/data
python -B governance/extensions/mission_control/generate.py normal --repo . --revision '<full-sha>' --inventory governance/extensions/mission_control/inputs.json --output governance/extensions/mission_control/data --changed governance/RATIONALE.md
python -B governance/extensions/mission_control/generate.py verify --repo . --revision '<full-sha>' --inventory governance/extensions/mission_control/inputs.json --output governance/extensions/mission_control/data
```

Normal mode requires intact `data/state.json`, equal inventory/generator behavior and matching dataset hashes. Supply every changed input path, including deletions and link targets. It independently checks the old/new Git tree and declared proposal identities for omissions. It rebuilds only affected families and validates all resulting source/link traceability before writing. Unknown paths, unsupported dependency state, changed inventory/behavior or missing/corrupt outputs fail closed: use explicit full regeneration. Git graph changes affect commits only unless declared source/link inputs also change. Changes to a referenced target affect the referencing dataset because the target's traceability is embedded.

For proposed content, add `--proposal <external-json>` to any mode. The external JSON maps each exact POSIX path to its raw-byte SHA-256, or `null` for a deletion. Only listed files are read from the checkout, with identities and exact case verified; all other content comes from the declared commit. Proposal content is labeled proposal, never committed. Equal committed/proposed input selections reconstruct identical snapshots. The inventory itself is supplied explicitly and hashed in state. No implicit full fallback exists.

## Generated datasets are never committed

The five datasets are derived, disposable and non-authoritative, unlike source specifications. Since 2026-10-11 they are not tracked: the former committed snapshots, their pinned `snapshot-selection.json` and the check that verified them are gone. Git history keeps the old copies, and the acceptance record keeps their evidence as history. The lead developer generates them locally when they need them, as described under [Local refresh](#local-refresh), and the generator, its tests and the terminal stay. The CLI above still takes an explicit `--selection` file of the same two keys (`revision` and `proposal`) instead of `--revision`/`--proposal`; the launcher writes one for HEAD into scratch for each run.

Run focused acceptance with `python -B governance/tools/run_tests.py -s governance/tests/extensions/mission_control -p 'test_generate.py' -v`. No runtime, container or UI acceptance is established by this run.

## Local refresh

The lead developer regenerates the datasets when they need them, without an LLM and without a commit. Either press Refresh in the [terminal](ui/README.md) or run, from the repository root:

```sh
python -B governance/extensions/mission_control/data_launcher.py refresh-local
python -B governance/extensions/mission_control/data_launcher.py refresh-local-full
governance/extensions/mission_control/mission-control-data.sh refresh
```

The third line is the same command as the first through a thin shell shim that also works from outside the repository. `refresh-local` and `refresh-local-full` are the launcher's two modes. It starts with the [runtime guard](../../CHECKPOINT-TOOL.md#runtime-guard) (declared LOCAL, so it runs while a lifecycle operation holds its lock) and works in ignored `tmp/mission-control-data/` scratch, removed on exit. It writes a selection for the checkout's committed `HEAD` into that scratch (uncommitted edits are not read, and there is no proposal overlay) and updates the datasets incrementally by default: the local copy keeps the generator's `state.json` beside its datasets, the changed input paths come from Git between the revision in `meta.json` and `HEAD`, and the generator's `normal` mode rebuilds only the affected datasets (19 to 22 s on the development machine against 39 s for a full rebuild plus verify). A copy already at `HEAD` is left alone. It falls back automatically to a full rebuild, and prints why, when the state is missing, damaged or no longer matching its datasets, when the generator code or inventory is not the one that built it, when the recorded revision is not an ancestor of `HEAD`, when more than 200 input paths changed or when `normal` refuses. It skips the independent `verify` pass, incremental or not: the copy is a local convenience, the generator already validates every record's source and link traceability on each run, and determinism is covered by the test suite. `refresh-local-full` is the full update on the command line: a full rebuild followed by the `verify` pass, which reconstructs independently and proves byte-identical, deterministic output.

Only after generation succeeds does it build the new copy in a temporary sibling folder of `.local/mission-control/data/` in the primary checkout, swap it in and delete the old one, with a small `meta.json` (generated at, source revision, generator version) beside it. There is one current copy and no history, shared by every worktree. It never writes a tracked file, so it cannot dirty a checkout, and a failed run leaves the previous copy in use. The terminal serves a whole local copy and nothing else: with no copy it says so and the Refresh button makes one. A fresh worktree therefore has no datasets until a refresh; the terminal check generates its own into a temporary folder. The [terminal](ui/README.md) keeps serving during a refresh; open tabs retain their loaded copy, so reload the browser after refresh reports success. The [design record](MISSION-CONTROL-V1-DESIGN.md#datasets-leave-the-repository-2026-10-11) owns the rest.

## Read-only terminal

The [Mission Control terminal](ui/README.md) provides Overview, Status briefing and five artifact sections using only the locally generated JSON. Run `python -B governance/extensions/mission_control/ui/serve.py` from the repository root and open the address it prints. The port is the project's setting in `project-governance/config/mission-control.json`, 8765 without it, and `--port` overrides it; a port that is taken stops the server with one line instead of another port being tried ([Run locally](ui/README.md#run-locally)). Python must meet repository policy; focused UI checks additionally require Node.js on PATH. The [UI settlement](MISSION-CONTROL-V1-DESIGN.md#ui-review-settlement-2026-10-04) owns the interaction decisions.

## Structured commit metadata

Commit records add `classes` (always an array, empty when historical evidence is insufficient), `subclasses` (always an array), `worker` (string or null), and `inferredFields` (reconstructed field names). Explicit Class lists and subclasses are canonicalized; output follows the registry order in `governance/config/checkpoint-profiles.json`. `categories` and `topics` retain their existing meaning and bytes. UI presentation of these fields is deferred.

For historical messages without Class, use the classes that the artifact classification table gives every changed path, live or under its Historical paths section; unmapped paths or merge commits yield unknown. The Subclass labels of those paths may supply subclasses only when base classes are known. Mark each reconstructed nonempty value in `inferredFields`. Omitted optional Subclass on explicit messages remains an empty array without inference. Worker is read only from an explicit trailer: author/committer and writing style do not establish execution environment. No model/configuration is guessed and Git history is unchanged. Malformed declared metadata fails rather than becoming inferred metadata. Policy, registry and the classification table are selected source inputs and commit dataset dependencies.

Historical `Class: mixed` trailers from the retired model reconstruct the underlying base-class list from selected path evidence and mark `classes` in `inferredFields`; original messages remain unchanged. Unknown evidence yields empty classes/subclasses. New preparation rejects `mixed`. Explicit new metadata normally has empty `inferredFields`; supported inferred names are `classes`, `subclasses`, and `worker`.
