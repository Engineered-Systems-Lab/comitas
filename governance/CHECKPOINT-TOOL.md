# Checkpoint tool v1

Implementation notes for [the authoritative workflow](CHECKPOINT-WORKFLOW.md) and G018. This tool does not interpret authorization, compose messages, update records, or grant permission. Nothing in this document authorizes a real transaction.

## Inputs and commands

Use Git and Python 3.13 or later under the [interpreter policy](CONSTRAINTS.md#python-interpreter-policy); in command examples `python` stands for any such interpreter, and compatible 3.14+ is allowed. Start in a quiescent owned checkout with an existing HEAD and attached branch. Linked worktrees require the [mission ownership convention](WORKTREE-WORKFLOW.md); main preparation is rejected while other worktrees exist. Active commit hooks (including shared default hooks), in-progress Git operations and unreviewed inherited `GIT_*` overrides are rejected. No Git configuration is written. Profiles invoke the running Python interpreter by argument array; no shell evaluation or execution-policy change is used.

The only permitted worker overrides are optional `GIT_PAGER=cat` (exactly; disables paging), and an optional **complete** configuration injection: `GIT_CONFIG_COUNT=2`, `GIT_CONFIG_KEY_0=safe.directory`, `GIT_CONFIG_VALUE_0=<resolved repository root>`, `GIT_CONFIG_KEY_1=safe.directory`, `GIT_CONFIG_VALUE_1=<resolved repository root>/*`. Values must match the native string spelling of the resolved root exactly (for a repository at `C:\dev\project`: `C:\dev\project` and `C:\dev\project/*`). No path normalization, alternate spelling, partial pair, additional entry, other count/key/value, or other `GIT_*` variable is accepted. A clean environment remains supported. Validation happens before the first Git call and again for tool Git calls; the tools themselves neither remove nor rewrite overrides. Governed commands start through their thin launcher, whose [runtime guard](#runtime-guard) removes the other `GIT_*` variables first.

The subtree entry is explicitly permitted only for descendants of this exact root. Both entries relax Git ownership checks and allow repository configuration/hooks to be considered; they are trust grants, not content-only settings. Parent paths, sibling paths and global `*` trust remain rejected. Active commit hooks remain prohibited. Injected configuration remains in `git config --list --show-origin -z` and therefore in the existing sealed configuration digest; adding/removing the permitted pair after preparation fails the strict configuration check in prepare, inspect and commit. Approval alone does not compare the approver process configuration with that digest; the sealed worker configuration is preserved for commit-time revalidation.

The worker supplies an external UTF-8 JSON array of explicit repository-relative whole-file paths, an external UTF-8 message file, the expected full HEAD SHA, full branch ref, and a reference to the lead developer's selective-staging delegation. The delegation reference records the worker's assertion; machinery cannot authenticate its meaning. Resolve mixed-authority edits within a file before preparation. Deleted tracked files must be listed explicitly. Renames require both old and new paths. Directories, globs, duplicates, traversal, ignored/transient/private paths, symlinks and frozen paths are rejected. The one exception to the ignored-path refusal is a tracked deletion: it adds no content, so an ignore rule that matches it, such as one added in the same transaction to cover the files being untracked, does not refuse it. An existing or untracked path that a rule matches is still refused. Unchanged manifest entries fail exact staged-inventory correspondence.

New metadata-enabled preparation also supplies `--worker-context <external-json>`, containing exactly `{"identity":"OpenAI Codex","isAI":true,"configuration":"GPT-6.1 Sol Medium"}` (the model/configuration is an example, not a default). Declare the actual final transaction environment: `configuration: null` means unavailable/unknown, and `isAI: false` identifies a non-AI worker. This is a worker assertion, not provider/model authentication or a global enumeration. When AI configuration is known, Worker MUST equal the identity followed by that exact bracketed configuration. Omission is permitted only when unavailable/unknown. Identity must match Worker. The declaration is copied into sealed profile data; tools do not rediscover or invent configuration at commit time. Historical JSON reconstruction remains independent of this forward-only preparation gate.

### Runtime guard

Every governed command starts with the runtime guard, `governance/tools/runtime_guard.py` (G043). Each thin launcher in `governance/tools/` calls it before it imports anything else, and so does `checkpoint.py`. Commands are written the short way and run from the repository root under any Python 3.13 or later:

```sh
python -B governance/tools/runtime_guard.py --check
python -B governance/tools/checkpoint.py --repo . inspect
```

`python` means any Python 3.13 or later; to use a specific interpreter, run it by its path. There is no registration, no operator step and no second command form. The guard never searches for, discovers or downloads an interpreter. `--check` prints the running interpreter's fingerprint and the names of the variables the guard removed.

The guard is a standard-library module written in syntax that any Python 3 can parse, so that an interpreter that is too old fails with one message instead of a syntax error. It does these things, in this order:

- **Version check.** Under Python older than 3.13 it prints `FAIL: governance tools require Python 3.13 or later; this is Python <version> (<path>). ... Nothing was searched for or downloaded.` and exits 1. Nothing else of the repository has been imported or touched.
- **No bytecode.** It sets `sys.dont_write_bytecode`, so a governed command leaves no compiled files; the documented commands still write `-B`.
- **Git environment.** It removes every inherited `GIT_*` variable from the process environment except exactly `GIT_PAGER=cat`, before any Git call. Hosts inject variables such as `GIT_EDITOR=true`, and a few `GIT_*` variables could redirect the repository, index or configuration Git uses. When it removes any, it prints one line to standard error naming them (names only, never values) and `--check` lists them as `scrubbed`. A tool imported by a test, or started without its launcher, keeps the strict rejection of unreviewed `GIT_*` overrides described above.
- **Lifecycle gate.** While a worktree lifecycle operation (create, reconcile, integrate or remove) holds the lifecycle lock, a GATED command is refused at once, with no wait and no option to wait: `FAIL: refused at once: a worktree lifecycle operation (create, reconcile, integrate or remove) holds the lifecycle lock, and <command> is GATED ... Nothing was started and nothing was waited for. Run it again after the operation finishes.` A command that does not write shared state passes. A lifecycle command started through its launcher has not taken its own lock yet, so it never refuses itself. The lifecycle lock is the file `.local/locks/worktree-workflow.lock` in the primary checkout (the parent of Git's common directory, found from any worktree), and the gate keeps its own small copy of that location because it must run before any repository module is trusted; a test asserts that the copy agrees with `governance/tools/support/local_state.py`, which names the location for every other tool. The tools create the lock with an exclusive create, make the `locks` folder on demand and refuse to start a lifecycle operation when `.local/` is not git-ignored; a missing folder or file means no lock. A repository without a primary checkout (a bare repository, or a common directory that is not a `.git` folder) has no such place: a GATED command is then refused with a clear message instead of guessing.

The gate knows three modes, kept in one registry in the guard, one entry per command and, for a command with subcommands, per subcommand:

| Mode | Meaning | Passes while the lock exists | Entries |
| --- | --- | --- | --- |
| `READ` | Writes nothing. It may show stale or torn data while a lifecycle operation runs, which is acceptable because its output is advisory. | yes | `approval_words`, `show_classification`, `validate_continuity`, `runtime_guard --check`, `timing_record stats`, `worktree paths` and `execution-status`, `local_jobs paths`, `list`, `pointer`, `read`, `queue`, `kinds`, `brief` |
| `LOCAL` | Writes only machine-local scratch (`.local/`, the scratch folder beside the main checkout, the machine-local timing record), or a file the caller names explicitly, and decides nothing from Git state. | yes | `run_tests`, `timing_record export` and `import`, and an extension script that states this mode for itself, such as the Mission Control generator and data launcher |
| `GATED` | Writes shared state, or decides on Git state and then writes. A torn read could close a Job wrongly or seal a candidate against a half-changed ref set. | no | `checkpoint`, `commit_metadata` (it reads a transaction's refs and manifest, then writes), `worktree clear`, `doctor`, `create`, `integrate`, `remove`, `reconcile`, `carry`, `carry-go`, `local_jobs put`, `transfer`, `prune`, `rename`, `note`, `complete`, `dispose`, `claim-coordinator`, `adopt` (it reads that no HEAD exists and then writes the index and one project file) |

The registry fails closed: a command or subcommand that is not in it is GATED. `LOCAL` means named paths only, never "whatever the ignore file lists". The core registry names no extension (the core never depends on an extension, G042), so an extension script passes its own mode when it enters the guard, and the registry always wins for a registered command. A conformance test fails when a launcher is missing from the registry; it cannot prove that a `READ` command never writes, because a mode is a statement about the command. The one known exception is `validate_continuity --freeze` ([G054](DECISIONS.md#g054---freezing-is-always-allowed-and-only-changing-a-freeze-is-restricted-2026-10-21-accepted)): it writes the frozen manifest, one project file of the checkout it runs in, and nothing shared, so the registry keeps the command `READ`; run it in your own worktree, never in a main checkout that another operation is promoting into.

**The interpreter fingerprint.** The guard computes the running interpreter's fingerprint: the resolved executable path, its size, the SHA-256 of the file and the version. The pin is per transaction, not per machine. The first step of a transaction records it: the `preview` record, or the `prepare` when there was no preview (a prepare that carries a go keeps the preview's pin). The packet holds it as `interpreter`, under the packet's authentication and therefore inside the digest that an approval binds, and `finish` copies it into the landing record. Every later step compares the running interpreter with the pin at its start, before it reads or changes anything: `preview-go`, `prepare`, `seal`, `approve`, `approve-consent`, `commit`, `verify`, `finish`, `reconcile`, `integrate`, `carry` and `carry-go` (which compares with the pin of the first preview of the go). On a difference it refuses with `the interpreter changed since the preview: re-run the preview, nothing was lost yet`, followed by the names of the fields that differ. `inspect`, `present` and `abandon` do not compare, so a drifted transaction can still be read and withdrawn. The hash is the strict signal: a patch-version upgrade replaces the file and is caught like any other change. A packet or record made before the pin existed carries none and is not compared. A tool run outside a transaction needs only the version check.

### The adoption helper

`governance/tools/adopt.py` (implementation in `governance/tools/support/adoption.py`, registered GATED in the guard) is run once in a new repository made from Comitas, after `git init -b main` and `git add -A` and before the first commit ([G053](DECISIONS.md#g053---a-new-project-runs-one-adoption-helper-and-its-first-coordinator-claims-the-role-by-command-2026-10-20-accepted)):

```sh
python -B governance/tools/adopt.py
```

It does two things and prints what it did and the next step. It sets the executable bit of every staged `*.sh` entry that is a regular file at mode `100644` with `git update-index --chmod=+x`, because `core.filemode` is false on Windows and `git add` stages a script as `100644`; it never edits `core.filemode` or any other Git configuration. It writes `project-governance/config/citations.json` with `{"version": 1, "external_repositories": ["template"]}`, or adds `template` to the labels of the file that exists (any other label and key stay; a file that does not parse, holds an unknown key or a label list of another shape is refused and left alone), and stages it with `git add`. It refuses, before changing anything, where `HEAD` exists, where nothing is staged and where the folder is not the top of a Git repository, so it never runs in Comitas or in a project that is already going. Before the first commit a second run changes nothing. The reasons are the tests `test_script_modes` and `test_cited_commits` of the conformance folder, which fail in a copy without it.

### One bootstrap pass

At transaction start, use the existing metadata helper to freeze an external document:

```sh
python -B governance/tools/commit_metadata.py --transaction 'refs/heads/tx/<mission-id>' --output '../_review/<mission-id>/worker-context.json' --runtime '../_review/<mission-id>/session.json' --launcher '../_review/<mission-id>/launcher.json'
```

Both input files are optional, explicitly named adapter inputs, supplied from trusted execution/session metadata and known launcher/config values respectively. Each accepts only `provider`, `product`, `model`, `configuration` and `isAI`; omitted/null fields are unknown. Model is exact exposed text; configuration is provider-defined text (not necessarily reasoning). The one named environment variable `WORKER_CONTEXT` accepts the same JSON shape as a lower-priority launcher input. There is no environment enumeration, automatic provider command, filesystem search or log reader. A host adapter may supply one lightweight callable probe to `WorkerBootstrap.resolve`; it is called at most once only for missing product/model/configuration with a known provider. No probe is shipped without a proven direct interface. Inputs are assertions of trusted provenance, not provider authentication.

First non-null values win per field; lower-priority sources cannot replace known values. Conflicting provider/product evidence fails rather than mixing environments. The result retains provider/product/model/configuration, per-field provenance, explicit unknowns, identity and full transaction branch. The human projection joins known provider/product as identity and known model/configuration inside brackets; unknown configuration is never guessed. Completely unavailable identity projects `Unknown worker`, with null worker kind. Exact text is never normalized into an OpenAI vocabulary. Repeat bootstrap with the same output/branch reads only the frozen document, even if input files/environment changed; a different branch fails. Treat that external file as transaction-owned input, then pass it to the existing `prepare --worker-context` gate, which validates its projection/branch and seals a copy. Seal/present/approval/commit/verify do not resolve metadata again. The original three-field explicit declaration remains supported.

Codex can supply directly exposed session metadata through this adapter, but neither a thread ID nor an app's available-model list proves the active model/configuration. Claude Desktop and Claude Code use distinct `product` values through the same adapter; visible UI text alone does not establish programmatic discovery. No built-in model/configuration auto-discovery for either vendor is claimed. Supply exposed data once through the adapter or use unknown/null fallback without a lead developer prompt when governance permits.

Run these examples from the repository root, the mission workspace; `--repo .` is required. The example `../_review/<mission-id>/` folder is the mission's review folder in the [container layout](WORKTREE-WORKFLOW.md#container-layout), outside the checkout, and holds the supplied manifest and message files.

```sh
python -B governance/tools/checkpoint.py --repo . prepare --manifest '../_review/<mission-id>/scope.json' --message '../_review/<mission-id>/message.txt' --worker-context '../_review/<mission-id>/worker-context.json' --job-handle '<job-handle>' --profile auto --expected-head '<full-SHA>' --expected-branch 'refs/heads/<branch>' --delegation "<explicit selective-staging order reference>"
python -B governance/tools/checkpoint.py --repo . inspect
python -B governance/tools/checkpoint.py --repo . present
python -B governance/tools/checkpoint.py --repo . commit
python -B governance/tools/checkpoint.py --repo . verify
python -B governance/tools/checkpoint.py --repo . handoff
```

The optional `--job-handle` is the snake_case handle of the [Job](LOCAL-COORDINATION.md) being delivered, taken from the worker's brief and checked with the local job helper's own handle rule, or `epic--job` for a Job inside an Epic: two valid handles joined by exactly two hyphens, shown as given in the one Job row. It is sealed into the packet as `job_handle`, null when omitted, so the digest binds what the lead developer sees, and a bounded reconciliation carries it with the packet. Like `--session-id` it is a declaration: the tool never checks it against local records, never writes it into the commit message, and a transaction prepared again after `abandon` must repeat it.

Replace placeholders before use. `status` aliases `inspect`. Preparation alone selectively stages; it does not commit. Review the complete packet, diff/stat, checks and limitations. Normal approval is a direct lead developer Approve / Reject decision in the active task after the agent presents the sealed review and full exact message. The agent records that decision using the interface below; the lead developer runs no command and copies no transaction token. The old interactive `approve` command remains a manual recovery/debug interface, requiring the exact displayed token. It is not the normal user workflow. It authenticates the sealed prepared packet and checks repository identity, HEAD/branch, manifest, tree/index, validated working content (including policy/profile/tool), external message bytes and status before receipt recording (and before and after the legacy prompt). Environment allowlisting, Git operation and hook protections still apply. The receipt binds the complete original packet, including the worker configuration and validation evidence; approval never refreshes those facts. Prepare and commit retain strict configuration equality, so execution must return to the prepared worker environment and fails if its bound configuration or repository facts changed. The exact message is displayed as an escaped UTF-8 string, including trailing spaces, CR/LF and final-newline presence, and retained losslessly as base64 plus SHA-256. Approval of an edited message requires new preparation and checks. Commit uses Git's verbatim message mode and verifies the raw resulting commit object.

## Conversation consent interface (agent execution contract)

`present` returns the complete packet, escaped full exact message, transaction identity, complete prepared digest and a vendor-neutral `approval_request`: the same identity and digest, `controls` (`Approve` -> `approve`, `Reject` -> `reject`) and `text_tokens` (`APPROVE` -> `approve`, `REJECT` -> `reject`). The agent presents manifest/diff, evidence/limitations and the entire exact message, retaining that identity internally. Only a subsequent direct user decision on that review may authorize it. The initial work order does not approve an unseen seal.

A host adapter renders `controls` through the execution host's own explicit selectable-action mechanism when one is exposed, and otherwise asks for a text token. It never fabricates a selection, adds prose options or shows an Approve control whose result the tool would reject. The agent writes an external UTF-8 JSON decision input, then invokes this internal command:

```sh
python -B governance/tools/checkpoint.py --repo . approve-consent --consent '../_review/<mission-id>/decision.json'
```

The input has exactly `source` (`active-task-user`), `conversation_id`, `user_message_id` (a traceable active-task turn or control-event reference), `channel`, `response`, `decision` (`approve` or `reject`), `transaction_id` and `prepared_sha256` (retained from `present`). `channel` is `interactive-control` when the answer arrived through the host's selectable decision interface (a selected control, or text entered into that same interface when the host reports both alike), or `text-token` for an ordinary active-task reply; `response` is the exact label, value or reply the host returned, unedited. Tooling rejects an undeclared channel, then maps `response` to a decision and requires the declared `decision` to equal the mapped value. `Reject`, `REJECT` and `reject` map to `reject` by an exact lookup that ignores only surrounding whitespace. Every approving response, `Approve`, `APPROVE` and `approve` among them, goes to the [approval-word matcher](#approval-words), which owns that rule; anything else is refused, with no prose recognition. The channel is recorded provenance and never alters the authorization result: a selected Approve and a typed `APPROVE` or `Approve` produce the identical machine decision ([G018 decision-channel equivalence](DECISIONS.md#g018-decision-channel-equivalence-2026-10-05)). Tooling then rechecks the current seal and prepared facts. `approve` atomically records a `approver-decision-v1` receipt; `reject` records nothing, withdraws a recorded approval for that seal and exits nonzero. Commit/verification accept only an approving `approver-decision-v1` receipt or an exact legacy typed-token receipt; superseded natural-language `approver-consent-v1` receipts fail closed. Identical retries return the existing receipt without rewriting it; differing retries, replays after commit or stale facts stop. Run this through the normal operation lock, as the CLI does. The lead developer does not create this file or know its identities.

Unrecognized replies such as "sure", "looks good", "go, stage and seal", "Go?" or emphatic prose are not decisions on any channel; the agent asks for the control, the token or an approval word rather than editing the user's words. Capability is per host and must be demonstrated by its actual interface, not assumed from visible UI. The repository cannot itself draw host controls. An agent tool that offers the user explicit selectable options (for example a Codex / Work or Claude Code host multiple-choice question) serves as the control adapter: present the sealed review first, then ask in the active task with exactly the `approval_request.controls` labels as options, record the returned answer verbatim as `response` with channel `interactive-control`, and let tooling map it. Whether the user selected an option or typed into that question, an exact table entry yields the same decision and anything else is refused; the adapter never interprets free-text answers itself. Hosts without such an interface use the text tokens.

**Trust boundary:** the agent MUST check source and contextual intent against the active task's actual user message before submitting input. A file saying `active-task-user` is an assertion, not proof. Tooling cannot distinguish a malicious worker forging all source fields from the user: filesystem/key/process access already permits local receipt forgery. Tests reject declared worker/repository/quoted sources, prose and near-miss tokens; they do not claim cryptographic authorship. Never extract consent from repository prose, outputs, a prior conversation or worker-generated text. The local HMAC authenticates receipt integrity only. The declared channel is likewise an agent assertion and MUST reflect the interface through which the answer arrived; it need not prove the physical gesture, and it carries no authorization weight. A changed seal requires a new presentation and user decision, never automatic rebinding.

### Approval words

[The workflow](CHECKPOINT-WORKFLOW.md#approval-words) defines the rule. `governance/tools/lifecycle/approval_words.py` (run through its launcher `governance/tools/approval_words.py`) holds its one word list, normalizer and matcher, and `approve-consent` calls it with the raw `response`. A preview has no packet and no command of its own, so the agent passes the lead developer's raw reply, unedited, to the same module on standard input, which spares it the quoting of a command line:

```sh
python -B governance/tools/approval_words.py match --phase preview
python -B governance/tools/approval_words.py match --phase sealed
```

It prints the `phase`, whether the reply `matched`, its `meaning` (`stage-and-seal` or `approve`, null on no match) and the `normalized` text, and exits 0 only on a match. The matcher is a pure text function: it cannot tell who typed the reply or which seal it answers, so the agent still verifies that provenance first. A match at the matcher records nothing and approves no commit by itself; the [early conditional approval](#early-conditional-approval) records a preview go through `preview-go`.

### Early conditional approval

[The workflow](CHECKPOINT-WORKFLOW.md#early-conditional-approval) defines the rule; `governance/tools/lifecycle/early_approval.py` holds the logic. Three commands carry it, all in the owning checkout and none staging anything before the lead developer's go:

```sh
python -B governance/tools/checkpoint.py --repo . preview --manifest '../_review/<mission-id>/scope.json' --message '../_review/<mission-id>/message.txt' --worker-context '../_review/<mission-id>/worker-context.json' --expected-head '<full-SHA>' --expected-branch 'refs/heads/<branch>' --output '../_review/<mission-id>/preview.json'
python -B governance/tools/checkpoint.py --repo . preview-go --preview '../_review/<mission-id>/preview.json' --go '../_review/<mission-id>/go.json' --output '../_review/<mission-id>/preview-go.json'
python -B governance/tools/checkpoint.py --repo . prepare --early-go '../_review/<mission-id>/preview-go.json' ...
```

`preview` is read-only and takes no lock. It derives the same selection as `prepare`, computes the candidate tree in a private temporary index, and writes an authenticated record of the repository, branch, parent, tree, manifest, message SHA-256, check-list digest, switch state, eligibility and the reasons when it is not eligible. The record is unchanged by what follows. The command also renders the preview as one Markdown block with `governance/tools/lifecycle/review_render.py` (`render_preview`), prints it to standard output and writes it as `preview.md` beside the record (the output name with the suffix `.md`; an output name that already ends in `.md` is refused). The block holds the identity table (Job, workspace folder, branch, short parent and tree ids, preview id, reach), the manifest with each path's class, subclass, effective sensitivity (both rows when the candidate's table differs from HEAD), flags and change size, the derived checks with the estimate and its basis when `timing_record` is on, the limits, the full draft message once as written and once escaped, the eligibility verdict with the tool's reasons, an empty `Review focus` slot and the go line: for an eligible manifest a go approves this exact candidate (tree id) if every check passes and any difference or failure returns to the sealed review, and for any other the go only stages and seals. As with the [sealed review](#sealed-review), the worker presents the block verbatim and adds only its own `Review focus`; a summary instead of the block is a defect. The carry notices of [the carry](#the-carry) and [the go carry](#the-go-carry) do not re-render a preview: they name the moved ids and the proofs, and the manifest and message are byte for byte the ones the lead developer saw.

`preview-go` takes the agent's recording of the lead developer's reply, with the same shape as the sealed decision plus `preview_id` and `preview_sha256`, which the rendered preview block prints under `Go file values` and the go file copies unchanged (the worker computes nothing): `source` (`active-task-user`), `conversation_id`, `user_message_id`, `channel`, `response`. The tool passes the raw `response` to the [approval-word matcher](#approval-words) with phase `preview`, refuses an ineligible or edited preview, a switch that reads off, a moved HEAD and working content whose tree differs from the preview, and writes the authenticated go. Like the sealed decision, the reference is the agent's assertion and the tool cannot authenticate who typed it.

`prepare --early-go` records the go in the packet, counts the attempt in an authenticated scratch record and runs every check. When sealing finishes it compares the sealed parent, tree, manifest, message SHA-256 and check-list digest with the preview, recomputes eligibility from the sealed classification at the reach the switch reads, requires every check to have passed and the reach not to read off, and then writes a `approver-preview-go-v1` receipt bound to the complete prepared digest and moves the packet to `approved`. Otherwise the packet stays `prepared` and `early_approval` records why; `present` shows that section and the sealed Approve decides. A go that cannot be used (altered, another checkout, another parent, used or past its third attempt) never stops the prepare. `commit` accepts the receipt like any other approval, reads the switch again first, and marks the go used.

`finish` writes `landing.json`, authenticated and kept in scratch after the packets are cleared, so that the landing notice and the integration guard can read them. For every approved commit of the branch (the runtime commit of a continuity pair included) it also keeps an `approvals` entry: the diff the lead developer approved, compressed and whole, with its patch id, the exact message digest, the manifest, the seal digest and the digest of the sealed selection, which is what [the carry](#diff-bound-approval) is later checked against. An entry that cannot be built is named in `approvals_error` and never stops the lifecycle; that commit simply has nothing to carry. `worktree.py integrate` reads the switch from main's tip again and refuses a tip whose landing record says it was early-approved when the switch reads off; the seal is then redone. `python -B governance/tools/checkpoint.py --repo . landing` prints the notice, rendered by `governance/tools/lifecycle/review_render.py`: the commit, subject, parent, tree, how it was approved, whether main now holds it, the checks passed, the manifest with each path's class and size, and the revert command. It never depends on the switch. The record goes with the worktree when it is removed.

### Feature switches

`project-governance/config/checkpoint-features.toml` is the project's file: the framework ships no copy, Comitas ships it as the starter a new project copies and then owns, and an upgrade never touches it. It holds one key per feature, named like its Job, with a comment above it saying what it does and how to turn it off. The framework's code supplies the fallback of every key: a key the file leaves out, a file that is missing and a file that does not parse all mean the feature is off. The tool reads it with `tomllib` from main's current tip, never from a working tree. For the early conditional approval the key is `early_approval_reach`, a string: `"off"` never carries a go, `"low"` carries one only when every manifest path has low [approval sensitivity](ARTIFACT-CLASSIFICATION.md#approval-sensitive-paths) (the hyphen in the column), and `"medium"` also carries `medium` paths. A `high` path (the approval machinery) and a path with no row never carry a go whatever the reach, a runtime-boundary path is judged like any other (see [the runtime boundary](#diff-bound-approval)), and each path counts as the higher of its row at HEAD and its row in the candidate's own table ([sensitivity of a path](#sensitivity-of-a-path)). Only the exact strings `low` and `medium` are on; `high`, a missing key or file, any other value or type, an invalid file or a duplicate key is off, and off means the sealed Approve. The tool reads the reach at the preview, at the go and when sealing, records the reach it sealed at in the packet, and reads it again before the commit, where a reach that is now off or no longer covers every sealed path stops the early approval and the seal is redone; before integration it requires only that the reach is not off. The [test runner](#test-runner) reads two more keys from the same file through the same reader, and the [carry of an approval](#diff-bound-approval) and [of a go](#the-go-carry) read `diff_bound_approval`, a boolean of which only `true` is on: a missing key, any other value, an unreadable or invalid file or a duplicate key is off, and off keeps the fresh Approve, or the fresh preview and go, for a moved base. Turning a feature off is the lead developer's manual commit in the main checkout, and turning it on again takes the sealed Approve, because the file is of `high` approval sensitivity. The recipe:

```sh
# in the main checkout, with nothing else staged
# edit project-governance/config/checkpoint-features.toml: early_approval_reach = "off" (or parallel_tests = false, or diff_bound_approval = false)
git add -- project-governance/config/checkpoint-features.toml
git commit -F message.txt
```

with a message in the repository shape, the one file named in a `## Checkpoint` bullet and these final trailers: `Class: tooling`, `Subclass: checkpoint` and the `Worker:` line. The switch then reads off for every new transaction, and a transaction already in flight stops at its next read; its main is stale after the flip, so it is prepared again from the new main.

### Diff-bound approval

[G018 diff-bound approval extension](DECISIONS.md#g018-diff-bound-approval-extension-2026-10-14) records the design below. **Status.** Implemented: the `medium` reach of `early_approval_reach`, the [sensitivity of a path](#sensitivity-of-a-path) rule and, since 2026-10-14 (slice 1), [the carry](#the-carry) of a committed, approved branch with its key `diff_bound_approval`, and, since 2026-10-14 (slice 2), [the go carry](#the-go-carry) of a go given at a preview or at a staged transaction, under the same key, with `worktree.py reconcile` no longer refusing a transaction that adds a folder.

**Principle.** The lead developer's go or Approve binds to the diff they saw. Any mechanical re-derivation that yields the same diff with the checks passing keeps it. The early approval carries that binding across the prepare step; the carry carries it across a moved base. Evidence is mechanical checks, and the checks always run again on the tree that lands, so nothing is replayed.

**Keys** of [the feature file](#feature-switches). `early_approval_reach` is `"off"`, `"low"` or `"medium"`; `"high"` is not a reach, and a missing key, an unknown value or an unreadable file means `off`, so every failure keeps the sealed Approve. `diff_bound_approval` is a boolean committed `true`; only the boolean `true` enables the carry, and anything else is off, so a moved base takes a fresh Approve. Turning either off is the lead developer's manual commit, and turning one on takes the sealed Approve, because the file is `high`.

**Sensitivity levels.** The Approval-sensitivity column of the [artifact classification table](ARTIFACT-CLASSIFICATION.md#approval-sensitive-paths) grades each path: `-` is low, `medium` marks the governance documents, the table and the tests that pin the machinery, and `high` marks the approval machinery itself, an explicit list in that table, which never carries a go or a carry whatever the keys say. The list is not repeated here, and the tool never guesses it.

#### Sensitivity of a path

A path counts as the higher of its row in the table at HEAD and its row in the candidate's own table (low, then medium, then high; each table is the union of the framework's and the [project's](#the-project-overlay)), so no path is judged by a table its own transaction wrote. The rule is a pure function of the manifest and the two table texts, implemented as `Table.sensitivity` in `governance/tools/continuity/artifact_classification.py`, with no heuristic or similarity threshold.

| Path in the manifest | Counts as |
| --- | --- |
| Modified (a row at HEAD) | the higher of the HEAD row and the candidate row |
| Deleted (its row moved to Historical paths or gone) | its HEAD row |
| New (no row of its own at HEAD) | the higher of the row that encloses it at HEAD and the candidate's row, so a new file is never declared lower than its area |
| No row at HEAD and no enclosing row, a `blocked` profile on either side, or a HEAD table that cannot be read | `high` |
| On the runtime continuity boundary | graded like any other path by the rows above; whether it is on the boundary is judged by the higher-of rule too, see below |

A rename is a deletion plus a new path, so renaming a `high` file puts a `high` path in the manifest. The preview, the go and the sealed packet apply the same function: each sealed entry records the HEAD level, the candidate level and the effective one, an entry without the HEAD level is refused, and the review flags a row the candidate raised (`sensitivity-raised`) or tried to lower (`sensitivity-lowering-ignored`).

**Gates of the carry.** Every gate must hold, and each failure is safe because it returns to today's fresh Approve. The switch `diff_bound_approval` is true. `git merge-tree` of the candidate onto the new main is clean, so a shared file is a notice and not a gate. The carried diff equals the approved diff by `git patch-id --stable` and by bytes, with the message and trailers unchanged, modulo the id map below. The selection re-derived for the candidate on the new main (class, profile, checks, sensitivity, early-go eligibility) equals the sealed selection. Every selected check runs again on the carried tree. A notice, with no click, shows the old and new ids, the old seal, the old and new parent, the upstream range, the proofs, the results, and the files that both the candidate and the upstream range touched. The landing record holds an authenticated audit of all of it. [The next section](#the-carry) says how each gate is evaluated and what it says when it refuses.

**All classes.** The mechanism applies to every class, runtime included, under the same gates and the kill switch.

**Continuity pair.** A runtime commit R and its continuity records commit C stay two transactions, each with its own Approve, in one worktree and branch. Each commit of the branch is carried in order with an id map of the predecessors already carried (old id, old tree, old parent to new): empty for R, and for C the check is that the carried diff equals the approved diff after the map is applied, because the records cite R's id, tree and parent. If the substitution does not account for the whole difference, C takes a fresh Approve. The follow-up-pending obligation is carried with R and re-pointed to R', the old record kept as audit.

**Repeated carries.** A branch may be carried again, and each carry is verified against the originally approved diff, never against a chained patch-id, and recorded.

**Slices.** Slice 1 carries committed, approved candidates, single or in a chain, of any class, with the id map, and is implemented. Slice 2, implemented 2026-10-14, carries previews and the staging go, so a moved base neither voids the go nor makes the worker recreate its worktree, including transactions that add a folder; see [the go carry](#the-go-carry).

**The runtime boundary.** Decided 2026-10-14: the reaches also cover manifests on the runtime continuity boundary (the table's runtime Boundary column), under the same gates and the kill switch. A runtime commit's continuity records commit keeps its own sealed Approve, and the runtime checks run again on the sealed tree. Implemented the same day: `governance/tools/lifecycle/early_approval.py` no longer refuses such a manifest, so the preview, the go and the sealed check judge its paths by sensitivity alone, and the follow-up of a runtime commit is unchanged. The Boundary column takes the same higher-of rule as the sensitivity: a path is on the runtime boundary when it is on it in the table at HEAD or in the candidate's table (`Checkpoint.in_runtime`), so a candidate that drops a Boundary cell from its own table still gets the runtime gates, the runtime flag and the records follow-up. `show_classification.py` reads the table at HEAD and prints each path's effective sensitivity beside its row.

**Honest limits.** The id substitution is only as good as the records citing ids in the recognised forms; anything else takes a fresh Approve. Re-run checks catch semantic breakage only as well as the tests do. A same-file overlap is a notice, not proof of independence. The judge of the early go is still the table: a wrongly graded row is wrong at every reach. The limits of the carry itself are listed with it, below.

#### The carry

Slice 1, implemented 2026-10-14. One explicit command, run from the primary checkout through the launcher like `integrate`, with the committed reviewed tooling:

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' carry --path '<mission-checkout>' --owner '<mission-id>' --expected-main '<full-main-SHA>' --expected-tip '<full-branch-tip-SHA>' --job-handle '<job-handle>'
```

It applies to a branch that is finished (its checkpoint lifecycle is idle, so a runtime commit's continuity records are already committed), committed and approved by this tool, when main is not an ancestor of its tip. It is not a step inside `integrate`: the proof runs every selected check again, which takes as long as a seal, and a lifecycle lock held that long would freeze every other mission. `integrate` keeps refusing a stale branch, and its refusal says whether the carry is on. After a carry the usual guarded `integrate` of the new tip follows, which reads the switch again; nothing is pushed.

**How it proves.** Nothing is moved until every gate holds for every commit of the branch, taken in order. For each commit it builds the carried commit as unreferenced objects: `git merge-tree --write-tree` of the commit onto the new parent with its old parent as the base, the ids of the commits carried before it replaced in the files this commit changed, and `git commit-tree` with the original author, committer, dates and message bytes, so the same inputs always give the same commit. It then compares, derives and re-runs in a disposable shared clone, through the checkpoint tool itself (`derive_selection`, then `prepare`, which runs the sealed checks), so the owned worktree is not touched. Only then does one short step under the lifecycle lock read everything again (main and the tip unchanged, the switch still true, the landing record unchanged, the shared refs and configuration unchanged), write the audit to the landing record, and move the owned branch and its files to the new tip with `read-tree -m -u` and a compare-and-swap `update-ref`, the pattern of `reconcile`. A failure at any point before it changes nothing; a failure inside it restores the landing record and the index.

**The gates and what they say.** Every refusal reads `Carry refused at the <gate> gate (commit <short id>): <detail>. Nothing was moved; a fresh Approve on a new reconciliation mission is needed.` and the old rule applies.

| Gate | What must hold | Detail text on refusal |
| --- | --- | --- |
| `switch` | `diff_bound_approval` is the boolean true on main's tip, read when the carry starts, again before it moves and at integration | `<diff_bound_approval is not the boolean true, or the feature file on main is missing, unreadable or invalid> on main; the carry is off` |
| `record` | The branch is a straight line of single-parent commits from its merge base; the authenticated landing record has, for every commit, an entry with the approved diff and the sealed selection that matches the commit's parent, tree, message and branch | `the branch is not a straight line ...`; `the worktree has no landing record ...`; `no approval record with a sealed selection and the approved diff; it was approved before the carry existed or not by this tool`; `the approval record does not describe this commit (parent, tree, message or branch)` |
| `merge-tree` | The commit merges cleanly onto the new parent; a file that both sides touched is a notice and not a gate | `the commit does not merge cleanly onto the new base: <conflicting files>` |
| `diff` | The carried diff equals the originally approved diff after the id map: the same `git patch-id --stable`, the same bytes once hunk headers and blob ids are removed, and the same paths as the approved manifest | `the carried diff differs from the approved diff (patch id <a> against <b>, <n> against <m> bytes, first difference: <line>)`; `the carried commit changes other paths than the approved manifest` |
| `message` | The carried message, trailers included, is byte for byte the approved message | `the carried message differs from the approved message or its trailers` |
| `selection` | The selection derived for the carried candidate on the new base (class, profile, checks, sensitivity under the higher-of rule, runtime flag, policy) has the sealed selection's digest. It fails closed: a classification table at the new parent that cannot be read refuses, where the early approval's `in_runtime` falls back to the candidate's table | `the selection derived on the new base (class, profile, checks, sensitivity or policy) differs from the sealed one (<a> against <b>)`; `the classification table at the new parent cannot be read`; `the selection cannot be derived on the new base: <error>` |
| `checks` | Every selected check passes again on the carried tree, runtime gates included; nothing is replayed | `a selected check failed on the carried tree: <check ids>` |

Two refusals are not gates: `Main is already an ancestor of the source tip; there is nothing to carry, integrate it`, and the ordinary lifecycle guards (clean main and mission checkout, idle scratch, exact tips, hooks, ownership, shared refs), which stop the command with their usual messages.

**The id map.** Commits are carried in order. After each, the map records the old commit id, tree and parent of the commit just carried and the new ones, in full and in every short form of at least seven hex digits that stands alone (a longer or shorter run of hex digits is another word and is left). For the next commit the map is applied twice: to the files it changed in the carried tree, where records that cite the earlier commit are rewritten (a runtime commit's continuity records cite its id, tree and parent), and to the approved diff before the comparison. So `diff` compares what the lead developer approved, with the new ids, against what was carried, and anything else in the difference refuses. The map is empty for the first commit. Because each carry is compared with the originally approved diff, kept whole in the landing record, a branch carried a second time is checked against the original approval and never against the first carry's copy.

**The audit and the notice.** The landing record, authenticated with the worktree's receipt key and kept in scratch beside the receipt key until the worktree is removed, gains `approval_path: "carried"` (with `original_approval_path`), the carried tip's ids, a `carried_from` audit and the carried entries in `approvals`, the old entries staying as history. The audit holds: the owner, the Job handle, the time, the key and the main commit it was read at, the old and new tip, the old and new base, the carry number, the upstream range (its commits and paths), the files both the candidate and the upstream range touched, the tooling hashes and, for each commit, the old and new commit, parent and tree, the merge tree, the approved and the carried patch id, the digest of the change, the id map, the original seal digest, the original approval path, the sealed selection digest and the result of every check. The command prints the notice rendered from it by `governance/tools/lifecycle/review_render.py`, and `checkpoint.py landing` prints the same section later. The worker pastes the notice into the Job record. No click follows: the lead developer's approval of the exact diff they saw stands, and the notice is the record. At integration the tool reads the switch again, and an approval that was an early go also needs its reach not to read off.

**Honest limits.** The id substitution is only as good as the records citing ids in the recognised forms; a form it does not recognise stays unchanged on both sides of the comparison, so it passes the diff gate and is left to the re-run `continuity` check to catch. The re-run checks catch semantic breakage only as well as the tests do, and a runtime commit's runtime gates need their environment (a container runtime, a database) or the carry refuses at `checks`. A same-file overlap is a notice, not proof of independence. All commits of a branch carry or none does: a gate that fails for one commit moves nothing, and the refusal names that commit. A branch approved before this landed has no sealed selection or approved diff in its landing record and takes the fresh Approve; the carry applies from the first transaction finished by this tool. A runtime commit whose continuity follow-up is still pending is neither carried nor integrated, so the follow-up obligation is never carried: the carry sees the pair only after both are finished. The carried commits are new objects: a worker who held the old tip must read the new one from the notice. The proof needs Git 2.40 or later (`merge-tree --write-tree --merge-base`), and it takes as long as a seal for each commit of the branch.

#### The go carry

Slice 2, implemented 2026-10-14. The lead developer's go is their judgment about a diff, and a moved main does not change that diff. One explicit command, run from the primary checkout through the launcher like `carry`, with the committed reviewed tooling:

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' carry-go --path '<mission-checkout>' --owner '<mission-id>' --expected-main '<full-main-SHA>' --go '../_review/<mission-id>/preview-go.json' --message '../_review/<mission-id>/message.txt' --worker-context '../_review/<mission-id>/worker-context.json' --output '../_review/<mission-id>/preview-go-2.json' --job-handle '<job-handle>'
```

**Where it lives.** Its own command, neither inside `reconcile` nor inside `carry`. `reconcile` carries an authenticated packet under the G031 eligibility rules, which refuse an overlap, and it leaves the transaction unapproved; `carry` works on a committed branch with a landing record. A go has neither: it is a record of the previewed facts. The command takes that record and works for both uncommitted states a go can be in. With nothing staged (a preview only), it moves the worktree. With a staged or sealed transaction prepared with that go (a packet not yet committed), it first withdraws the packet as `abandon` does, which unstages exactly the transaction's own paths and keeps the receipt key and the go-attempt record, and then moves the worktree; the worker prepares again with the carried go, and every selected check runs again, as it does at every seal. A transaction that holds the sealed Approve is not carried before it is committed, and a committed branch takes [the carry](#the-carry); `reconcile` stays as it was for the transactions it already carries.

**Gates.** Every gate must hold, each failure is safe and each refusal reads `The go was not carried at the <gate> gate: <detail>. Nothing was moved; show a fresh preview and take a fresh go (or the sealed Approve).`

| Gate | What must hold | Detail text on refusal |
| --- | --- | --- |
| `switch` | `diff_bound_approval` is the boolean true on main's tip, read when the carry starts and again before it moves | `<diff_bound_approval is not the boolean true, or the feature file on main is missing, unreadable or invalid> on main; the carry is off` |
| `record` | The go record is authentic (its authenticated envelope matches the worktree's receipt key) and is a go | `the go record is missing, altered or not a go: ...` |
| `state` | HEAD and the branch are the previewed ones; the working tree differs from HEAD only in manifest paths, a new directory included (listed file by file); the candidate tree built from the working content is the previewed tree; scratch holds only the receipt key, the lock, the go-attempt record and the packet; a packet is uncommitted, was prepared with this go and does not hold a sealed Approve | `the go belongs to another checkout`; `HEAD or the branch is not the previewed one`; `unrelated dirty state: ...`; `the working content is no longer the previewed candidate`; `the sealed transaction was not prepared with this go; ...`; `the transaction holds your sealed Approve ...` |
| `merge-tree` | `git merge-tree` of the previewed candidate onto the new main, with the previewed parent as the merge base, is clean; main descends from the previewed parent; a file both sides touched is a notice and not a gate | `the candidate does not merge cleanly onto the new main: <conflicting files>`; `main does not descend from the previewed parent` |
| `message` | The message file is byte for byte the previewed message | `the message is not the previewed message, byte for byte` |
| `diff` | The candidate's diff on the new main equals the ORIGINALLY previewed diff by `git patch-id --stable` and by bytes once hunk headers and blob ids are removed, over the same paths as the previewed manifest, and the candidate rebuilt on the new main is the merged tree | `the candidate's diff on the new main differs from the previewed diff (patch id <a> against <b>, <n> against <m> bytes, first difference: <line>)`; `the merged candidate changes other paths than the previewed manifest` |
| `selection` | The preview facts derived again on the new main, in a disposable clone, through the preview's own function (`preview_facts`), reproduce the original preview's branch, manifest, message digest, check list (ids and arguments) and per-path sensitivities. It fails closed: a classification table that cannot be read on the new main refuses | `what the new main derives differs from the previewed <facts>`; `the classification table on the new main cannot be read`; `the selection cannot be derived on the new main: <error>` |
| `eligibility` | The go is still eligible on the new main: the early approval reach read there is not `off` and covers every path, each judged by the higher of its row at HEAD and in the candidate's table, so a reach that now reads off or a path that became `high` ends the go | `the go no longer carries on the new main: <reasons>` |

Nothing is moved until every gate holds. The checks are not a gate of this command, because nothing is sealed yet: they run on the tree that lands, at the seal, as always.

**The move.** One short step under the lifecycle lock and both checkpoint locks reads everything the proof read again (main and the worktree unchanged, the switch still true, the shared refs and configuration unchanged, the packet unchanged), withdraws the packet if there is one, and moves the worktree with Git itself: the manifest paths are set back to the previewed base's bytes, `read-tree -m -u` moves the whole tree from the previewed base to the merged tree, the branch is moved to the new main by compare and swap, and the index is set to the new main, so the candidate stays uncommitted and unstaged on it. The worktree, its path, its branch and its receipt key are the same. A failure at any point puts the old base and the old candidate back from the tree object that names it, or says that it could not and names that tree.

**The carried go.** The authenticated go gains a `rebound` section holding the original preview (its facts and its diff, compressed and whole), and every move with its audit, and its `preview` is the preview derived on the new main, with a new id, parent and tree; the lead developer's reply is copied unchanged and names that preview. The old go is spent (marked used and pointing to the new one) and its attempts carry over, so the cap of three prepare attempts stays. A later move is checked against the original preview, never against the first carry's copy, so repeated moves never chain. `prepare --early-go` takes the carried go like any other, and its seal still compares the sealed parent, tree, manifest, message and check list with the carried preview and requires every check to pass.

**The audit and the notice.** The audit is inside the authenticated go: the key and the main commit it was read at, the move number, whether the go was at a preview or at a staged transaction, the old and new parent and tree, the old, new and original preview ids, the upstream range (its commits and paths), the files both the candidate and the upstream range touched, the patch id, the original patch id and the digest of the change, the selection facts (check digest, sensitivities, reach, eligibility) and the tooling hashes. The command prints the notice rendered from it by `governance/tools/lifecycle/review_render.py`; the worker pastes it into the Job record. No click follows. The landing notice does not repeat it.

**Folders.** `reconcile` refused a transaction that adds a folder because it judged unrelated dirty state from the status taken before staging, where Git lists a brand-new directory as one untracked entry that no manifest path equals; it now judges the status taken after staging, where the files are listed one by one, and a path that is really unrelated still stops it. The go carry reads the working tree file by file, so a new directory was never a problem for it.

**Honest limits.** The checks run again at the seal, so a go that survives a move still costs the whole seal. A staged transaction is prepared again, not rewritten in place. The move rewrites the manifest files through Git's checkout, so their line endings follow the checkout rules, while the candidate tree stays the one the gates proved. A same-file overlap is a notice, not proof of independence. The audit does not reach the landing record. A sealed Approve is carried only after its commit, by [the carry](#the-carry).

### Test runner

`governance/tools/run_tests.py` runs the tests of a check. A check stays one command, `python -B governance/tools/run_tests.py -s <folder> -p '<pattern>' -v [-k <filter>]`, which exits 0 only when every test passes, so the checkpoint tool still runs its checks one after another and decides by exit code alone. The runner discovers the tests as `unittest discover -s <folder> -p '<pattern>'` does (a folder inside a package, such as `governance/tests`, is discovered from the folder above its outermost package, as `-t` would), and finding none is a failure. Every policy command that ran a test suite through `unittest discover` calls it; the runtime gates (builds, containers, databases) and `mission-control-ui` are not suites of this kind and are unchanged.

The mode comes from two keys of the [feature file](#feature-switches), read from main's current tip with the reader the early approval uses, and never from the environment, because the tool binds the environment into its evidence. `parallel_tests` is a boolean: `true` runs the tests in parallel, and `false`, a missing key, any other value or an unreadable or invalid file runs them sequentially through unittest itself. `test_workers` is a whole number: `0`, also the value when the key is missing, means one worker process per core, a positive number caps the workers, and any other value fails safe to sequential. Turning the switch off is the lead developer's manual commit of that one file, as for the early approval; turning it on again takes the sealed Approve. The first line the runner prints names the mode: parallel with the worker count, or sequential and why, so the sealed evidence says which way the tests ran.

In parallel mode the discovering process cuts the tests into units and feeds them to a dynamic queue served by the worker processes, so a free worker always takes the next unit. A unit is one test id, except that a class with `setUpClass` or `tearDownClass`, and a module with `setUpModule`, `tearDownModule` or `load_tests`, is one unit, so a fixture runs once per unit. Each worker has its own temporary folder under one short folder per run, inside `tmp`, a sibling of the main checkout's folder (`<main checkout root>/../tmp`, found as the parent of Git's common directory, so a transaction worktree and a clone use the same one; the short names keep clear of Windows path limits, and `TMP` and `TEMP` do not move it). The runner creates `tmp` when it is missing, removes only the per-run folder it made and never touches other folders in `tmp`, so a killed run leaves its folder there for the developer to delete. When `tmp` cannot be created, the runner says so in its output and falls back to the earlier location (the drive root on Windows, the default temporary folder elsewhere), and its output is captured per unit and printed together, never interleaved. The run lists the tests per module, names every test that did not pass with its captured output, and prints the totals in unittest's form. A test that was discovered but did not report, for example because its worker stopped, counts as an error. `--shuffle <seed>` shuffles the units and the order inside a unit, for the periodic independence runs; the tests are independent by rule (each owns its temporary folder, writes nothing to the real repository, binds port 0 and changes no shared environment), and a shuffled parallel run that differs from a sequential run is a defect of a test.

The replay rules are unchanged: `replayable` recognizes a replayable check by its pattern and filter in either command form, so a packet sealed before the runner keeps its unittest commands and a new one replays the same checks.

### Sealed review

Two reviews happen in a governed mission, and the names keep them apart. The preview comes before anything is staged: the manifest, the derived checks and the draft message, with no packet yet; the lead developer's go starts staging and sealing. The sealed review comes after `prepare` has staged the paths and run every check, when the packet is `prepared`; the lead developer's Approve or Reject applies to it. The workflow says [when a preview is required and how it is waived](CHECKPOINT-WORKFLOW.md#review-before-the-seal).

`present` also returns a `review`: deterministic Markdown rendered by `governance/tools/lifecycle/review_render.py` only from the sealed packet, and `present --text` prints just that text. The layout is fixed and pinned by tests: an identity table (the Job handle, shown as a hyphen when none was declared, then worktree, branch, parent, tree, worker, transaction, state and the full digest); the manifest with each path's class, subclass labels, flags (`runtime`, `frozen`, `bound`, and `broad` for a path whose checks fell back to the whole envelope) and change size; the checks with result, seconds, the expected time from the estimate sealed when `prepare` began, whether each ran or was reused and any slower or faster flag; the limits; the state of the working tree outside the manifest; the exact commit message, once as written and once escaped so trailing spaces and line endings show; an Early approval section when a go was supplied and did not apply; and the decision, which names the Approve and Reject controls and the accepted words in lowercase bold: **go**, **approve**, **approved**, **proceed**, **do it** and **reject**. The estimate is sealed into the packet as `timing_estimate` before the checks begin, so this run's own times never contaminate it. The review is a view and is not sealed, so it can never change the digest, and a rendering fault returns `review_error` without blocking a decision.

The agent shows the rendered text verbatim and adds only its own `Review focus`, which is judgment and cannot be generated and which stays out of the commit message.

## State and evidence

The state machine is `preparing -> prepared -> approved -> committing -> commit-attempted -> verified` or `follow-up-pending`; validation-only preparation inserts `validated` before `prepared`. Failure states retain evidence and staging: `prepare-failed` and `verification-blocked`. A transaction that has not begun to commit (`preparing`, `prepare-failed`, `validated`, `prepared` or `approved`) can be withdrawn with `abandon`, described below. A failed commit remains `commit-attempted`, never automatically retries, and does not imply successful verification. Inspect reports failures; stale validated/prepared/approved state exits nonzero. Commit accepts only a sealed approved state.

`python -B governance/tools/checkpoint.py --repo . abandon [--reason '<note>']` withdraws such a transaction without changing any content. It authenticates the sealed packet, requires HEAD and the branch to still equal the sealed parent, and refuses if anything outside the manifest is staged, so it can never clear unrelated staging. Then it unstages exactly the transaction's own staged paths and clears the scratch slot. Working bytes, refs and every unrelated index entry stay as they were, no suites run, and a repeat after an interruption finishes the job. The authenticated go-attempt record `early-approval.json` and the receipt key stay in scratch on purpose, so that a new prepare still counts the attempts of a go; the guarded [worktree removal](WORKTREE-WORKFLOW.md#remove-only-the-owned-completed-mission) accepts exactly that record, the key, the lock and the landing record beside an otherwise idle store, so an owner can remove its own worktree and branch after an abandon. Nothing is archived: scratch is disposable, a withdrawn seal can never be reused or restored, and the command's output (transaction, state, whether an approval was withdrawn, the paths and the optional note) is the whole record. A transaction in `committing`, `commit-attempted`, `verified` or `follow-up-pending` is refused: use `verify` or `finish`.

The checkpoint store (called scratch in this document) is the `governance/` folder of the checkout's own Git directory: `<primary>/.git/governance/` for the primary checkout and `<primary>/.git/worktrees/<name>/governance/` for a linked worktree ([G046](DECISIONS.md#g046---the-checkpoint-store-lives-in-the-worktrees-git-directory-2026-10-18-accepted)). It holds `receipt.key`, `transaction.json`, `pending.json`, `handoff.json`, `cleanup.json`, `landing.json`, `early-approval.json`, `operation.lock` and the `stale-<hash>.json` files the guard writes when it repairs a stale packet. It dies with its worktree, because Git deletes the worktree's Git directory with the worktree, and it is outside the working tree, so `git clean -x` cannot reach it and no editor or search indexes it. `governance/tools/support/local_state.py` names the folder and no other file spells it; the name collides with nothing Git or the tools keep in a Git directory (`HEAD`, `index`, `config`, `hooks`, `info`, `logs`, `objects`, `refs`, `worktrees`, `locked`, `gitdir`, `commondir` and the markers `quiet_operation` reads: `MERGE_HEAD`, `CHERRY_PICK_HEAD`, `REVERT_HEAD`, `rebase-merge`, `rebase-apply`, `index.lock`). Construction rejects a store that is a link or a junction and needs no ignore rule. **The receipt key is never made again silently:** it is made at the first use of an empty store, and a store that holds records but no key stops the tool with one message that names the store and says the key was deleted or the store was damaged; `key` stops with a message of its own when it is asked for a key that is missing. The key is created with mode 0600, is never printed or logged and is never copied into a packet. JSON writes use temporary files plus atomic replacement. A process lock excludes other tool operations; a crash may leave it behind. A lock left behind carries no owner, so its presence proves nothing. The checkpoint operation lock (`operation.lock` in that folder) and the lifecycle lock are removed only with the lead developer's word, after establishing that no process owns them (the running processes and their command lines; a container runtime is not a checkpoint process); see [H3](WORKER-HAZARDS.md#h3-stale-lock-files). The coordination writer lock, the helper's short exclusive lock on Job records, follows [local coordination](LOCAL-COORDINATION.md#updates-handoff-and-disposal) instead: the Coordinator may remove it once it has confirmed that its writer stopped, and tells the lead developer afterwards. Do not run concurrent editors, Git writers or validators that mutate inputs during a transaction: the lock cannot constrain unrelated processes, and final checks are not an operating-system-wide atomic lock.

Each packet is authenticated with HMAC-SHA-256 using a randomly generated local 32-byte key. Approval additionally binds a digest of the complete prepared packet and either the asserted approving lead developer decision or the legacy exact typed confirmation. Bound facts include transaction/repository identity, the interpreter fingerprint ([runtime guard](#runtime-guard)), branch/parent, manifest, staged tree/index entries, exact message, checks and timing/output, policy/profile, Git configuration and hashes of tracked plus nonignored nontransient untracked working content. Changed facts reject execution. This is a local integrity receipt, not a digital signature or proof of who typed: an actor with access to the key, process or tool can forge it. Protect the metadata directory with the user's OS account permissions; do not share its key or present HMAC as an adversarial security boundary.

`checkpoint-policy.json` and `checkpoint-profiles.json` version 4 are reviewed executable configuration, not a sandbox. They name no path: the [artifact classification table](ARTIFACT-CLASSIFICATION.md) gives each path its change class independently of its validation profile, its boundary, whether its bytes are sealed and the invariants a change can affect. The most specific row wins, every manifest path must resolve to a row, and a blocked or unknown path fails before staging. New component or shared infrastructure paths require a reviewed table row; there is no permissive fallback.

Use `--profile auto`. The derived name is the sorted `+`-joined union of affected profiles, dropping `record-only` when another profile already provides continuity. An explicit name is only an assertion that must equal this result. The packet retains per-path categories in `profile_data.classification`, validation profiles in `path_profiles`, the sorted `categories` and aggregate `change_classification` (`mixed` for multiple categories), commands, limitations and timings. Human Class lists are compared against the underlying `categories` set in metadata registry order, never against the internal `mixed` aggregate. Every declared subclass must be eligible under at least one declared class. A Subclass is a label and never selects a check: the trailer must equal the Subclass labels the table gives the manifest paths, restricted to those eligible under a declared class. Mixed categories can share one profile; one category can require several profiles. Neither relationship loses affected checks. All commands must exactly match policy. Only version 4 is read: it reads only the table, earlier path-list formats no longer exist, and no switch selects another. Normative docs conservatively require governance checks; unknown docs block. Adding obligations to a record path requires reviewed classification before preparation.

| Validation profile | Selected checks (in addition to staged whitespace and G018 integrity) |
| --- | --- |
| `record-only` | Unchanged continuity, including document/index and frozen evidence checks |
| `governance` | Continuity; `test_checkpoint*.py`; every `test_*.py` of `governance/tests/continuity/` and `governance/config/` (the continuity and conformance tests) |
| `tooling` | Continuity; `test_checkpoint*.py`; every `test_*.py` of `governance/tests/continuity/` and `governance/config/` (the continuity and conformance tests) |
| A runtime profile of your project | Continuity; the offline and runtime gates that component owns (`runtime_checks`), none of another component's |
| Mixed | Deduplicated union of affected profiles |
| Unknown or unsupported | Block before staging; review classification and applicable gates |

### Timing record

The tool keeps an advisory, machine-local record of how long each check takes, so a worker can say how long a seal should take and notice when one departs from its history. The `timing_record` key of `checkpoint-policy.json` configures it: `mode` (`local` or `off`), `window` (how many recent runs count, default 20), `min_samples` (runs needed before a figure is trusted, default 3), `slow_factor` and `slow_margin_seconds` (a check is slower than expected when it takes at least 1.5 times its mean and at least 10 seconds more), and `fast_fraction` with `fast_min_mean_seconds` (a check that averages 20 seconds or more and finishes in under 40 percent of its mean is faster than expected, which often means tests did not run). Absent or `off`, nothing is recorded.

Durations belong to the hardware that produced them. The record is an append-only JSON-lines file, `checkpoint-timings.jsonl`, in the `.local/timings/` folder of the primary checkout (found from any worktree through Git's common directory): every worktree shares it, no tracked path ever holds it, it cannot make a checkout dirty and it survives worktree removal. The tool creates the folder when it first appends and refuses, with a clear message, to write while `.local/` is not git-ignored (a read of a missing record simply finds no entries). A record kept by an earlier version in the Git directory (`checkpoint-timings.local.jsonl`) is not read and not moved: copy it by hand to `.local/timings/checkpoint-timings.jsonl`, or use `export` and `import`. Each entry has a `subject` (`check:<id>` today, generic so later benchmarks reuse the shape), the `metric` (seconds), the value, whether the run passed, the run identifier, a machine token (platform, CPU count and Python version) and a small context. Only checks that actually executed are recorded; reused evidence is not. Recording happens after each validation invocation (validation-only preparation or seal), whatever the outcome, and it never alters validation: if the record is unreadable or unwritable the seal still completes and the packet carries `timing_observations.unavailable`. Failed runs are recorded but never enter the statistics.

New observations keep timing schema v1 and add attribution in `context`. `run` identifies one validation attempt; `context.transaction` identifies its checkpoint transaction, so validation-only preparation and later sealing have distinct run IDs. Historical entries remain unchanged: their `run` can be the transaction ID and missing attribution remains unknown. The existing frozen `profile_data.worker_context` supplies the declared worker (or null when unavailable). Optional `prepare --session-id <id>` records a declared chat/session ID in the packet; omission is null. Neither field authenticates identity, and tooling does not discover one from caches, parent commits or timestamps.

Each newly executed observation also retains its parent, candidate tree, profile/path count, exact argv and the Python executable/version/hash, plus phase (`validation-only` or `seal-validation`). Timing is written before a final packet seal exists, including when validation fails: `context.sealed_digest` is null, rather than a claimed final seal binding. The actual candidate tree supplies the available content identity. No later attribution or seal digest is backfilled into old entries. Reused evidence creates no new timing observation. Export/import and estimates continue to accept unattributed v1 history unchanged.

Before sealing, run `python -B governance/tools/checkpoint.py --repo . estimate --manifest <scope.json>`. It is read-only, takes no lock and stages nothing, so it also works while another seal runs; `prepare` prints the same summary to stderr. The result states its basis: `measured` (every check has enough runs on this machine), `imported` (history from other hardware, only a rough guide), `partial` (some checks have no usable history, so the total is a lower bound and the gaps are named) or `none` (no history, so there is no estimate and no figure is given). Report the basis with the figure. An estimate assumes every check runs fresh. After the checks finish, departures from a check's own history are sealed into the packet as `timing_observations`, shown by `present`. They are advisory flags and never block or approve anything.

`python -B governance/tools/timing_record.py stats` shows the statistics. `export --output <file> --label <name>` writes the record to a file you choose and refuses to overwrite one; nothing is staged or committed. A person may commit an export by hand, for example as `docs/timings/<label>.jsonl`, a path Comitas's project table classifies as a record (a project adds that row to its own table to commit an export). `import --input <file>` seeds the record from an export and is idempotent. Entries from a different machine token are kept but are only ever `imported` basis.

### Artifact classification table

[Artifact classification](ARTIFACT-CLASSIFICATION.md) is the one authored table of what each path is and which validation it needs. The checkpoint, worktree, continuity and commit-metadata tools read it and no other list of paths. Every `prepare` parses the table, so a missing table or a malformed row stops preparation. It selects each manifest path's class, profile, runtime and frozen boundary and invariants from the table, and seals each path's resolved Class, Profile, Boundary, Bound, Invariants, Subclass and Reachable values with the profile as `artifact_classification`; `present` therefore shows them for review. The table is part of the sealed content, and the files it marks Bound are sealed even when they are not in the manifest. The table is the union of the framework's rows and the project's ([the project overlay](#the-project-overlay)), and the project's table, policy and profiles are sealed beside the framework's. The impact mapping keeps only the invariants, their dependency edges and command groups, and, for `governance/tools/checkpoint.py`, the reviewed symbol map in `impact.symbol_maps`; a path whose Invariants cell is `symbol-map` takes the symbol map keyed by that path.

Continuity requires every live file row to name an existing file and every Historical paths row to name an absent one, so deleting a file means moving its row in the same transaction. Historical rows reconstruct the class and subclass of old commits, for example in Mission Control. A transaction that deletes or renames away a tracked file consults its Historical row when preparing, estimating and sealing: the deleted path is validated by the profile and invariants of the row it had at HEAD, provided the working table has no live row for it, the Historical row names the same Class, and the HEAD row is live, not `blocked` and has no Boundary; it is sealed with a view marked `deleted` that takes the approval sensitivity of its HEAD row. Every other deleted path stays blocked, as do live files and malformed rows; [the table document](ARTIFACT-CLASSIFICATION.md#historical-paths) states the rule.

`python -B governance/tools/show_classification.py <path>... [--checks] [-v]` is a standalone, read-only script. It needs no transaction, takes no lock, calls no Git and writes nothing, so anyone can run it directly. For each path it prints the effective classification and where each cell came from. `--checks` adds the checks a change to the path would select, and why. `-v` adds the matching row, and its parent row for a path whose row inherits, exactly as written with their line numbers. A path no row covers prints as blocked.

### The project overlay

`governance/` is the framework and an upgrade replaces it wholesale; `project-governance/` is the project's own folder and an upgrade never touches it. Three of the framework's files have an optional counterpart there, and every tool takes the union of the two: the project's table (`project-governance/ARTIFACT-CLASSIFICATION.md`), more profiles (`project-governance/config/checkpoint-profiles.json`) and more commands, prohibited components and required checks (`project-governance/config/checkpoint-policy.json`). The loaders `load_table`, `load_profiles` and `load_policy` of `governance/tools/continuity/artifact_classification.py` read the working tree, and `table_from` reads the same files as committed at HEAD. The selection (`Selection.data`, `table`, `head_text`, `head_table` and `bound_paths`), the read-only explainer, the continuity check and the timing settings all use them, so a project row, profile or command is seen by selection, sealing, the early approval and verification exactly as a framework one is. With none of the project files present the result is the framework's alone.

**The project's rules, decisions and half of the reconstruction contract** (G050) follow the same model. `project-governance/CONSTRAINTS.md`, `project-governance/DECISIONS.md` (prefix D) and `project-governance/RATIONALE.md` are the project's optional homes for its rules, decisions and their rationale, and an absent one means none. The continuity check reads a present one as a document (its links must resolve and it must be reachable from `AGENTS.md`) and refuses a registry that holds a decision of the other prefix, G in the project's file or D in the framework's, with one message; the Mission Control generator lists the project's decisions and rationale beside the framework's under the same rule. The reconstruction contract is the framework's `governance/config/reconstruction-contract-v1.json` (version, bootstrap prompt, narrative sections, framework evidence) with the optional `project-governance/config/reconstruction-contract.json` added by `load_contract`: the project's facts, evidence and completion fact, a project fact that reuses a framework fact name refused, the evidence lists only extended, the bootstrap and the required sections the framework's alone, and without the project file the framework part stands alone. After this, `governance/config/` holds framework content only.

**Clashes are refused, never resolved.** The project's table may classify no path under `governance/` or `project-governance/`; the framework's table classifies all of both, with one row that grades the project folder `high`, because its files decide what a go may carry and a project cannot classify its own overlay. A project row for a path the framework's table also names is a duplicate. A project profile or command may not reuse a framework name. The project files may add profiles, commands, prohibited components and required checks and nothing else, so the impact mapping, the commit-subclass vocabulary and the policy keys `commit_metadata_required`, `link_retarget` and `timing_record` stay the framework's: an overlay cannot set them. A project file therefore never lowers a framework path. The [sensitivity rule](#sensitivity-of-a-path) applies to the union at HEAD and in the candidate: a project row that a candidate lowers keeps its HEAD level, and a project row it adds has no row at HEAD and counts as `high`.

**What the sealed packet binds.** The working-content snapshot (`working` in the packet) holds the hash of every tracked or new file and, by name, the framework's policy, profiles, table and driver files. It holds by name the project's three files as well, and a file that does not exist is bound as absent (a null under its name): an approval cannot survive a change to any of the six, nor the appearance of a project file that was not there at the seal. The merged policy and the selection derived from the merged profiles and table are sealed in the packet as before. A content-bound validation result also depends on every file of `project-governance/`, because the switches and the project's files change what a check does. The check of upstream changes during a reconciliation refuses a change to the project's policy or profiles as it does the framework's, and `assert_selection_current` derives the selection again from the union.

**Settings are overrides of code defaults.** The feature switches and the development log settings are not an overlay: each is one file in `project-governance/config/` with no framework copy, and the framework's code holds the fallback of every key. The switches are described under [feature switches](#feature-switches). The log settings (`devlog.json`) may be partial: a key left out takes its default (the folder `devlog`, ISO-8601 dates in UTC, a devlog kept), and a file that is missing or does not parse means the defaults, while a key that is set must hold a good value. `"enabled": false` says the project keeps no devlog: the continuity check then requires no entry beside the `implementation_checkpoint` pointer in the progress record and validates neither the log folder nor its index, the lifecycle gate and the completion check ask for no entry, and the integration guard's isolated candidate check passes on the pointer alone. Everything else the continuity check verifies, the stale pointer, the completion evidence and the frozen artifacts included, is unchanged, and with `enabled` true or absent the behavior is exactly the old one.

### Link retarget

The `link_retarget` key of `checkpoint-policy.json` lets a reviewed list of documents have their links repointed after a file move with continuity only. `documents` and `moves` (old path to new path) are repository-root-relative and sorted. Both are empty, and the mechanism is dormant, unless a cleanup is pending. A listed document may not be frozen or on the runtime boundary and needs a row in the artifact classification table.

At `prepare` a listed document qualifies only when its new text equals its HEAD text except for inline link targets, each changed target is exactly the file-relative path the mapped move implies from the document's own folder with the fragment unchanged, and no link still targets a moved path. A qualifying document is sealed as class `record` with the `record-only` profile, `artifact_classification` lists each old and new link, and the review flags the path `link-only`. Anything else keeps the document's normal classification, blocked or not: a partial retarget, an unmapped or external target, a changed reference-style or HTML link, or any other text. Continuity then proves that every new link resolves. Eligibility never lowers the frozen and runtime-boundary protections and grants no approval.

### Runtime profiles

Runtime gates belong to each component's reviewed profile: every profile that covers a runtime path declares its own non-empty `runtime_checks`, each an exact policy command, and the policy has no shared default, so no component inherits another's gates. A runtime path whose profile declares none is refused. The selector seals the union over the runtime paths actually in the manifest, so one component's gates never satisfy or burden another's. G023 replaces unrelated blanket regression requirements with the affected checks above.

Full `test_*.py` discovery remains available for justified broad audits, but no transaction automatically selects them. The mandatory continuity check is unchanged; selection does not skip G018, staged whitespace, snapshots, approval, commit verification, or guarded scratch completion. Timed command output is sealed as before.

For a verified runtime commit, the tool reruns the existing continuity checker unchanged. Only its precise stale-runtime-checkpoint failure, with passing pre-commit checks, preserved working inputs, independent document/frozen-manifest checks and completion evidence anchored by the new commit, may produce `checkpoint committed; continuity follow-up pending`. Other failures block. This state preserves the failing checker evidence and is neither continuity PASS nor lifecycle completion. Only the bounded continuity-record transaction may proceed while the record obligation remains unresolved, using `continue-records` as described below.

The deterministic `handoff.json` contains immutable result SHA, parent/tree, approved message and manifest, validation evidence, pre/post status, and follow-up obligations. It supplies data to a separately delegated fresh worker. It neither writes devlog entries nor decides their prose or whether a meaningful transition warrants one. Tooling commits never advance `implementation_checkpoint`. `verified` means the mechanical transaction passed, not that any separately required historical follow-up is complete.

### Claims and execution status

The tools declare their ref windows in a small local database, and `worktree.py execution-status` reads them next to evidence derived from Git. The [local coordination procedure](LOCAL-COORDINATION.md#execution-status) owns who reads the status and what the levels mean; this section is the implementation.

- **Store.** `governance/tools/worktrees/claims.py`, standard library `sqlite3` only. One file, `.local/claims/claims.sqlite` with its WAL files, in the primary checkout, which is the parent of the Git common directory. `/.local/` ignores it; it is local disk only, never committed or backed up, and rebuildable because it only mirrors what the derived evidence shows. The code refuses a symlinked, junctioned or non-directory `.local` or `claims` folder and a folder that Git does not ignore, creates the folder on the first write only, and opens read-only for reads, so a read creates nothing. Writes run in `BEGIN IMMEDIATE` with a 5 second busy timeout.
- **Schema version.** MAJOR.MINOR, kept in `PRAGMA user_version` as MAJOR times 1000 plus MINOR, so 1.0 is 1000. A minor adds fields: a tool with a lower minor upgrades the file additively inside one transaction, and a tool with a higher minor reads it and leaves it untouched. A different major is incompatible: the tool reports `schema_incompatible` with both versions, leaves the file alone and runs on derived evidence.
- **Tables.** `claims` holds one row per window: kind, scope (`prepare` or `lifecycle`), owner (the mission ID of the `tx/<id>` branch), Job handle, state, since time, worktree, process id and its start token, and the close time, with at most one open row per owner and scope. `events` is append-only: opened, state and closed with its reason. Levels are never stored. Schema 1.1 adds `claim_paths` (claim, path, class and the comma-joined subclasses) and a second kind of claim, `paths`, one open row per owner, which holds what the mission's preview named; a 1.0 tool never reads it and a 1.1 tool reads a 1.0 file without it. A closed claim keeps no path rows, and the append-only events add `landed`, `attention`, `cleared` and `reconciled`, which belong to no claim except the landing.
- **Hooks.** In `checkpoint.py`, `main` wraps each command in `claims.command_window`. Prepare, seal and resume open a window with the process id and start time, and on the way out keep it as `validated` or close it, by the packet state. Abandon, finish, commit and the approval decision close the owner's window. In `worktree.py`, `lifecycle_lock` declares a lifecycle window for create, reconcile, integrate and remove while it holds the lock, and the integration guard hashes `claims.py` with its other files (`claims_sha256`). Schema 1.1 adds hooks. `checkpoint.py preview`, which takes the optional `--job-handle`, writes the owner's path claims from the manifest's classification views (path, class and subclasses, a deleted path included) and replaces the owner's earlier ones; it is still read-only for the repository, and the claims database is the one thing it writes. Abandon releases the owner's path claims and writes an `attention` event; finish and commit keep them, because the work has not landed. `worktree.py`'s command line writes the `landed` event, which names the owners it overlapped, and releases the owner's path claims in one transaction after a guarded integration succeeds (`integrate` takes `--job-handle`), releases them after a removal and writes a `reconciled` event after a reconciliation. A failed prepare or seal, an abandon and an integration that stopped each write an `attention` event with the reason, the owner and the Job handle.
- **Never a gate.** Every hook is best effort. A failure prints one `NOTICE: claims database <state>: <reason>; continuing on derived evidence` line on standard error and the command continues; the states are `missing`, `locked`, `unreadable`, `corrupt`, `refused` and `schema_incompatible`. No hook raises into prepare, seal, approve, commit, finish, integrate or the other lifecycle operations, and none of them reads the database to decide.
- **Process liveness.** The standard library only: on Windows `ctypes` calls `OpenProcess`, `GetProcessTimes` and `GetExitCodeProcess`, and elsewhere `os.kill(pid, 0)` and the `/proc` start time. A pid whose start token differs is a reused pid, not the command.
- **Status payload.** `schema` is the string `"1.1"`; a reader accepts any minor of its own major and ignores fields it does not know. The fields are `level`, `line`, `read_at`, `windows`, `declared_without_evidence`, `database` (`state` and `message`) and `derived`. Each window has `owner`, `scope`, `state`, `job_handle`, `since`, `worktree`, `evidence`, `declared`, `command` (`pid` and `running`), `flags` (`undeclared`, `dead_command`, `age`) and `age_flag`. Schema 1.1 adds `claims` (one row per active owner: `owner`, `job_handle`, `level`, `subclasses`, `files`, `since`, `flags`), `overlaps` (`owners`, `kind` as `same_file` or `same_subclass`, the shared `files` and `subclasses`, and the `text`), `base_moved`, `stale_claims`, `owner` and `notes`. The level is FROZEN when any derived window exists, otherwise OVERLAP when two live owners share a file or a subclass, CLEAR when neither and UNKNOWN when the derived evidence cannot be read; a declared window without live evidence is listed and never freezes. The age flag shows after 60 minutes for a prepare and 10 for a lifecycle operation.

- **Path claims and overlap.** A claim lives while its transaction exists, meaning its worktree is registered and its branch exists; a claim whose worktree is gone is stale, is ignored for every decision and is counted in `stale_claims`. Two live owners overlap when they share a file (compared without regard to case), worded `same file(s): a.py, b.py` because a textual conflict is probable, or, with no shared file, a subclass, worded `same subclass, different files: checkpoint` because the change usually carries forward. The overlap is computed at read time and never stored, and it only predicts: whether an approval carries forward after the other owner lands is decided by the diff-bound proof and never by a claim. When the other owner lands, its claims are released and the waiting owner's read says `base moved: main advanced to <sha> by <owner>; <what is known>`, until its next preview, reconcile or carry. What is known comes from read-only facts: with the carry switch true and the owner's branch committed with an approval record, it says that `worktree.py carry` can try the approval, which no gate has judged yet; otherwise it says that the carry is off, that nothing is committed and approved to carry, or that the record gate would refuse. It evaluates no gate that needs work, so it never promises a carry.
- **Commands.** Run them from the primary checkout through the launcher, with `--main` naming it: `create`, `integrate` and `remove` need the main checkout, because the reviewed committed tooling owns the promotion and a candidate never re-executes itself.

- **The watch.** One line each, starting with `LANDED` or `ATTENTION`, then the reason, the owner, the Job handle and the time. A landing is the `landed` event of a guarded integration. Attention is a prepare or seal that ended `prepare-failed` or stopped, an integration that stopped, an abandoned transaction, a window whose declared command died while the window is still open or with no transaction behind it, and a Job record that the worker set to BLOCKED or whose reported activity is STOPPED while its window is open. Routine events (a window opened or closed, a claim declared or cleared) stay quiet, and so does everything that existed before the watch started. Each attention condition prints once until it clears. There is no heartbeat: a worker whose session simply ended without writing anything shows only indirectly, and the lead developer watches for that. Without a readable database it prints one notice and polls the packets, the operation locks, the worktree list and the tip of main: a landing then reads `LANDED (inferred, claims database unavailable) main advanced <a>..<b>` with no owner or Job, and a failed integration is invisible. The command reads only, never blocks the approval machinery and names no vendor.
- **Clearing.** The lead developer runs `clear` in a terminal; the tool cannot authenticate who runs it, so the rule is a convention in the briefs: workers and the Coordinator never run it and report a stale claim instead. Each claim shows a short id (`c7`), its status and its evidence: whether the worktree is registered, the branch exists and the packet state, whether the derived evidence still shows a window, the process id and whether it runs, and the Job record's state. The transaction wins over the Job record, which never clears a claim: a Job marked COMPLETE or CANCELLED while its transaction exists is shown as a conflict and stays LIVE. A window whose command died while its transaction still exists is LIVE, and clearing its claim does not unfreeze the refs, which the derived evidence still holds. Every clearing closes the claim with a `cleared` event holding the evidence, prints what it cleared and appends one line to `.local/claims/clearing.log`.
- **The lead developer's entry point.** `governance/scripts/claims.sh` finds the primary checkout from its own location and the Git common directory, starts `worktree.py` with `py -3` (or `python3`, then `python`, only when `py` is absent) and runs `worktree.py --main <primary> <command> [args]` from there: `execution-status` (alias `status`, short `-e`), `watch` (`execution-status --watch`, short `-w`), `clear` (short `-c`) and `doctor` (short `-d`). It adds no logic, prints the tool's output unchanged, returns its exit code, never adds `--apply` or `--repair` and refuses every other word with a usage line. Workers use the command form in the table.
- **The guard and the status.** The [runtime guard](#runtime-guard) refuses every GATED command at once while a lifecycle operation holds its lock, and lets the READ commands through, among them the exact read-only forms `governance/tools/worktree.py --main <path> execution-status ...` and `paths`, which must answer while an integration or removal runs. That is also why `--wait-clear` works while a window is open. Workers write no loop for the refusal: they run the command again after the operation finishes, and `--wait-clear` waits for the status.

### Components of the checkpoint tool

`governance/tools/checkpoint.py` is the command line and a thin composition. It builds the one `Checkpoint` class from four components, each a mixin class in its own module, and re-exports every name the tool, the worktree guard and the tests have always imported from it, so `import checkpoint` and `checkpoint.py --repo . <command>` behave exactly as before the split. The cut follows what each part reads and changes. The components call one another only through `self`, and share no state except the repository and the packet, so a method moved between them needs no change of body.

### Layout of the tools: commands and packages

The commands are the public interface. Every script a documented command line, `AGENTS.md`, a workflow document or a shell script names stays at its path in `governance/tools/` (`checkpoint.py`, `worktree.py`, `local_jobs.py`, `run_tests.py`, `runtime_guard.py`, `validate_continuity.py`, `show_classification.py`, `timing_record.py`, `commit_metadata.py`, `approval_words.py`, `adopt.py`) and keeps its command line. Apart from `checkpoint.py`, which is itself the facade of the checkpoint driver, each is a thin launcher (`run_tests.py` hands over to `governance/tests/run_tests.py`, which sits with the tests it runs and is importable as `governance.tests.run_tests`): it puts the repository root and the tools folder at the front of `sys.path` (absolute, resolved, once per process), enters the [runtime guard](#runtime-guard) and hands over to the implementation. The implementation lives in five packages named for what they do, mirroring the test folders, and imports its siblings by dotted package name rooted at the repository (`from governance.tools.lifecycle import checkpoint_state`), so no generic top-level name such as `support` is ever needed on the path. The tools' tests are not in these packages: they are in the sibling `governance/tests/`, in folders named like the packages (see [Test layout](#test-layout)).

### Test layout

Tests live near what they pin, in four trees:

- **Tool tests** are in `governance/tests/`, a package beside `governance/tools/`, in subfolders named like the packages they test and that are packages too: `lifecycle/` (the checkpoint tool: prepare, seal, approval, evidence, reconcile, abandon, deletion, commit metadata, early approval, approval words and review rendering), `worktrees/` (transaction worktrees and claims: the lifecycle guard, carry, execution status and path claims), `coordination/` (local jobs), `continuity/` (the classification table parser and the continuity checker, on synthetic tables and disposable fixtures) and `support/` (the test runner, the launcher, the entry points, the shared paths, timing, link retargeting and the Git stand-in). They build disposable repositories and exercise the tools, so they pin the tools and are the same in every project that adopts it. A test whose purpose is a tool stays here even when one case reads the shipped policy. `governance/tests/fake_git.py` is the shared stand-in for Git reads. The package markers (`governance/tests/__init__.py`, which also puts the repository root and the tools folder on the import path, and one `__init__.py` per subfolder) make discovery that starts at `governance/tests` find every `test_*.py`, so a policy command stays `run_tests.py -s governance/tests -p '<file>'`. Because the folder sits inside a package, the runner discovers it from the repository root, like `unittest discover -s governance/tests -t .`, and the tests keep dotted names (`governance.tests.lifecycle.test_checkpoint`). A test imports a tool module by its package path (`from governance.tools.lifecycle import early_approval`), a facade by its bare name (`import checkpoint`) and a test helper of another group by its package path (`from governance.tests.lifecycle import test_checkpoint as fixtures`). The markers are [approval-sensitive](ARTIFACT-CLASSIFICATION.md#approval-sensitive-paths): without one, its folder silently drops out of discovery.
- **Conformance tests** are in `governance/config/conformance/`, a package: the tests that read this project's real artifact classification table, policy, profiles, golden pin and reconstruction contract, and its real repository (the selector scope, the real table and its golden pin, the continuity checker on this repository, the modes of the shipped scripts). They pin the adopter's configuration content, so they sit with it and are the adopter's to change when the configuration changes; the tools can be updated without touching them. A test of a tool's behavior on synthetic input is not one of them, even when it covers the same module: the parser and the continuity checker are tested on fixtures in `governance/tests/continuity/`, and the conformance module of the same name (`test_artifact_classification.py`, `test_continuity.py`) holds the cases that read the real files. They reach the tools' test helpers by package path (`from governance.tests.fake_git import FakeGit`), which works because `conformance/__init__.py` puts the repository root on the import path. A policy command that runs them starts discovery at `config` (`-s governance/config`), the commands for the paired modules also start at `governance/tests` (`-s governance/tests -s governance/config`), and a broad command repeats the option to discover in both trees. The one command that runs the whole conformance folder is `continuity-regressions`, which discovers every `test_*.py` of `governance/config` and of `governance/tests/continuity`; [the impact selection](CHECKPOINT-WORKFLOW.md#impact-selection-beneath-profiles) selects it for any change under `governance/` or `project-governance/`.
- **Component tests** of a project's own components stay with the component they pin, with their own rows in the table and their own commands, which start discovery at the component's folder.
- **Extension tests** are in `governance/tests/extensions/`, one folder per optional extension of `governance/extensions/` (the Mission Control tests are in `governance/tests/extensions/mission_control/`). They are packages too, and they pin the extension, not the core.

**Faking Git.** A test that only needs the tool to read committed content (the classification table at HEAD, a document at HEAD, the feature file on main) uses `FakeGit` from `governance/tests/fake_git.py` and never hand-rolls `tool.git = lambda ...`. `FakeGit({'<path>': <text or bytes>})` answers `show <rev>:<path>`, `cat-file -e`, `ls-files`, `rev-parse` and `symbolic-ref` from those files, fails a missing path with the `ValueError` the tool's own Git call raises, answers every other read with empty bytes, so a read the tool starts making later does not break an unrelated test, and records its calls in `calls` (`reads('<verb>')` filters them). `others` gives a named revision, such as `refs/heads/main`, its own files, and `unavailable=True` fails every call. `bare_tool(root, fake)` builds a `Checkpoint` with no repository behind it, `patch.object(tool, 'git', fake)` puts the reads on a real tool, and `fake.rooted` serves `validate_continuity.git`, which takes the root first. A test that needs a real index, commit, worktree or a failing real command builds a disposable repository as `governance/tests/lifecycle/test_checkpoint.py` does, or wraps the real `tool.git` to inject one failure; it does not fake Git. `governance/tests/support/test_fake_git.py` pins the fake.

**Running tests.** The tests do not depend on how they are started: through the launcher and the runner, from Git Bash or PowerShell, or with plain `unittest`. One module, through the supported route: `python -B governance/tools/run_tests.py -s governance/tests -p 'test_checkpoint_abandon.py' -v` from the repository root; one module or one test with plain unittest, from the repository root: `python -B -m unittest -v governance.tests.lifecycle.test_checkpoint_abandon` (add `.ClassName.test_name` for one test). A conformance module needs the repository root and the tools folder on the import path, which its package marker provides: from `governance/config/`, `python -B -m unittest -v conformance.test_continuity`. The one environment the tests need is a working POSIX `bash` for `test_checkpoint_claims_script.py`, which tests a shell script. The test looks for it itself, first the `bash` on the PATH if it starts and runs a command, then the one of Git for Windows next to `git`, and skips with a message that says so when it finds none. It never takes the first `bash` on the PATH blindly: a PowerShell session finds `C:\Windows\System32\bash.exe`, the WSL launcher, which fails on every call when no distribution is installed, and that was all of the 42 failures seen in a plain run of five modules from PowerShell: they were the tests of this one module, while the claims, path claims and runner modules passed in the same session and the same five modules pass all 149 tests from Git Bash. Everything else the tests need they make themselves: a disposable folder and repository each, a free port, and no real repository state.

A test file is classified by its own exact row in the [artifact classification table](ARTIFACT-CLASSIFICATION.md), so a new tooling test needs its row in the transaction that adds it. Python 3.12 and later exit non-zero when a discovery finds no tests, so a command that selects one file fails if the file moves without its command.

### Validation before sealing

A prepare is a freeze window for what the transaction depends on, and for nothing else. One that selects the long `governance-regressions` suite, as a tooling change to the checkpoint tool does, took about 37 minutes (36m41s and 36m45s measured), and before and after its checks it compares the [protected set](WORKTREE-WORKFLOW.md#protected-set-ref-policy): the owner's own branch and worktree row, `main`, tags, replace refs, notes, unnamed namespaces and the Git configuration. A change to any of these in that window fails it with `Refs changed during validation`. Another mission's branch, a session branch, a remote or Codex ref, the stash and another worktree's registration may be created, removed or moved, so lifecycle work for other missions no longer waits and prepares of different missions can overlap; tolerated changes are retained by name in `transient_ref_audits`. A seal runs the same comparison and an integration rechecks the protected refs and the configuration. A packet prepared under an older policy keeps it: the [same-tree transient ref-name exception](WORKTREE-WORKFLOW.md#same-tree-transient-ref-name-policy) or, before that, the full inventory, so for such a packet any other ref, branch or worktree change still fails these comparisons.

`prepare --validate-only` selectively stages the exact candidate and retains a `validated` packet without making it approvable. Run `seal` to finish preparation; `resume` is the same operation for interrupted validation. Ordinary `prepare` still validates and seals in one invocation. Do not run a separate unbound suite expecting it to substitute for packet evidence.

Only the exact reviewed disposable regression commands that [the checkpoint evidence component](tools/lifecycle/checkpoint_evidence.py) declares replayable (`REPLAYABLE` and `IMPACT_REPLAYABLE`) are replayable. The authenticated packet holds each result, its digest and a conservative exact-input binding: transaction/repository, parent/branch, full staged tree/index/manifest, all validated working bytes (including tools/configuration), policy/profile, argv, Python executable hash/version, running driver hash, Git executable hash/version, Git configuration, environment and refs/status. Each completed check is saved atomically. Sealing records `executed` or `reused` in `validation_runs`; reused output/duration remains the original execution evidence. Whitespace, continuity, runtime/component gates and all unrecognized commands run fresh.

Before it runs any check, `seal` derives the transaction's selection again, with the same function `prepare` uses, from the live artifact classification table, policy and profiles and from the sealed manifest, message and worker context. It refuses unless the derived checks, runtime flag, per-path classification and trailer check equal the sealed ones, and it also refuses when the derivation fails, as for a blocked or frozen path. After a [bounded reconciliation](WORKTREE-WORKFLOW.md#bounded-stale-base-reconciliation) this is the step that stops a transaction whose rules changed upstream; the message tells the worker to abandon it and prepare again from the current base. A change that leaves the selection equal does not stop it.

Missing/failed evidence, mismatched bindings/result digests/argv or duplicate evidence reruns that suite. Packet HMAC failure stops for operator review: untrusted facts cannot establish a candidate to rerun. Changed candidate content or G018 facts requires reviewed re-preparation and new approval; `seal` never adopts a different candidate. Restart with `inspect`, then `resume` only after confirming no live process and resolving any retained operation lock. An interruption before staged facts exist requires explicit staging inspection. A completed expensive result can survive interruption before final sealing; no in-flight result becomes PASS. Legacy recovery commands retain their separate existing authority boundaries.

## Recovery and limits

Restart with `inspect`; approval and evidence survive restarts. After interruption around commit, use `verify`, which accepts only an exact HEAD/parent/tree/message match, empty post-commit index and preserved working/residual state. Residual comparisons use the sealed `prepared_status` after selective staging, excluding exact manifest paths. Pre-staging `residual` remains historical evidence: Git may collapse a new transaction directory into an untracked directory entry before staging, which is why `reconcile` judges unrelated dirty state from the sealed `prepared_status` instead. Unrelated paths remaining after staging and validated working-content hashes must still match; existing packets are not rewritten to correct that classification. It never retries a commit. Repeated successful verification is idempotent and recreates the same handoff bytes if the handoff write was interrupted. Unexpected HEAD or missing/tampered packets/key require operator review, not reconstruction of approval.

There is one transaction slot. A stale owned base is a normal lifecycle state eligible for explicit [bounded reconciliation](WORKTREE-WORKFLOW.md#bounded-stale-base-reconciliation), preserving the original authenticated packet and refreshing parent/index/tree bindings without clearing owned staging. Other failed/stale transactions require operator inspection; `abandon` withdraws one that has not begun to commit, so re-preparation needs no manual unstaging. Never discard unrelated staging or working content. After successful verification and required durable record promotion, use `finish` below; failed/stale transactions cannot use cleanup. Reconciliation audits remain in scratch until verified completion and are included in restart-safe cleanup. Record prose and Step-3 worker integration remain outside the tool.

Evidence reuse is transaction-local and command-specific. The replayable suites that read only tooling, configuration and authored inputs use `content-v1` bindings over manifest bytes, validation files, declared governance inputs and checkout rules, together with exact policy/profile, environment, configuration, driver and interpreter/Git identity. Parent, full tree/index and refs are excluded only for these reviewed content-only suites. Continuity regressions use `base-v3` for packets prepared under the [protected-set ref policy](WORKTREE-WORKFLOW.md#protected-set-ref-policy): the base/history facts bind the protected refs, including `main`, and nothing tolerated. `base-v2` packets keep the [same-tree ref-name policy](WORKTREE-WORKFLOW.md#same-tree-transient-ref-name-policy), whose transient names/targets remain separately audited and whose surviving-name retargeting is refused. Legacy packets retain `base-v1` and exact all-ref names; no packet or historical result is migrated. Driver/input changes invalidate old evidence under the existing rules. All other checks execute fresh. Results require authenticated exact input/output bindings and successful exit; ambiguous, changed or failed results rerun. `validation_runs` records `executed` or `reused`. Final `seal` always refreshes cheap continuity/whitespace and checks candidate integrity, and supplies no approval. A changed parent always requires fresh G018 exact approval.

No push, amend, destructive cleanup, branch switching, credential handling or Git configuration mutation is implemented. Hooks are rejected rather than trusted to preserve approved bytes. Signed commits remain deferred. Linked worktrees retain private checkpoint scratch/indexes and bind private/common Git directories plus the native ownership marker in packet identity. The separate [worktree lifecycle guard](WORKTREE-WORKFLOW.md) handles creation, fast-forward integration and removal without granting G018 authority. Tests create their own temporary repositories and identities; production never configures Git identity. Run `python -B -m unittest discover -s governance/tools -p 'test_checkpoint.py' -v` for isolated checkpoint regression coverage.


## Scratch completion

The [disposable-state workflow](CHECKPOINT-WORKFLOW.md#disposable-operational-state-2026-10-02)
governs scratch.

`finish` rechecks the exact approval receipt, immutable commit parent/tree/message,
HEAD/branch/index, configuration, validated content and unrelated status. It accepts
only a verified result. A sealed, temporary deletion journal binds those facts and
the exact packet/handoff hashes; interrupted deletion resumes only if they still
match. Cleanup deletes only the named scratch packets, handoff and journal. It is
idempotent; it neither creates a historical archive nor removes unknown files or
the receipt key. A pending runtime is rejected until its continuity records are
committed and verified. A successful tooling transaction with no new mandatory
record obligation needs no redundant durable packet: its Git commit is the result.
Normal completion additionally requires Progress and the matching runtime log to
match their committed versions, and that log to be linked from the committed
index using the existing same-directory Markdown link convention. Unrelated
uncommitted index entries need not be included.
A working-copy continuity PASS alone is insufficient durable promotion.

`continue-records` accepts a verified `follow-up-pending` runtime, atomically moves
its authenticated packet to scratch `pending.json`, and permits only explicit
Progress/devlog paths in the next normal preparation. It does not imply lifecycle
completion or continuity PASS. The subsequent transaction uses ordinary exact
approval and all normal checks; `finish` then checks the predecessor and clears both
packets. No unrelated transaction can bypass stale committed runtime continuity,
including after scratch loss. Do not delete scratch before completion.

Continuity evidence paths explicitly reject `tmp/`, including existing files;
operational handoffs cannot become authoritative reconstruction evidence.
