# Transaction worktrees

This procedure implements G025 alongside [G018 checkpoint authority](CHECKPOINT-WORKFLOW.md), [G019 source inspection](CONSTRAINTS.md#authoritative-artifact-first), and [scoped validation](CHECKPOINT-WORKFLOW.md#validation-scope). It grants no commit or integration authority. A transaction owns its filesystem, index, and branch until integration.

## Ownership and shared state

Use one temporary linked worktree for each active transaction or mission. A mission may include the runtime checkpoint and its separately approved continuity-record transaction, sequentially in that same worktree. Never give two active workers the same checkout, index or branch. Handoff transfers the existing mission to one successor after the previous worker stops; it does not create a second owner. Do not maintain permanent per-agent worktrees.

`main` is integration territory while linked worktrees exist. Keep its checkout clean and idle. Prepare changes in the mission checkout, with branch `tx/<mission-id>` and native Git lock reason `transaction:<mission-id>`. Choose a unique lowercase ID containing only letters, digits and hyphens, up to 64 characters; a date plus short purpose is useful. The ID identifies the mission, not the worker's identity or approval authority. A pre-existing branch, path, lock or checkpoint packet is an ownership conflict to inspect, never a reason to use force, reset, unlock, prune, or silently reuse it.

Git worktrees isolate working files, HEAD and index. Objects, ordinary branch refs, tags, stash, configuration and default hooks remain shared. Git's worktree lock prevents accidental removal/pruning; it is not an OS file-access lock. Workers MUST respect ownership and MUST NOT edit another worktree, write another branch ref, change shared configuration/hooks, or run unmanaged Git mutations concurrently with integration/removal. Use the guard below for lifecycle operations. It serializes those operations and excludes cooperating checkpoint commands; it is not a security boundary against arbitrary shell commands or a second process deliberately ignoring the protocol.

Machine-local state that every worktree shares follows one rule: the Git directory holds only what dies with its worktree, and everything else lives in the git-ignored `.local/` folder of the primary checkout, which is the parent of Git's common directory and is found the same way from any worktree. That folder already holds the claims database and the coordination notes; it also holds the timing record (`.local/timings/`) and the lifecycle lock (`.local/locks/`). `governance/tools/support/local_state.py` names these locations and no other file spells them. The tools create the folders on demand and refuse to write there when `.local/` is not ignored; a repository without a primary checkout (bare, or a common directory that is not a `.git` folder) has none, and they refuse instead of guessing. A clone has a primary checkout of its own, so it has its own `.local/`. This state is machine-local and disposable, but `git clean -x` deletes it (see [H22](WORKER-HAZARDS.md#h22-git-clean--x-deletes-local)). The per-checkout checkpoint store is the other half of the rule: it dies with its worktree, so it lives in that checkout's own Git directory, in the subfolder `governance/` (`<primary>/.git/governance/` for the primary checkout, `<primary>/.git/worktrees/<name>/governance/` for a linked worktree), and `git clean -x` cannot reach it ([G046](DECISIONS.md#g046---the-checkpoint-store-lives-in-the-worktrees-git-directory-2026-10-18-accepted)). Backups of `.local/` need no exclusion for the store: it is not there.

## Protected-set ref policy

The [G025 protected-set extension](DECISIONS.md#g025-protected-set-ref-extension-2026-10-12) protects what a transaction depends on and tolerates everything else, so unrelated ref, branch and worktree activity no longer fails a prepare, a seal or an integration, and prepares of different missions can overlap. `governance/tools/checkpoint.py` defines the protected set once (`ref_tolerated`, `own_worktree_row` and `ref_projection`); every site compares through it and adds only its own extras.

- **Exact:** the owner's own `refs/heads/tx/<mission-id>` branch and its own worktree registration row; `main` as the parent; every tag (a tag named like a branch shadows it in short-name resolution); `refs/replace/*` and `refs/notes/*` (they change what Git shows without changing a commit); the Git configuration (hooks, identity); and any ref in a namespace this list does not name, such as `refs/heads/feature/*`, which fails closed.
- **Tolerated:** other missions' `refs/heads/tx/*` branches, `refs/heads/claude/*` session branches, `refs/remotes/*`, `refs/codex/*` (which subsumes the same-tree exception below), the registrations of other worktrees and `refs/stash`. Our own tools still never drop, apply or modify the stash.
- **Sites:** prepare, validation and seal compare the protected refs with `main` excluded, as before; reconciliation adds the owner's worktree row; integration adds the configuration and names the owner's branch; the base-sensitive evidence binding hashes the protected refs including `main`. Without a named owner every transaction branch stays exact.

Preparation records the policy name in the packet and the full ref inventory. A change to tolerated refs retains the names added, removed and moved, without object IDs, as an audit in the packet, the reconciliation journal or the integration output. A change to anything exact stops the operation. An old packet or journal keeps the policy it was sealed with, either the same-tree policy below or the earlier exact comparison; it is never rebound or edited, and for it the earlier rule that no ref, branch or worktree may change during a prepare still applies.

Threat review. Between approval and commit, what matters is the branch tip the commit extends, `main` (the parent and the integration target), how names resolve (tags, replace refs and notes) and the hooks and configuration that run around the commit; all of these stay exact. Another mission's branch, a session branch, a remote or Codex ref, another worktree's registration and the stash do not enter the commit's tree, its parent, its message or the checks, which run in disposable repositories or read the owner's own history, so changing them cannot change what was approved. The tools use full ref names, so a tolerated ref cannot shadow an exact one. Tolerance asserts no process identity and does not defend against an actor who deliberately edits the repository; the sealed packet, exact approval and guarded fast-forward are unchanged.

## Same-tree transient ref-name policy

This policy governs packets prepared before the protected-set policy above and applies to them unchanged. The [G025 extension](DECISIONS.md#g025-same-tree-transient-ref-name-extension-2026-10-08) permits one narrow exception to exact shared-ref name preservation. Classify all refs as protected unless they are direct tree refs below `refs/codex/turn-diffs/captures/` or `refs/codex/turn-diffs/checkpoints/`. Within each exact prefix, renamed refs must retain the same multiset of tree targets, and surviving names must retain their target. New target objects, added/deleted target counts, cross-prefix moves, symbolic/non-tree refs and every other namespace still stop operations. Tree target changes are deliberately not tolerated by this version. Classification asserts no process identity and authorizes no ref deletion.

Preparation records this policy and complete ref inventory. Validation and reconciliation retain tolerated before/after names/OIDs in authenticated packet/journal evidence; integration returns the corresponding audit for the operator to retain. Protected ref names/OIDs, worktree registration, configuration, ownership and candidate facts remain exact. Base-sensitive evidence uses the same protected-ref classification and transient prefix/target multiplicity; fresh validation also checks surviving-name targets. Content-only evidence retains its existing input rules. An old packet or journal without the policy binding keeps exact ref comparison and cannot inherit the exception. Preserve it; use separately authorized abandonment/re-preparation or human-reviewed reconciliation, never packet editing.

For this guard upgrade, prepare and seal the candidate using the committed main checkpoint driver with the owned checkout as `--repo`; this keeps the current strict ref/evidence behavior until exact approval. If those guards stop, preserve evidence and inspect rather than silently switching to unapproved candidate code. After exact sealed approval, commit/verify/finish with that same driver. Only then may the committed exact approved candidate checkpoint/worktree pair run integration under the existing guard-upgrade rule below, with its reviewed checker hash. No uncommitted guard is authoritative. Changed main or failed guards stop; no automatic retry, live ref surgery or bootstrap exemption is introduced.

## Container layout

Transaction worktrees live in one container outside every checkout, one folder above the main checkout `<parent>/<repo>` and named by it, under the [G025 worktree container extension](DECISIONS.md#g025-worktree-container-extension-2026-10-10):

- `<parent>/_worktrees/<repo>/<mission-id>/` is the mission's workspace, the folder a person opens in an IDE.
- `<parent>/_worktrees/<repo>/_review/<mission-id>/` holds the mission's external review inputs: manifest, message, worker context, session and launcher inputs and decision files. From the workspace root it is `../_review/<mission-id>/`. The worker makes it with the review inputs, and it dies with its worktree: the [guarded removal](#remove-only-the-owned-completed-mission) deletes it after the worktree and the branch ([G025 review folder lifecycle extension](DECISIONS.md#g025-review-folder-lifecycle-extension-2026-10-18)).

The names `_worktrees` and `_review` are one anchor in `governance/tools/continuity/artifact_classification.py`. A mission ID cannot begin with an underscore, so it never collides with `_review`. `python -B governance/tools/worktree.py --main '<main-checkout>' paths --owner '<mission-id>'` prints the container, workspace and review folder as JSON, reads no Git state and creates nothing, so no worker guesses them. The rules below are unchanged: a worktree may not nest inside any registered worktree, main included, which is also why a folder inside the repository is not an option. Worktrees made before this layout and the app's own session folders lie outside it; `integrate`, `remove` and `reconcile` keep taking the checkout's own `--path`.

## Inspect and create

Before editing, inspect current HEAD, branch, status, index, log, `git worktree list --porcelain`, branch refs, stash inventory, AGENTS and relevant authoritative artifacts. Check for outstanding checkpoint/continuity obligations. Preserve every pre-existing worktree/ref and unrelated tracked, untracked or ignored file. Worktree creation does not import dirty files from another checkout.

Use Python 3.13 or later under the [interpreter policy](CONSTRAINTS.md#python-interpreter-policy); `python` stands for it. The lifecycle guard accesses multiple roots and requires a clean `GIT_*` environment, allowing only optional `GIT_PAGER=cat`; it never silently strips or broadens trust overrides, so start it through its launcher, whose [runtime guard](CHECKPOINT-TOOL.md#runtime-guard) removes the other `GIT_*` variables and names them. Use an appropriately authorized operator environment if sandbox access cannot cover both roots. Checkpoint commands within a single worktree retain their existing exact per-root override policy.

From the repository containing the tool, substitute reviewed full SHAs and absolute paths. The workspace comes from the [container layout](#container-layout), so no path is supplied:

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' create --owner '<mission-id>' --expected-main '<full-main-SHA>'
```

Creation requires clean, idle main, passing committed continuity, an unused branch and an absent path that does not nest inside any registered worktree, main included. `--path` remains accepted for a transition, but only when it equals the derived workspace; any other location is refused. Once every guard has passed, creation makes the missing container folders (the container and its `_review` folder) and nothing else; the mission's own review folder is made by the worker with the review inputs. It uses native `git worktree add --lock --reason ... -b ...` at the exact checked main revision; no branch reset or implicit remote selection. The returned checkout is the worker's working directory for all inspection, edits, tests, staging and checkpoint commands. Do not continue using the main directory out of habit.

The guard reserves the branch and path atomically through native Git plus a short shared lifecycle lock (`.local/locks/worktree-workflow.lock` of the primary checkout). Checkpoint preparation rejects main while other worktrees exist, rejects unowned/mismatched linked worktrees and duplicate branch registrations, and refuses occupied transaction slots. Linked packet identity binds the checkout, private Git directory, common Git directory and native ownership marker. The existing per-worktree operation lock protects checkpoint commands. Shared commit hooks are still checked at their actual common location.

## Prepare, approve and finish locally

Run the existing [checkpoint tool](CHECKPOINT-TOOL.md) with `--repo '<mission-checkout>'`, its exact `refs/heads/tx/<mission-id>` and current parent SHA. External manifest/message files remain outside governed working content. Each checkout has its own packets and integrity key in the `governance/` folder of its Git directory; never copy packets or keys to another checkout. Selective staging requires lead developer delegation; full exact-message and bound-transaction approval remains a separate stop. The sealed change category describes the artifact; its validation profile selects affected checks independently. Neither category nor profile grants approval or changes the existing runtime continuity boundary. A different parent, branch, tree, message or validated content requires new preparation and approval. No worktree operation supplies that approval. While a prepare, seal or integration runs, only the [protected set](#protected-set-ref-policy) may not change, so creating or removing another mission's worktree or branch no longer waits for it; a packet prepared under an older policy keeps the [stricter rule](CHECKPOINT-TOOL.md#validation-before-sealing).

- **Records, governance and tooling without runtime implementation changes:** run the manifest-derived checks, exact approval, commit, verification, full continuity and guarded `finish`. Do not advance the runtime implementation checkpoint or create recursive logs.
- **Runtime:** keep the mission worktree and ownership while the verified runtime commit is continuity-follow-up-pending. Use `continue-records` (the records may already be drafted; any other difference from the sealed runtime refuses, naming the paths); a separately delegated fresh worker may take over the mission sequentially to prepare its Progress/devlog follow-up. Obtain separate exact approval, commit and verify those records, restore full committed continuity PASS, then finish both packets. Do not integrate or remove a pending-runtime worktree.

Scratch cleanup completes the checkpoint lifecycle, not the mission's integration. Keep the worktree/branch reserved until integration and review are complete. Absent scratch is not proof of human approval; Git and governed records retain durable evidence, and the operator must establish the actual approved commit identities. Lost pre-completion approval evidence still requires review under G018.

## Review and integrate

One integrator owns main during promotion. Inspect the final commit range, authoritative artifacts, exact changed paths and actual evidence; Git textual compatibility cannot establish semantic compatibility. Confirm scope, source transaction approval, completed lifecycle, and integration authority for the exact source tip under [default completion and explicit stopping points](CHECKPOINT-WORKFLOW.md#default-completion-and-explicit-stopping-points). Creating a worktree or passing tests is not that authorization. Apply the owning rule before requesting another integration approval or advancing beyond an explicit stop. Changed facts or failed gates stop work, with no blind retry or bypass. No automatic push occurs.

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' integrate --path '<mission-checkout>' --owner '<mission-id>' --expected-main '<reviewed-full-main-SHA>' --expected-tip '<reviewed-full-source-tip-SHA>' --candidate-validator-sha256 '<reviewed-working-byte-SHA-256-of-governance/tools/continuity/validate_continuity.py>'
```

The guard holds the shared lifecycle lock and both checkpoint operation locks; checks ownership, clean working trees/indexes, idle scratch, exact tips, Git-operation/hook guards and committed continuity on both sides; and requires main to be an ancestor of the source tip; when it is not, its refusal says whether the [carry](CHECKPOINT-TOOL.md#the-carry) is on. Destination-compatible tooling checks pre-promotion main. The explicitly reviewed candidate checker `governance/tools/continuity/validate_continuity.py`, not its launcher `governance/tools/validate_continuity.py`, checks candidate layout and committed records, then checks promoted main through an explicit root using that same source checker and hash. Its raw working bytes must match the supplied SHA-256 and its LF-normalized bytes must equal the committed blob; destination checkout line-ending conversion does not select different executable bytes. Missing/invalid checker identity or continuity stops before promotion. This avoids asking an old-main parser to interpret a structural migration.

The integration guard and checkpoint module MUST come together from committed, reviewed main tooling, or from the exact approved candidate when this transaction upgrades the guard itself. The CLI rejects mixed roots and uncommitted driver bytes and reports tooling revision/hashes. Prefer launching from main for subsequent transactions. The guard remains authoritative for promotion; it MUST NOT load candidate checkpoint/worktree modules or candidate policy commands. Candidate continuity runs through an isolated standard-library loader with an explicit repository root. Checker review and exact hash approval are a trust boundary, not a sandbox for arbitrary Python: a hash proves identity, not correct semantics. Review candidate validator changes as executable governance before approving them.

After validation the guard independently rechecks destination/source cleanliness, exact tips, ownership, hooks and shared refs/stash/configuration. It uses `git merge --ff-only --no-autostash` against the exact SHA, verifies main's result/continuity and rechecks preservation. It creates no merge commit and does not rewrite the approved commit's parent, tree or message. Source approval remains bound to its original worktree; promotion preserves those immutable commits. Do not run checkpoint `verify` against a copied packet in main. A pre-promotion stop with unchanged facts permits an explicit retry with the same expected revisions and reviewed checker identity; no automatic retry or rebinding occurs. Retain command output, checker identity and guard revision/hashes as integration evidence.

If main changes during integration, either checkout is dirty, a branch is claimed twice, continuity is incomplete, hooks require review, or a lock is occupied, stop. Integration never reconciles implicitly. Use the explicit bounded operation below only for an eligible uncommitted transaction. A failure after fast-forward is an integration incident: retain both worktrees/refs and inspect the actual main revision; do not roll back or retry blindly. A crashed operation may leave a lock; establish that no process owns it, inspect state, and remove the lifecycle lock or the checkpoint operation lock only with the lead developer's word ([H3](WORKER-HAZARDS.md#h3-stale-lock-files)). Unknown scratch is never automatically deleted.

## Divergence and semantic reconciliation

If main is not an ancestor of the source tip, the guard fails. Do not silently rebase, cherry-pick or merge an already approved checkpoint: those operations change its identity or introduce a new commit outside the existing single-parent G018 mechanics. Preserve the old worktree/ref and approval history.

The one sanctioned way to give an approved commit a new parent is `worktree.py carry`, under the [diff-bound approval](CHECKPOINT-TOOL.md#the-carry) design: when `diff_bound_approval` reads true, the tool builds the carried commits itself and keeps the lead developer's approval only if the merge is clean, the carried diff equals the approved diff (modulo the ids of the commits carried before it), the message is unchanged, the selection derived on the new main equals the sealed one and every selected check passes again, and it records the old and new ids, the upstream range and the proofs in an authenticated audit with a notice. Never rebase or cherry-pick by hand. An uncommitted candidate whose go was given at a preview takes `worktree.py carry-go` under the same switch: it carries the go, not an approval, to the new main and moves the worktree there with the candidate on it, so the worker recreates nothing and takes no fresh go when the [go carry](CHECKPOINT-TOOL.md#the-go-carry) gates hold. With the switch off, or when any gate refuses, the rest of this section applies unchanged.

Inspect current authoritative main artifacts and the mission's approved diff. Prepare a new reconciliation mission from current main, deliberately reapply only the still-authorized changes, resolve textual and semantic conflicts, rerun affected validation and obtain fresh G018 exact approval. Runtime changes still need their own continuity-record follow-up. The old mission remains preserved until the replacement mission for the same Job has landed; then the worker that owns the old mission removes it, its branch and its review folder through the [superseded removal](#a-superseded-mission), without asking the lead developer ([G048](DECISIONS.md#g048---the-owner-removes-its-superseded-mission-2026-10-19-accepted)). The ordinary removal guard still refuses an unintegrated tip. No GitFlow, release branch hierarchy or permanent agent branch is introduced.

## Bounded stale-base reconciliation

G031 supersedes G025's new-mission requirement only for eligible uncommitted transactions. A stale base requires bounded reconciliation, not transaction discard. Inspect current authoritative main and the full upstream range before executing:

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' reconcile --path '<owned-checkout>' --owner '<mission-id>' --expected-old-main '<full-A-SHA>' --expected-main '<full-B-SHA>'
python -B governance/tools/checkpoint.py --repo '<owned-checkout>' seal
```

The operation requires a complete authenticated preparation at A, explicit ownership, unchanged working bytes/index/message/configuration, no residual dirty paths (judged on the status taken after staging, so a brand-new directory of the manifest is not residue), idle clean main exactly at B and unchanged unrelated refs/worktree registrations since preparation. Main must descend from A through one or more single-parent commits. The journal binds every commit, every touched path (including subsequently reverted changes) and the A..B binary diff hash. Case-insensitive exact and ancestor/descendant path overlap with the manifest blocks without mutation. Merge history, upstream transaction authority/policy/tool changes, checkout-rule changes, active content filters, sparse checkouts and collisions with ignored/untracked content require human review. There is no conflict resolver or automatic scope expansion.

For a safe range, the guard independently constructs the expected successor index, then uses Git's two-tree `read-tree -m -u A B` carry-forward and compare-and-swap of only the owned branch from A to B. This creates no commit, stash, reset, force update or shared-main mutation. Exact successor index/tree and working-byte hashes must match; owned working bytes and staged modes/blobs remain unchanged. Both lifecycle and checkpoint locks remain held. The changed base/tree bindings enter unapproved `validated` state, requiring `seal`, fresh checks where stale, review and fresh G018 exact approval. An old approval never carries across the parent change of an uncommitted transaction, apart from a go at an eligible preview under the [go carry](CHECKPOINT-TOOL.md#the-go-carry); a committed one takes the [carry](CHECKPOINT-TOOL.md#the-carry) or a fresh approval.

A reconciled transaction MUST derive the same selection from the successor base, or it is not sealed; re-prepare. The selection is the checks, the runtime flag, each path's resolved classification and the Class and Subclass trailer check. `seal` derives it again from the live artifact classification table, policy and profiles, using only the sealed manifest, message and worker context, and refuses unless the result equals the sealed selection. Any derivation error, such as a path that became blocked or frozen or a trailer that no longer matches, is also a refusal. Reconcile has already moved the index and the owned branch by then, so the refused transaction is unapprovable; HEAD still equals its sealed parent, which makes `abandon` legal, and the worker prepares again from the current base. An upstream change that leaves the selection equal, such as an unrelated row of the table, seals normally and keeps its reusable evidence. The review list of upstream paths above is unchanged: it sends rules text and tool code to a human, and the derivation covers what they select.

Before any live mutation, `stale-<envelope-hash>.json` retains the byte-identical authenticated old packet, including failure or approval history, and `reconcile-A-B.json` records authenticated `stale-base` inspection/planned successor facts. The successor references these superseded audit artifacts. Repeating the same range validates the completed result without rewriting it. Interruption after index carry-forward or branch update resumes only those exact recognized states; any drift stops for inspection without rollback. A killed process may leave protocol locks: existing reviewed lock recovery applies before retry; do not remove a live owner's lock. Completed audits remain until normal verified `finish`, which binds their exact cleanup inventory. They are scratch evidence, not a new permanent archive.

Content-bound evidence can replay only for the checks that [the checkpoint evidence component](tools/lifecycle/checkpoint_evidence.py) declares replayable (`REPLAYABLE` and `IMPACT_REPLAYABLE`), with exact commands, transaction identity, input hashes, policy/profile, driver/interpreter/Git/configuration/environment and authenticated passing output still matching. Their inputs include manifest bytes, validation files, declared governance inputs and checkout rules. Continuity regressions retain parent/tree/index/ref/history bindings; continuity, whitespace and integrity rerun fresh. Changed suite inputs or unsupported evidence rerun rather than inheriting PASS. `validation_runs` records execution versus reuse; final G018 still binds the complete reconciled candidate and exact message.

Transactions prepared before the required shared-context binding, incomplete staging, committed candidates, changed authority or semantic collisions require human-reviewed reconciliation under the preceding section. Do not silently unstage or transport them through shared stash.

## Remove only the owned completed mission

After integration and any necessary durable record promotion, inspect ignored files as well as normal status. Generated output is never a source of truth. Under the [local coordination procedure](LOCAL-COORDINATION.md), `.local/` is the explicit exception to disposable ignored output: record or transfer pending job material and prune terminal jobs before removal. The guard refuses any remaining file or indirect path under `.local`; it does not move notes or interpret job state. Other ignored output remains disposable under `.gitignore`. The store is not part of the working tree, and `git worktree remove` deletes it together with the worktree's Git directory, the landing and go-attempt records included. The guard still requires the checkpoint store to be idle, apart from the spent go-attempt record `early-approval.json` that `abandon` keeps on purpose, which removal alone tolerates beside the receipt key and integration still refuses; it still refuses untracked content that is not ignored, and reports the ignored files it deleted.

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' remove --path '<mission-checkout>' --owner '<mission-id>' --expected-main '<current-full-main-SHA>' --expected-tip '<integrated-full-source-tip-SHA>'
```

Removal checks ownership, exact revisions, clean indexes/checkouts, idle scratch, passing committed continuity and that the source tip is an ancestor of main. Under the shared lifecycle lock it unlocks and removes only that registered worktree, then deletes only its merged `tx/<mission-id>` branch with `-d`. It never uses forced removal, `-D`, global pruning, a recursive filesystem delete, or stash cleanup. Failed native removal attempts restore the ownership lock; partial failures require inspection, not force. Run removal from outside the worktree being removed. Existing unrelated branches and worktrees are not cleanup candidates.

The mission's own review folder, `_review/<mission-id>/` of the [container layout](#container-layout), goes last ([G025 review folder lifecycle extension](DECISIONS.md#g025-review-folder-lifecycle-extension-2026-10-18)). Nothing in it is a record: the manifest, the message and the worker context are in the commit, the previews and the sealed review were shown in the conversation, and the receipts lived in the store, which goes with the worktree. What is worth keeping is the landing notice and any carry notice, which the worker pastes into the Job record before removal ([H15](WORKER-HAZARDS.md#h15-what-a-carry-or-a-go-carry-does-not-keep)). Before anything is removed the guard checks the folder: absent, or a plain folder that holds only plain files; a subfolder, a link or a junction refuses the removal with the names, and nothing changes. After the branch is deleted it deletes exactly the files it saw and then the folder, with no recursive delete, and reports them as `review_folder`. A file that cannot be deleted, or one added meanwhile, keeps the folder and is reported there instead of failing a removal that has already happened; the Job's [closure](LOCAL-COORDINATION.md#updates-handoff-and-disposal) then finds it as a folder left behind. Another mission's review folder is never touched.

### A superseded mission

A mission is superseded when a rebuilt mission for the same Job replaced it and landed, so its own tip was never integrated and never will be. Its owner removes it after the replacement has landed, as part of the same cleanup as its own completed mission, and does not ask the lead developer ([G048](DECISIONS.md#g048---the-owner-removes-its-superseded-mission-2026-10-19-accepted)):

```sh
python -B governance/tools/worktree.py --main '<main-checkout>' remove --path '<old-mission-checkout>' --owner '<old-mission-id>' --expected-main '<current-full-main-SHA>' --expected-tip '<full-old-tip-SHA>' --superseded-by '<full-SHA-of-the-landed-replacement>'
```

With `--superseded-by`, removal replaces only its ancestry check by a proof, and refuses, changing nothing, unless every part holds: the old tip is not on main; the replacement commit is an ancestor of main; the old mission names exactly one Job, in its authenticated landing record and in its claims and windows, and a `landed` event of the claims database records the replacement commit under that same Job for another mission (a database that cannot be read refuses); the old checkpoint store is idle as for any removal, so a prepared, validated, sealed or approved packet refuses and a finished or abandoned store is accepted; and the checkout belongs to the owner named. Everything else of removal is unchanged: the lifecycle lock, no forced worktree removal, no global prune, the `.local` and review-folder checks, the review folder deleted last and the owner's claims released. Before it removes anything it appends a note to that Job's record with the old tip's full id, its subject and the replacement commit, so the work stays traceable, and a Job that cannot take the note refuses the removal. It then deletes the branch by a compare-and-swap of `refs/heads/tx/<mission-id>` against the proven tip. This is the only path that deletes an unmerged branch; `git branch -D` by hand stays forbidden. The output names the proof as `superseded_by`.

Focused coverage is included in the existing `test_checkpoint*.py` governance profile through `test_checkpoint_worktrees.py`; no component/container suite is implied. Disposable test repositories may create fixture commits. A live isolation demonstration must use an owned disposable worktree/branch, compare main's index and state, undo only its own probe, and remove the test worktree without a fake production commit.
