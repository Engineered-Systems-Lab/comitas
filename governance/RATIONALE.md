## Project impact invariants and narrowable checks: G055

**Rationale status.** Explicit.

**Decision / what we do.** The project's profiles file may add impact invariants (new names, same groups and requires semantics, over the framework's or the project's own commands), and a project profile may list the checks of its own that an impact mapping may replace (`narrowable`). A clash with a framework invariant name, an unknown group, an unknown required invariant, an unknown or required or runtime-gate check in `narrowable`, and any other key inside `impact` are refused. G045 is clarified: invariants are an addition, not a change.

**Why.** Source-stated (the Job scope of 2026-10-22, relaying the laboratory's request): a project row could use only `-` or a framework invariant, and a project profile paid every one of its checks for any path in it; the laboratory measured about 18 minutes for one profile of 159 files, a README typo included. Agent-reasoned: new names alone would not narrow anything, because the selection replaced only the two framework regression buckets and only in the framework's three narrow profiles, so a project profile needs a way to say which of its checks a mapping may replace; the opt-in `narrowable` list keeps the old behavior for every profile that does not use it and cannot reach required checks or runtime gates. Agent-reasoned: groups are checked against the merged policy at load time, which is stricter than the framework's own invariants (an unknown group there falls back to the whole envelope), because a project author can fix the file at once and a typo should not silently cost 18 minutes again.

**Alternatives.** Not recorded as considered by the lead developer. Considered by the agent: letting the overlay shadow or extend a framework invariant (rejected: it changes a framework setting, against G045); making every project profile narrowable by convention (rejected: it changes the behavior of existing project profiles on upgrade); a per-row list of checks to run (rejected: it moves the check choice from reviewed configuration into the table).

**Tradeoffs or costs.** Runtime gates are never narrowed by an impact invariant (they are refused in `narrowable`); selecting runtime gates by change would need its own design. A project that narrows trusts its own invariant map: a row naming too few invariants skips a check that the path needed. The mitigation is the existing one: the overlay file is `high`, bound by hash and shown in the seal. The explainer (`show_classification.py`) shows the narrowed list.

**Evidence.** `governance/tools/continuity/artifact_classification.py` (`merge_profiles`, `check_project_impact`, `replaceable_checks`), `governance/tools/lifecycle/checkpoint_selection.py` (`data`, `select_impact`), `governance/tools/continuity/show_classification.py` (`explain_checks`), the tests in `governance/tests/lifecycle/test_checkpoint_overlay.py`; [G055](DECISIONS.md#g055---a-project-may-add-impact-invariants-and-name-the-checks-an-impact-mapping-may-replace-2026-10-23-accepted), [G045](DECISIONS.md#g045---the-project-overlay-is-read-by-every-tool-and-the-settings-override-code-defaults-2026-10-18-accepted) and [the project overlay](CHECKPOINT-TOOL.md#the-project-overlay). This explanation grants no approval.

**Revisit when.** A project needs to narrow by symbol, a project invariant wants a framework invariant as a base, or an overlay mistake skips a check in practice.

## Project selector expectations: G056

**Rationale status.** Explicit.

**Decision / what we do.** A project may declare, in `project-governance/config/selector-expectations.json`, git pathspecs with the checks their tracked files must select and must not select. The conformance folder lists the files each pathspec matches and compares the real selection of each with the declaration, impact invariants included, and a failure is one message that names the files. A present declaration is strict; only an absent one means none.

**Why.** Source-stated (the Job scope of 2026-10-22, relaying the laboratory's finding): a tracked file with no row fails continuity and the project's golden pins what each row resolves to, but a new row with the wrong profile, added together with its matching pin, passed every check, and the laboratory could not state the expectation anywhere because the framework's selector tests are not the project's to edit. Agent-reasoned: a pathspec that is enumerated at test time keeps the declaration short and makes a new file under it subject to the expectation without a second edit, which a per-file list cannot do; judging each file by the tool's own `select_profile` means the project's invariants and `narrowable` checks are included, so the declaration cannot drift from what a change would really run. Agent-reasoned: strict reading and the empty-match failure follow G055's reasoning, that a misspelt key or a pathspec that matches nothing must not turn a guard off silently. Agent-reasoned: a declaration in `project-governance/config/` is already `high` and shown in the seal, so no new sensitivity rule is needed.

**Alternatives.** Not recorded as considered by the lead developer. Considered by the agent: a per-file list of expected profiles (rejected: it is the golden pin again and is the list that was edited together with the row); a new check in a profile or the policy (rejected: it changes selection, which is what is being guarded, and needs a command and profile of the project's own); asserting the profile name instead of check ids (deferred: two profiles can share checks, but check ids are what a change runs and a profile key can be added later); a starter file shipped with Comitas (rejected: it would be copied into every project and could not be generic).

**Tradeoffs or costs.** The test runs the selection once per matched file, a few milliseconds each, inside a folder that already runs for every governance change. A change to a file outside the two governance folders, with its row unchanged, does not run the test; a wrong row is introduced by a table edit, which does. A symbol-map row is always judged by its whole envelope, so the verdict never depends on the working tree, and a `never` on a check that a real change would narrow away can fail.

**Evidence.** `governance/tools/continuity/artifact_classification.py` (`selector_expectations`), `governance/config/conformance/test_selector_expectations.py`, `governance/tools/lifecycle/checkpoint_selection.py` (`select_profile`); [G056](DECISIONS.md#g056---a-project-may-declare-which-checks-its-paths-select-2026-10-23-accepted), [G055](DECISIONS.md#g055---a-project-may-add-impact-invariants-and-name-the-checks-an-impact-mapping-may-replace-2026-10-23-accepted) and [project governance](PROJECT-GOVERNANCE.md#selector-expectations). This explanation grants no approval.

**Revisit when.** A project needs to assert the profile name, or a symbol-map row needs a changed-symbol case.

## Freezing is always allowed: G054

**Rationale status.** Explicit.

**Decision / what we do.** Frozen files are checked against a committed checksum manifest, `project-governance/config/frozen-manifest.json`, written when they are frozen, and no longer against the runtime implementation checkpoint. `validate_continuity.py --freeze` records every frozen file that has no entry from its current content, whatever its history; an existing entry changes or goes only with `--refreeze <path>`. The checkpoint must still be the latest runtime commit. The check that the checkpoint commit changed no frozen artifact is dropped.

**Why.** Supplied by the lead developer, in their words as the Job scope of 2026-10-21 quotes them: "what is we allow the change from non-frozen to frozen to happen regardless of whether the file has been modified or not because we are rising a restriction, not lifting it..."; on the manifest, "you still suggest the recording that hash (so O2)"; on the checkpoint gate, "yes, leave it out"; and "I agree with the 3 of them" for the file name, the command with its named re-freeze and the release 0.2.0. Source-stated (the same scope, reproducing the failure in scratch projects made from the template): a runtime commit that adds a path and freezes it fails `Implementation checkpoint changed frozen artifacts`, and a path that predates the runtime checkpoint, is changed by a record commit and is then frozen fails `Frozen index differs from checkpoint`, while the order import unfrozen, small runtime commit, freeze passes. Agent-reasoned: both failures come from taking the runtime commit as the freeze baseline, so a checksum recorded when the file is frozen removes the dependence on history, and with it the dependence on a shallow clone's missing commits; the property worth keeping is that a frozen file does not change silently, which a checksum with a restricted command and a sealed Approve of the manifest change gives.

**Alternatives.** Chosen by the lead developer: a committed manifest of checksums (O2). Declined by the lead developer: an early refusal at the checkpoint gate ("yes, leave it out"). The Job scope records the chosen option (O2) and not the other options of the Coordinator's proposal, so none is listed here. Considered by the agent, not by the lead developer: keeping the checkpoint comparison beside the manifest (rejected: it is the cause of both failures); a signed manifest (deferred: the sealed Approve of a `project-governance/` change already binds its bytes).

**Tradeoffs or costs.** A project with frozen rows writes its manifest once and commits it, and the first check after a freeze needs the files staged, because the index must match the manifest. A manifest is as strong as the review of the change that writes it: nothing proves that a checksum describes the intended content, only that the content has not changed since. The old comparison also caught a frozen file changed in the runtime commit itself; the manifest catches it whenever the file differs from its entry, at the cost that a changed file and its changed entry in one approved change are accepted as a re-freeze.

**Evidence.** `governance/tools/continuity/validate_continuity.py` (`frozen_invariants`, `freeze`, `read_frozen_manifest`), the anchor `FROZEN_MANIFEST` in `governance/tools/continuity/artifact_classification.py`, and the tests `governance/tests/continuity/test_frozen_manifest.py` and `governance/tests/continuity/test_continuity.py`; [G054](DECISIONS.md#g054---freezing-is-always-allowed-and-only-changing-a-freeze-is-restricted-2026-10-21-accepted), [the frozen manifest](PROJECT-GOVERNANCE.md#the-frozen-manifest) and [continuity](COMMAND-CONTINUITY.md). This explanation grants no approval.

**Revisit when.** A project needs a frozen file to follow its own history again, the manifest grows large enough to review badly, or a second kind of freeze appears.

## Checkpoint authority: G018

**Decision / what we do.** The lead developer authorizes scope and separately approves the exact full commit message and bound transaction. Workers prepare and execute that scope; tools check mechanics. A runtime commit may have a bounded continuity-follow-up-pending phase until its actual SHA is recorded and full validation restored.

**Why.** Passing checks proves mechanical properties, not human intent. Binding approval to the parent commit, staged tree (the exact file snapshot), message, manifest and evidence prevents approval from silently applying to changed bytes. There is also a real sequencing problem: Progress and its matching log cannot contain a runtime commit's actual SHA before that commit exists. G018 names that temporary gap honestly instead of calling it PASS. Record-only commits do not trigger endless logs about logs.

**Tradeoffs or costs.** Changed approved facts require renewed preparation and approval. Runtime work needs a separate record transaction. Local keyed receipts protect local integrity, but do not prove human identity against someone controlling the tool and key.

**Evidence.** [Checkpoint workflow](CHECKPOINT-WORKFLOW.md), [tool limits](CHECKPOINT-TOOL.md), infrastructure log.

**Revisit when.** A demonstrated workflow defect prevents an authorized transaction or a new execution environment changes verification assumptions. Review the mechanics without inferring broader approval or weakening final continuity.

**Later refinements (2026-10-03 to 2026-10-05).** Three refinements followed, each prompted by use. The consent refinement let the lead developer approve with a direct command instead of copying an internal token, keeping the exact-seal binding. Natural-language recognition then failed in practice: a worker's recognizer rejected a plain "Approve" control selection and then an emphatic "Approved, approved, APPROVED !!!! :D", while correctly failing closed and committing nothing. Authorization therefore became a deterministic `approve`/`reject` decision bound to the transaction identity and complete prepared digest, with exact fallback tokens `APPROVE`/`REJECT`. A host experiment then showed that a selected control and typed text returned the same evidence, so the presentation channel was removed as an authorization predicate and one exact response table applies on every declared channel. The recurring lesson is that failing closed on the wrong predicate is still a bug: consent is to the exact transaction, not a typed password, and the boundary should validate the decision, not the presentation mechanism.

Costs: phrases such as "Approved." or "Go ahead" no longer authorize, so a host must offer an explicit control or the canonical token, and the declared channel stays required provenance. The receipt still proves local integrity, not human identity; the source remains the agent's verified assertion about the active task. Each refinement landed under the previously authoritative semantics, so neither authorized itself. Provenance: Git proves the commits and landed rules; the rejected replies, UI observation and design deliberation come from the inspected Codex chat and the lead developer's supplied account, as the Approval Incantation log states. The Birth of Meta-Governance log supports the original binding rationale: a convincing sentence cannot establish which tree was tested or which message approved.

## Disposable state: the committed checkpoint-lifecycle correction

**Decision / what we do.** Keep active transactions in ignored `tmp/checkpoint/` (later context, G046: the store moved to the `governance/` folder of the checkout's Git directory; the rest of this entry is unchanged). After approval, commit verification and required durable record promotion, explicit guarded `finish` removes packets and handoff. Git owns immutable commit content and identity; Progress, decisions, evidence reports and meaningful logs retain facts needed later. An unfinished or failed transaction retains its evidence and obligations.

**Why.** The committed workflow explicitly calls this operational scratch, not authoritative history. A runtime incident in the project the framework came from demonstrates why disposition and outstanding obligations must survive elsewhere: the runtime commit existed, but the original packet never achieved normal verification; a bounded repair and later lifecycle correction did not retroactively turn it into a verified transaction. A practical restatement of that committed rule is: **if deleting successful checkpoint scratch would destroy information still relied on, that information is stored in the wrong place.** This is this guide's synthesis of the durable-promotion requirement, not a quotation attributed to an unrecorded conversation. Operational state is not historical truth, and successful cleanup is not permission to erase unfinished evidence.

**Tradeoffs or costs.** Before cleanup, required facts must be in their existing durable homes. Lost approval evidence before completion still requires review. No permanent packet archive is required; the integrity key may remain without representing history or an outstanding transaction.

**Evidence.** [Disposable operational state](CHECKPOINT-WORKFLOW.md#disposable-operational-state-2026-10-02), scratch completion and the incident disposition, recorded in the Progress and runtime log of the time. **Rationale status.** Explicit for the lifecycle rule; the emphasized diagnostic is a labeled synthesis.

## Validation scope: G023

**Decision / what we do.** Validation scope must match change scope. The checkpoint manifest selects reviewed checks for records, governance or affected components; mixed changes combine those checks. Unclassified paths block until reviewed. G018 exact approval and continuity remain mandatory.

## Markdown link convention: G035

**Rationale status.** Explicit.

Source-stated (the Coordinator's read of the shim on 2026-10-18): the shim did five things, namely a version and capability probe, the registration of the interpreter's path and hash, the removal of `GIT_*` variables, the lifecycle gate with a 180-second wait and an exemption for `execution-status`, and running the tool; the documents showed two command forms (35 lines through the shim, 28 calling the tool directly). Source-stated (the Coordinator's correction, accepted by the lead developer): the right test for the gate is not "writes to non-local paths" but "writes shared state, or decides on Git state and then writes", because a command such as `local_jobs complete` writes only local files yet decides from Git state, and run during an integration it could read a half-changed state (a torn read: the branch gone while the worktree list still shows it) and close a Job wrongly. Agent-reasoned: two command forms were a permanent inconsistency that no document could resolve; the machine registration asked every adopter and every agent for a step that they skipped, and a registration binds a machine rather than the transaction whose drift costs time; the capability probe cannot fail where the version check passes, since the modules it imported are standard library on any 3.13, so it was dropped; a per-transaction pin placed at the first step and compared at the start of each later one makes a long prepare impossible to begin on a drifted interpreter, and `inspect`, `present` and `abandon` stay available so a drifted transaction can still be read and withdrawn; a record made before the pin existed is not compared, so in-flight work at an upgrade is not stranded. The reasons for the individual modes are agent-reasoned: `run_tests` is LOCAL because every policy check starts it and a prepare must not be refused because another mission is integrating; `validate_continuity` is READ for the same reason; `checkpoint` is GATED because it builds the checkpoint store and writes packets and receipts, and `commit_metadata` is GATED because it reads a transaction's refs and manifest and then writes, which is deciding from Git state; `timing_record export` and `import` are LOCAL (the lead developer's decision after the first registry: LOCAL covers a file the caller names explicitly, and they decide nothing from Git state), while the checkpoint tool's own recording of timings stays in-process inside the GATED command; a mode is a statement about a command that no test can prove, which is accepted; and an extension states its own mode so that the core registry names no extension.

**Alternatives.** Chosen by the lead developer: the guard in one small script called from every launcher; the pin per transaction and not per machine; refusing at once instead of waiting; keeping the version check; the three modes with a fail-closed default; the hash as the strict drift signal. Rejected by the lead developer in the design: a machine registration kept as the pin (the cost of drift is per transaction), the shim's wait of 180 seconds (workers retry), and a fingerprint check on every command (a command outside a transaction needs only the version check). Considered by the agent, not recorded as considered by the lead developer: keeping the shim and rewriting the documents to one form (rejected: the registration step and the late discovery of drift would remain); comparing the version string alone for drift (rejected: a rebuilt or replaced interpreter of the same version would pass); a gate that tests whether a command writes to ignored paths (rejected by the lead developer's own acceptance of named paths: an edit to the ignore file must not change what counts as safe); registering the Mission Control scripts in the core registry (rejected: G042).

**Tradeoffs or costs.** A GATED command is refused for as long as a lifecycle operation holds the lock, so a worker retries by hand where the shim waited. The modes are a statement about each command; a conformance test proves that every launcher is registered, not that a READ command never writes. The fingerprint hashes the interpreter's file, so an upgrade in place forces a new preview even when nothing else changed, which is the intended strictness. `checkpoint.py` is not a thin launcher and has to parse under an older Python before it can call the guard, so an interpreter old enough to reject its syntax still ends in a syntax error. The guard is approval-sensitive (`high` in the artifact classification table) and the packet change edits pinned files, so the change takes a sealed Approve.

## Shared machine-local state: G044

**Rationale status.** Recoverable.

**Decision / what we do.** Keep in the Git directory only what dies with its worktree, and put the machine-local state that every worktree shares in the git-ignored `.local/` folder of the primary checkout: the timing record moves to `.local/timings/` and the lifecycle lock to `.local/locks/`. One module names those locations. The tools create the folders on demand and refuse to write while `.local/` is not ignored, and the lock stays an exclusive create. The lifecycle lock and the checkpoint operation lock are removed only with the lead developer's word, after establishing that no process owns them.

**Why.** Supplied by the lead developer, in his own words as quoted in the Coordinator's design notes of 2026-10-16: "yes, put the store in the worktree's git directory", with the rule "files and objects that die with the worktree can stay in .git; the rest, let's try not to". Relayed without reasons of his own: the shared state is found from any worktree as the parent of Git's common directory, the check that `.local/` is ignored refuses to run when it is not, the locations are named in one small module, and the change is cut into slices, the first two being the paths in one place and the move of the shared state. Source-stated (the Coordinator's design notes): the timing record and the lifecycle lock are shared and long-lived or span all worktrees, so they cannot die with one worktree; the checkpoint store dies with its worktree and moves in a later step. Source-stated (the mission brief): the runtime registration no longer exists since G043, so there is no `.local/runtime/` folder; the template has no adopters, so there is no migration code. For the removal rule, the lead developer decided on 2026-10-18, as recorded in the Coordinator's notes, that the lifecycle lock and the operation lock gate Git and worktree operations and are removed only with his word, while the writer lock may be removed by the Coordinator after confirming that its writer stopped; the same notes quote his principle "We are building all this governance to automate the process and interrupt the developer only when there is a real need. Right? stale locks is not that case", which means this rule is the one in force until the tools can prove a lock stale themselves. Agent-reasoned: a lock created with an atomic exclusive create is the only thing that keeps two lifecycle operations from running at once, so moving it must not weaken that; checking that `.local/` is ignored at the moment a folder is created follows the way the claims code already protects its folder and turns a missing ignore rule into a clear message instead of a committed file; the primary checkout is the one place every worktree and the guard can find without configuration; a repository with no primary checkout is refused rather than guessed, because a wrong guess would put one lock or one record in two places; the runtime guard keeps its own copy of the lock's location because it runs before any repository module is trusted and under a possibly older Python 3, and the agreement test turns a drift between the two into a failing test instead of a lock nobody sees; a missing locks folder means no lock, so reads need no folder; and `git clean -x` deletes the ignored folder, so the hazard is written down next to the rule.

**Alternatives.** Chosen by the lead developer: the rule that only what dies with the worktree stays in the Git directory, and the `.local/` folder of the primary checkout for the rest. Chosen by the lead developer on 2026-10-18: removal of the two gating locks only with his word, and of the writer lock by the Coordinator, until the tools can prove staleness. Considered by the agent, not recorded as considered by the lead developer: leaving the files in the Git common directory (rejected: it is the arrangement the rule replaces, and a Git directory is not a place for shared tool state that outlives worktrees); a folder per user outside the repository (rejected: a clone must have its own state and the claims database already lives under `.local/`); moving the claims code to the new module in the same step (deferred: it already names its folder and refuses when it is not ignored, and the change would touch a file this step has no other reason to touch); migration code for a record left in the Git directory (rejected: the template has no adopters); letting the guard import the module (rejected: the guard must run under an older Python 3 before any repository module is trusted).

**Tradeoffs or costs.** The guard carries a second spelling of the lock's location, held in line by a test. A repository whose `.gitignore` lacks `/.local/` cannot run a lifecycle operation or record a timing until it adds the line, which is the intended refusal. A clone or a second machine has its own record and its own lock, as before for the Git directory. `git clean -x` loses the timings and the Job notes. Until the checkpoint store moves, state of the same kind still sits in two places. The removal rule keeps a stuck lifecycle lock waiting for the lead developer.

**Evidence.** `governance/tools/support/local_state.py`; `governance/tools/support/timing_record.py`; `governance/tools/worktrees/worktree_support.py`, `guard.py`; `governance/tools/lifecycle/checkpoint_state.py`; `governance/tools/runtime_guard.py`; `governance/tools/repo_paths.py`; the tests `governance/tests/support/test_local_state.py`, `test_timing_record.py`, `test_runtime_guard.py` and `governance/tests/worktrees/test_checkpoint_execution_status.py`; [G044](DECISIONS.md#g044---shared-machine-local-state-lives-in-local-of-the-primary-checkout-2026-10-18-accepted), [G043](DECISIONS.md#g043---the-runtime-guard-replaces-the-admission-shim-2026-10-18-accepted), [the worktree workflow](WORKTREE-WORKFLOW.md#ownership-and-shared-state) and [worker hazards](WORKER-HAZARDS.md#h3-stale-lock-files).
